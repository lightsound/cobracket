# Lifecycle transitions live in one shared table, and score changes keep a history snapshot

A tournament's lifecycle is a state machine, and it is now written as one: a tagged-union event vocabulary and a pure transition function over it. The stored state stays the single field it already was — `tournament.status`, one of `draft`, `published`, `live`, `completed` — and the events are `publish`, `editRoster`, `generateBracket`, `changeFormat`, and `recordResult`. `transitionStatus(status, event)` returns the next status or `undefined` for a forbidden transition; `eventAllowed(status, eventType)` answers whether an event can occur in a state at all. The table is data (records keyed by event and state), not conditionals scattered over the reducers, and it reproduces exactly the behaviour the guards enforced before: publication only from `draft`; roster edits, bracket generation, and format changes only before `live`; results only from `published` onward. Enforcement is server-side, in the module: the guards in `spacetimedb/src/lib/guards.ts` are event-based (`requireEvent`, `requireEventAllowed`, `requireOwnedTournamentIn`), they throw the same SenderError messages as before (`Cannot ${operation}: the tournament is ${tournament.status.tag}`), and every status change after creation goes through the one helper `updateTournamentStatus` (its only call sites are publish and reportResult); creation inserts the initial `draft` status directly, because creation is not a transition, and whole-row updates elsewhere never alter the status value. No reducer restates an allowed-status list or a next-status rule any more.

**No state-machine library is adopted.** XState and its kin are client-side libraries: a machine defined there would be a second definition of the lifecycle, living in the one place that cannot enforce it, while the module — the surface every client, including a future MCP surface (ADR 0009), actually writes through — would still need its own guards. The pattern is what transfers (a tagged union of events, a pure transition function, states as data), and it costs one small module here; a library would add a dependency and a runtime model (actors, spawned machines, interpreters) sized for interactive UI flows, which the tournament lifecycle is not. The client does not interpret a machine either: it derives which actions to offer from the same table (below), and the server remains the only enforcer.

**One table, two consumers, shared the way the format engine is shared.** The machine lives in its own package, `spacetimedb/lifecycle/`, mirroring `spacetimedb/format/` (ADR 0031): an internal `machine.ts` and an `index.ts` face that re-exports only the types and the two functions, tagged `@public`. The module imports it by relative path (`../../lifecycle` from `spacetimedb/src/lib`), the module-assembly drivers copy it beside `src/` exactly as they copy `format/`, and the client reaches it through its existing seam: `src/lib/operations.ts` re-exports the `TournamentStatus` type and `eventAllowed`, and the management page derives its gates from those (`editable` is `editRoster` allowed, `reportingOpen` is `recordResult` allowed, `canPublish` is `publish` allowed over a generated bracket). Display-only uses of the status (badges, placeholder wording) are not lifecycle decisions and do not consult the table. A status or event added later is added in the one package, and its consumers fail to compile or fail their tests until they reckon with it.

**`recordResult` carries a completion flag, because the table cannot know it.** Whether a recorded result completes the tournament is a fact only the format engine's derivation can produce (ADR 0005): it depends on the whole bracket, not on the current status alone. So the event is `{ type: "recordResult", completesTournament: boolean }`, the reducer derives the progression with the candidate result first, and only then asks the table for the next status. This keeps the one-way rule inside the table instead of beside it: from `completed`, a completing correction is allowed (`completed` to `completed`) and a non-completing one is forbidden, and that forbidden cell is exactly the reducer's old "a correction may never reopen a completed tournament" check, with its message unchanged. `eventAllowed` for `recordResult` is true in `completed` for the same reason — some corrections are legal there — even though a particular correction may still be refused once its completion is known.

**Match state is not part of this machine.** A match has no stored state to transition: its state is derived by the format engine from the bracket structure and the append-only result rows on every read (ADR 0005), and corrections and voided results are derivation outcomes, not transitions anyone performs. Building a match state machine would mean storing what is already derivable and keeping the two in agreement forever, for no new enforcement. This ADR governs the one stored lifecycle the product has.

**Event Sourcing is not adopted; a score-change history is.** Results already are an append-only record, and state is derived from them, so a general event-sourcing design — every state change as an event, state as a fold over the log — would duplicate what ADR 0005 already gives the bracket and add a projection discipline the rest of the product does not need. The one piece worth taking is an append-only change history for dispute handling, and it lands as a private table, `score_change`: one row per successful `reportResult`, written in the same transaction, holding the tournament and match ids, `changedBy` (the tournament's owner id, the same value the result row records as `recordedBy`), `changedAt`, and a snapshot pair — `previousSides`, the sides of the match's most recent result before this report (empty for a first report), and `newSides`, the validated sides this report recorded. It is read through one sender-gated view, `organizer_score_changes`, and deleted with its tournament. The history is deliberately not read off the `result` table at dispute time: result rows are engine inputs whose semantics may change as formats grow (their sides are interpreted by derivation, corrections supersede by position, voided rows linger), while a dispute asks what the score was, what it became, and who changed it — the before/after pair and the act itself, snapshotted at the moment of change, in the form it had then. The history is never an input to state derivation: nothing derives a status, a progression, or a standing from `score_change` rows, and deleting them would change no behaviour except the history's availability. It is also not the Activity Log of ADR 0014: it has no audiences, no per-audience field shaping, and no delivery; it is an organizer-facing record of score changes in their own tournaments, nothing more.

## Considered Options

- **Adopt XState (or another state-machine library) on the client.** Rejected: it defines the lifecycle where it cannot be enforced, leaving the module's guards as the real definition and the library as a drifting copy; its runtime model is built for orchestrating interactive flows, not for a four-state server lifecycle.
- **Keep per-reducer allowed-status lists and a local next-status helper.** That was the prior shape, and it worked, but every rule lived at its call sites: adding a state meant auditing every list, and the client restated the same gates as status comparisons that could silently disagree with the server's. The table makes the lifecycle one artefact that can be tested exhaustively.
- **Full Event Sourcing for tournament state.** Rejected above: derivation from append-only results (ADR 0005) already provides replay and correction semantics for the bracket, and the lifecycle itself is four states whose transitions a table covers completely.
- **Answer disputes from the `result` table alone.** Rejected above: it couples the dispute record to engine-input semantics that are free to change, and the before/after pair a dispute needs would have to be reconstructed by replaying derivation history rather than read as recorded.

## Consequences

- What tooling enforces, stated plainly: ImportLint holds the package face — `machine.ts`'s internals (the status and event enumerations, the table itself) are package-private, and only the `@public` face of `spacetimedb/lifecycle/index.ts` is importable outside it, which the gates verify. An exhaustive test in the package pins the table: a hand-authored matrix, written independently of the implementation's records, covers all four statuses against all six event instances (the four simple events plus `recordResult` with the completion flag false and true), plus `eventAllowed` for all twenty status/event-type pairs. The single status-change helper, by contrast, is structure, not tooling: nothing mechanically prevents a future reducer from writing `status` directly, and the discipline is that `updateTournamentStatus` is the one place that changes it after creation — creation inserts the initial status directly and whole-row updates elsewhere preserve it — the same honest split ADR 0031 records for the module's guard discipline.
- Adding a lifecycle state or event means updating the table and its exhaustive tests in the same change (recorded as a rule in AGENTS.md); consumers that gate on the lifecycle — module guards, the management page — take the new vocabulary from the package or the seam, never from a restated list.
- The `score_change` rows grow one-for-one with result rows, so the existing per-tournament bounds cover them: deletion takes them under the same cap as results (`MAX_RESULTS`), and no separate retention rule exists while tournaments are deleted whole (ADR 0011's disposition).
- Reversal conditions — reopen this ADR when any of these becomes true: (1) an orthogonal state dimension (visibility, registration state, a review state) is folded into the same machine and the single table's cells multiply combinatorially instead of staying readable as one record per event; (2) hierarchy, parallel regions, or history states become necessary to express the lifecycle, which is the point where a table stops being the simple representation and a library's model may earn its place; (3) a second stored lifecycle appears whose state cannot be derived the way match state is, so the one-machine assumption this design rests on no longer holds; (4) audit needs grow beyond result disputes — cross-tournament, audience-shaped, or delivered activity — which is ADR 0014's territory and should be built as that, not as an extension of `score_change`.
