# The module secret lives in a private table, seeded once at provisioning

The module has one server secret, and it lives in the module's own database: a private table, `module_secret`, holding a singleton row — a 32-byte `key` and a `keyVersion` (1 at the first seed). No view exposes the table, so the key never leaves the module. It is seeded by one reducer, `seed_module_secret`, taking the key as hex, under three rules, each refused with a SenderError that names the problem: the hex must decode to exactly 32 bytes; no `module_secret` row may exist yet; and no `identity_user` or `app_user` row may exist yet — seeding is accepted only on a completely fresh database, it binds the caller to nothing, and it creates no user. The publish procedure in every environment seeds immediately after publishing, before the database is announced or used: the standalone drivers (the connection suite, the live suite, the browser gate) generate a host-CSPRNG key per boot for their throwaway databases, and the local flow (`bun run spacetime:publish:local`) chains a seed step that keeps the developer's key in the gitignored `.spacetime-secret` file at the repo root, created with host-CSPRNG bytes on first use. This ADR amends ADR 0031's "module environment variable" sentence and ADR 0022's key-home sentence: the home is this table, not an environment variable, for the reasons under Consequences below. The copy in the owner's password manager, which both ADRs prescribe, stands — it is the recovery copy for a database that has to be re-provisioned, not a second home the module reads.

**The first derivation is the share slug.** A tournament's share slug is a bearer capability (an unlisted tournament's URL is its only guard), and the module has no CSPRNG: `ctx.random` is seeded from the transaction timestamp, which anyone can guess, and masking it with the sender Identity — a public identifier — left one organizer's slugs correlated given an observed slug and its approximate timestamp (the deepsec audit's finding against the old `randomSlug`). The slug is now a keyed derivation, minted in the module's secret library: `HMAC-SHA256(key, "slug" || 0x00 || keyVersion as u32 BE || organizer's app_user id as u64 BE || counter as u64 BE)`, encoded as 12 characters from the existing slug alphabet by rejection sampling over the digest bytes (accept a byte below 252, the largest multiple of 36 in a byte; if a digest is ever exhausted, re-derive with an attempt byte appended). The counter is per-organizer, in a second private table, `slug_counter`, and each mint consumes and stores the next value, retry attempts included. So uniqueness comes from the counter — an organizer never reuses a (keyVersion, counter) pair, and different organizers' inputs differ — and unguessability comes from the key: without the secret, an observed slug constrains nothing about any other slug. The probe-then-insert backstop on the slug's unique index stays, as does the plain-Error exhaustion throw; a database with no secret row refuses creation with a plain Error ("Module secret is not seeded"), an operational fault in the InternalError category, not a caller error. The slug is stored on the tournament row, so a future key rotation — a new keyVersion, seeded under whatever successor procedure rotation gets when it is needed — changes only future mints; published Share Links keep working.

**The first-caller race, and its closure.** A seed reducer callable by anyone invites the attack that the first caller seeds _their_ key and thereby owns every derivation. The three seed rules close it jointly: on a database anyone has used, a seed is refused (a binding or a user exists); on a seeded database, a second seed is refused; so the only database that accepts a seed is a fresh one, and the publish procedure seeds it immediately after publishing, before the database is announced. The stated residual assumption: the publisher is the only party who knows a fresh database's address before then — true of the drivers (suite-only names on loopback ports), of a developer's local standalone, and of the Maincloud cutover provisioning ADR 0031 already prescribes, where the database is created and seeded before its name is shared. A party who learns an unseeded production database's address in that window could seed it first; the window is minutes, the address is the secret until announced, and a wrong-key database announces itself at once, because the owner's own first use either finds seeding refused or finds slugs the owner's records cannot reproduce — and with no users yet, the remedy is to delete and re-provision the database.

## Considered Options

- **A module environment variable (ADR 0031's and ADR 0022's first form).** Rejected here for the three reasons under Consequences: it makes every environment that runs the module — local drivers, CI, the harness's wire-level counterparts — grow its own host env-value management long before the cutover provisioning those ADRs assumed, and it leaves the secret's presence a host fact the module cannot itself enforce or prove.
- **Derive slugs from a hash of public inputs** (organizer id, timestamp, tournament name). No secret anywhere means no unguessability: anyone who knows the inputs — all public or guessable — recomputes the slug space offline. That is the old timestamp PRNG with extra steps.
- **Store a random slug generated at provisioning time per tournament, from a seeded PRNG.** A PRNG seed is a server secret by another name, with a weaker primitive than HMAC and a state-synchronization problem (the seed's consumption must be transactional with the mint — which is exactly the counter table, at which point the keyed derivation is the simpler design).

## Consequences

- Why a table, stated once: (1) slugs need a key in every environment the module already runs in — the local drivers, CI, and the harness — long before the cutover provisioning ADR 0031 assumed, and each of those would otherwise need its own host env-value management; a table is seeded by the same publish step everywhere, with no new host plumbing per environment. (2) Presence and absence of the secret become database facts the module enforces itself — an unseeded database refuses slug-minting writes, and a seed after any use is refused — provable at the wire level (the connection suite pins both the table's privacy and the second-seed refusal); host environment values the module can only read, not govern. (3) One home serves every module derivation: this same secret is intended to key Events slice 1's email-code HMAC, the participant code (ADR 0013), and ADR 0022's dormant sanction tags, with the `keyVersion` carried over from ADR 0031's design, so each stored derivation row names the key version it was made under and rotation can dual-read until old rows expire.
- ADR 0031's Consequences said the secret "is provisioned once, at the cutover, so provisioning happens once" because the MVP needs no derivation. The slug makes that premise false — the MVP's SpacetimeDB backend needs a derivation now — so provisioning happens per environment from this ADR on, mechanically, at publish time; the cutover keeps no special secret step of its own beyond the password-manager copy.
- The harness seeds a fresh datastore with a fixed test key before tournament-creating tests, so the derivation is exercised in-process on every run, deterministically.
