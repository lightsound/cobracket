# Adopt SpacetimeDB as the backend: native Identity for sign-in, own tables and procedures, and the module layout

cobracket's backend moves from Convex to SpacetimeDB — a TypeScript module (SpacetimeDB 2.15) on Maincloud in production, and a local standalone server for development, CI, and the gates. Three reasons, in the order they forced themselves. First, the auth foundation is a dead end: Convex Auth 2.0.0 stable removed the anonymous sign-in exports ADR 0003 adopted, so the preview alpha the app runs on leads nowhere. Second, the Events design pays a continuous tax for Convex's optimistic concurrency — seat documents kept as serialization points that concurrent registrations "conflict on" while Convex retries them, per-mutation document caps sizing every Event-wide operation, a sharded counter so registrations never write a count — while SpacetimeDB executes reducers serially, one at a time in arrival order, so the naive shape is the correct one: a feasibility trial (2026-11-14) drove the deliberately naive read-check-insert-increment registration against one hot row at 1,000 registrations a second with no errors and per-connection order perfectly preserved, saturating near 15,600 a second on a throttled sandbox node. Third, subscriptions deliver per-connection row differences instead of re-run snapshots, which is the shape the spectator asymmetry (a popular Share Link has orders of magnitude more viewers than participants) wants. The same trial proved the other two load-bearing unknowns before this decision: email-code sign-in with anonymous linking built on native Identity alone, and the Solid 2 client adapter passing the diagnostics gate unchanged. This ADR supersedes ADR 0003 and ADR 0020, and the mechanism half of ADR 0021; ADR 0021's product rules stand in full and are restated below, as amended by the ADRs that amended them, and this ADR is their source from here.

**Identity needs no auth library.** A tokenless connection receives a server-issued Identity; the SDK persists its token on the client, and that token is the credential. There is no sign-in provider, no key pair, no JWKS endpoint, no refresh, no `auth:keys` — they all disappear. Resolution is one binding: an `identity_user` row maps an Identity to an `app_user` row and says whether it is an anonymous identity or an account; the first reducer call from an unbound identity binds it to a fresh `app_user` row, idempotently per identity. The client's three-way session contract survives at the seam, re-expressed: no token answers `unauthenticated`; a token whose identity resolves to an alias or to a deleted user answers `user_missing`; a bound identity answers `organizer`. The distinction is kept because a verification gap must not read as a deleted user — where ADR 0021 signed an alias or a deleted user out at the app layer because the core kept rotating its tokens, here there are no sessions to end, and thirty days of disuse is a module-side last-seen rule recorded on the identity, which ADR 0027's reaping of lost anonymous identities reads. Auth stays isolated behind the one client module ADR 0003 prescribed (`src/lib/auth`), which now wraps the connection's token and a subscription to the caller's binding row.

**The module layout** (the successor to ADR 0020's rule, translated). A top-level file in `spacetimedb/` registers reducers, procedures, and views, and nothing else registers any; the operations API of ADR 0001 and 0009 is the set of public reducers and views those modules register. A subdirectory is a library: one shared library holds validators, guards, limits, and the write modules every path must go through, and identity resolves in exactly one place — the binding module — which every reducer consults first: a reducer's first act is to check `ctx.sender` against the binding and guard tables. Pure engines with no platform dependency (the format engine) stay sibling packages, as before. Generated client bindings (`spacetime generate`) are generated code and are not edited by hand. Enforcement, stated honestly: nothing on this platform corresponds to `@convex-dev/eslint-plugin`'s require-access-control check or to the Oxlint rule that kept registration in top-level files. The guard discipline is convention, carried by tests — the module harness's guard tests and the connection-level suite — and one compensation is real: fallow sees the module directory's dead code, which its Convex plugin never let it see inside `convex/`.

**Every read is a view; every base table is private.** Access control on SpacetimeDB is per-table, not per-row: a public table can be subscribed whole and delivers every row in it — drafts, unlisted and private tournaments, other organizers' rows — and a slug is a filter the client chooses, not a boundary the server enforces. So no read surface is a table. Reads are named views: sender-gated wherever the surface depends on who is asking (an Organizer's own lists, the session views above), probed by index where the surface depends on an argument (the Share Link's slug). A view returns flat rows of a single type, so an assembled page is several views the client subscribes to, and ADR 0019's field audiences are separate view row types per audience rather than one row type with conditional fields. Procedural views probe base tables by index; they do not scan. Where a surface cannot be carried by views, the fallback is a public projection table maintained by the same reducers that mutate the base rows, holding only publish-safe fields.

**Writes are short reducers; heavy work is a procedure.** A reducer is one transaction and blocks the database's single thread while it runs, so a reducer stays short. Any computation over roughly a thousand rows is a procedure that reads, computes, and writes back in short transactions — Ranking recomputation (ADR 0025, 0030) is the standing example, and bracket generation past MVP sizes, including the 2,000-player case `docs/specs/events.md` re-opens, is a chunked procedure. Scheduled work — settle, automatic publication, deletion batches, reaping — is scheduled tables and reducers. Delivery is rows written at commit, drained by scheduled processing (ADR 0014, as amended).

## Email-code sign-in, restated (ADR 0021's product rules, as amended)

**One sign-in method: a six-digit one-time code sent to an email address.** No password. The person types their email, receives a code, types it back, and from then on is reachable (ADR 0015) under that address. A code is bound to the identity that asked for it and to its purpose (sign-in, email change, deletion, a history's hand-over), expires after ten minutes, is single-use, allows five wrong attempts, and is superseded by the next code for the address; sending is limited per address and per requesting identity, once a minute and five times an hour, and the request answers alike for every address. The mechanism is cobracket's own, as it already was in substance: the flow runs as procedures — `issueCode`, `verifyCode`, `beginLink`, `completeLink` — one short transaction each, because a reducer cannot return a value and a throwing reducer rolls back, which would erase the failed-attempt counter. The code is an HMAC keyed derivation following the `@spacetimedb/auth` pattern — one-time tokens as HMACs keyed by a server secret — rendered as six digits; the module's table stores the code's hash, never the code. The secret is a module environment variable, set once out of band when the database is provisioned, never generated or rotated by a deploy once derived rows exist, with a copy in the owner's password manager and a `keyVersion` on every row that stores a derivation, so rotation dual-reads until old rows expire; the same secret keys the participant code (`HMAC(server secret, Community id, identity id)`, ADR 0013) and ADR 0022's dormant sanction tag. The message goes through `@spacetimedb/resend` behind the module's own thin mailer interface, sent from a dedicated sending domain verified before Events slice 1, and it carries no user-typed text (ADR 0027). The verified email lives in cobracket's own table, so an account is deleted by deleting those rows and the same address can sign up again afterwards (ADR 0022). A hard bounce on a code or notice email prompts re-verification of the address — the prompt ADR 0027's no-recovery rule treats as one of the person's own routes — and never unpublishes anything. An account holds one email address. Providers that yield a verified email (Google, Discord) can be added later behind the same entry point; a sign-in that yields none (a passkey) would not make a person reachable and is not planned.

**No publish gate.** ADR 0021 required a reachable Organizer at publication; ADR 0024 then required an account for the whole Organizer side and dissolved the gate, the reachable-member invariants, and the sign-in inside the publish flow. Nothing here revives them: the subject of a permission is always a reachable account (ADR 0024), and anonymity exists only on the Registrant side, as ADR 0024 and ADR 0013 bound it. The MCP server likewise issues tokens only to accounts with a verified email (ADR 0003's token, on the surface ADR 0009 defers).

**Signing in with an email that another account already holds merges the anonymous identity into that account.** A browser's identity is minted before cobracket knows who the person is, so the same person can hold an anonymous identity Y on one device and an email account X from another — with one amendment from ADR 0027: the platform mints an identity on any tokenless connect, so the module treats an identity as unregistered until a Turnstile-verified procedure call marks it, and registering without an email — acting on a claim link included — and asking for a code are the guarded acts that mark one; every per-identity limit binds to a marked identity. There is one entry point — email, then code — and the server decides: an unknown email attaches to the current identity in place (the row is upgraded, every Entry and Entrant row follows); a known one merges Y into X. The verification spends the code and yields a short-lived proof the merge commit requires; two browsers verifying one new address serialize on the verified-email table, and the loser lands in the merge path; with nothing to merge, the empty Y is deleted, not aliased. The merge previews what Y holds — since ADR 0024, its Entries and Entrant rows, ended ones included, and the sanctions on the person, nothing else — and the two things it cannot undo later: the sanctions on Y that X takes on, and how many Communities will learn through the participant code that Y and X were one person (the code is derived per Community, ADR 0028, so the preview counts those Communities); two choices, bring them or cancel: "sign in without them" was dropped because a browser holds one identity at a time, so leaving Y behind strands it forever (a colleague's live bracket on a shared venue PC), and only cancelling changes nothing; the cancel screen points to a private window or another browser profile. The merge is one transaction, which the anonymous identity's holdings cap of 100 (ADR 0027; the cap counts Entry and Entrant rows — Y's Entrant rows in every state and each Entry it has one on, once, and an Entry holds at most 32 active Entrant rows) keeps inside one transaction. In the merge, Y's Entrant rows re-point to X; participant numbers are derived codes, so the merge re-points no number rows — the former code is stored on the identity's Entrant rows, and X's code wins. Y's `players` row is kept as an alias of X's, not deleted (ADR 0030, reversing this paragraph's first form); when X has none yet, Y's row becomes X's. Y's own row likewise stays as an alias — stripped to the mark — merged into X, so recorded actor ids need no rewrite; it never authenticates again and grants no access. Sanctions are unioned in both directions without removing an existing Entry (the Organizer, told, decides), and "sanctions" reads as sanctions of either scope, Track-scope blocks included (ADR 0027). Y's Entries that followed its account name get that name as their Track-specific name, so nothing changes on screen. Where Y held an active playing Entrant row on a Track where X holds one too, the preview asks per conflict with no default, showing the further-along Entry (results, then published, then pinned, then confirmed); the one not kept ends as `left`, cancelling its Entry only when it was the last playing Entrant, and a forming Entry only when it was the last Entrant (ADR 0029). Where re-pointing would leave the person two unended rows on one Entry, a pending row goes — the merged identity's, when both are pending — and two active rows are asked about in the same way; a pending request the merge leaves against the request rules is withdrawn (ADR 0029). Where both identities are credited in one completed tournament, both rows stay, the tournament counts once at the better placement, matches between the two are not counted, a stored Revision marks the alias row merged, a later name link or claim that would credit the merged Player there is refused, and copies already taken (seeds, prior standing) use the better row. The merge is refused when either side is suspended (ADR 0027 confirms a merge into a suspended account is refused likewise). An address that has no account gets one line on the screen after the code, saying so and naming the other address as the way in, and the account is created at that screen's confirmation, so going back leaves no empty account (the spec's merge paragraph in `docs/specs/events.md` carries the rest).

**Changing an email verifies the new one and then removes the old**, and a change to an address another account holds is refused — two email accounts are never merged in place; the one path that joins them is the deletion of one, whose preview offers to hand the deleted account's Player history to another account of the person's, verified by a code to that address (ADR 0022; built last of all, after the Player page and Rankings feature lines). The old address is told and holds a seven-day revert link (the address stays reserved meanwhile — no sign-up, upgrade, or change can verify it; reverting restores it and ends every session; a further change inside the window opens no new one, the first address stays reserved and its link reverts the chain), and deletion is refused while the window is open. A sign-in from a new device already sends a code to the inbox, so it needs no notice of its own. A session already signed in under an email account is not offered the sign-in form (it signs out first, or changes its email).

**Sessions persist on the device until thirty days of disuse**, and a signed-in email account can sign out; an anonymous identity cannot, since signing out would be losing it. The registration form embeds the sign-in: email, code, name, register, on the Event page with no navigation, with no pending Entry state and no seat held while a code is in flight (a seat belongs to a reachable person, never to a form in progress) — read with ADR 0029: on a team Track an Entry exists as `forming` before it registers, holding no seat, and "sign in to wait" is a one-player Track's question, since a team Track requires an account of every Entrant. On an anonymous-allowed Track the email field is optional, with one line saying what registering without it gives up; a full anonymous-allowed Track makes it required, since the only outcome left is the Waitlist (ADR 0015). A code arriving after the close completes the verification and the registration is refused with the reason. Claim links stay exempt from the requirement on a one-player Track; on a team Track a claim is an account's (ADR 0029). A session signed in under another email is shown "not you?".

## Considered Options

- **Stay on Convex and ride the auth alpha, or rebuild sign-in on Convex.** The alpha is a dead end regardless (2.0.0 stable removed what ADR 0003 adopted), and staying keeps the Events design paying the concurrency tax this decision exists to stop paying; the spec rewrites it forces (the concurrency section of `docs/specs/events.md`) are larger than this migration's docs.
- **Adopt `@spacetimedb/auth`** for the code flow. Its handler list is closed (password, OAuth, link-style email verification) and it exports no session-minting primitive, so the six-digit code is build-it-yourself there too; the trial proved the direct path on native Identity in about 290 lines, and one less 0.1.0 dependency owns the seam.
- **An external JWT issuer** (a small service verifies the code and signs a token the database validates, the shape another of the owner's projects runs with Clerk). It works, and it is a second deployable, a second secret, and a network hop inside the sign-in path, bought only if native binding had failed; it did not.
- **A Rust module.** The module language with the longest SpacetimeDB history, but the whole codebase — engine, tests, tooling — is TypeScript, the TS SDK at 2.15 carried the trial's three proofs, and the format engine ports into a TS module unchanged.

## Consequences

- The migration slices follow this ADR: module foundation (the six MVP tables, the format engine relocated, the module test harness, and the verification spike for the view-carried read surfaces of the "every read is a view" rule), operations parity, the client adapter at the `src/lib/convex.ts` seam, the browser gate re-booted on a local standalone, the Maincloud cutover, and the removal of Convex. Until the cutover, production keeps running Convex untouched.
- Events slice 1 (`docs/specs/events.md`) builds this ADR's sign-in — the procedures, the merge, the holdings cap — on the foundation, and, since it is the first slice to store a person's own contact data, account deletion and the privacy notice (ADR 0022). The MVP itself needs no derivation, so the sign-in flow lands with slice 1; the secret is provisioned once, at the cutover, so provisioning happens once.
- ADR 0021's Considered Options stay as its record; the options it rejected (magic links, passkeys or OAuth first, merging two email accounts in place, a third merge choice) are not reopened by this ADR — the mechanism changed, the product reasoning did not.
