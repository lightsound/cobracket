The product frame lives in [`docs/vision.md`](../vision.md); the standalone tournament is specified in [`mvp.md`](./mvp.md), and this spec changes it where noted.

**Status: draft.** Items marked _pending_ wait on questions not yet settled with the owner (listed at the end); "Implementation Slices" names the slice that needs each one.

## Problem Statement

An Organizer running a community event today collects entrants by hand — a Discord thread, a form, a spreadsheet — and then types every name into a bracket tool. Capacity, waitlists, late dropouts, invitations, and "is this bracket final?" are all managed in chat. Registrants cannot see where they stand, spectators cannot find the bracket, and every change is a message someone misses. Existing event tools (Luma) handle registration but know nothing about brackets; bracket tools (start.gg) handle both but are heavy, dated, and account-first.

## Solution

An Organizer creates an Event, adds Tracks — one per competition or split — and publishes a page. People register from that page in seconds, anonymously if the Track allows it, and always see their own status. Capacity, a Waitlist for reachable Registrants that confirms the next person automatically (or offers them the seat with a deadline, if they chose to be asked first), invite links for invitations and early access, and registration windows run themselves. When a Track should become a competition, the Organizer attaches a tournament; confirmed Entries flow into its Roster until the Organizer pins it, and publishing fixes the bracket players prepare for. Every change a person must learn of is recorded as an Activity, which is how Registrants, the other members of the owning Community, and integrations find out what happened. Everything an Organizer or Registrant can do stays in the one operations API, so MCP and a Discord bot can drive it too (ADR 0001, 0009).

## User Stories

### Organizer — the Event

1. As an Organizer, I want to create an Event as a draft with a name, description, start and end time, timezone, and an in-person place or online link, so that I can prepare it before anyone sees it.
2. As an Organizer, I want to give an in-person Event a public area and an exact address shown only to confirmed Registrants unless I choose otherwise, so that I do not publish my venue to everyone.
3. As an Organizer, I want to add Tracks to my Event — each with a name, an optional Discipline, an optional Capacity, an optional start time (for multi-day Events), a registration window, and a registration requirement (anonymous allowed, account required, or Squad-linked teams only) — so that one Event can host several competitions or splits, some stricter than others.
4. As an Organizer, I want a single-Track Event not to show the Track concept, so that a simple meetup stays simple.
5. As an Organizer, I want to publish my Event, so that people with the link can see it and register.
6. As an Organizer, I want to choose whether my Event can be opened by anyone with the link or only by people I invite, so that I can run private or pre-release Events.
7. As an Organizer, I want to make a Track invite-only, or hide it from people without an invite, so that I can run invitationals and early access next to open Tracks.
8. As an Organizer, I want to keep a Track at account required, or allow anonymous registration where speed matters more, so that prestigious Tracks are not flooded by anonymous or duplicate entries.
9. As an Organizer, I want to edit an Event after publishing, with time and place changes announced to Registrants and the Tracks' windows and invite links moved along with a reschedule, so that nobody misses a change.
10. As an Organizer, I want to cancel an Event, with Registrants notified and the page kept up marked cancelled, so that people who registered anonymously still learn about it.
11. As an Organizer, I want to delete an Event nobody relies on, and a cancelled one once it is over and a week has passed, so that test runs and mistakes do not clutter my list.
12. As an Organizer, I want to delete a Track, with its Registrants told through the Event, unless its tournament already has results, so that a mistaken Track is removable.
13. As an Organizer, I want to see the impact of any operation that takes something away from people or exposes data before it happens, from the web or from chat, so that I never do it blindly.
14. As an Organizer, I want to preview my Event as a visitor, a Registrant, or an invite holder, so that I can check what each of them sees.
15. As an Organizer, I want to regenerate a leaked link, so that people who should not have it lose access.

### Organizer — Entries and the Waitlist

16. As an Organizer, I want to add Entries by name, one at a time or pasted as a list, so that people who signed up in Discord or walked in are on the list without registering themselves.
17. As an Organizer, I want to rename or remove any Entry, and optionally sanction the person on that Track — or, as my Community's owner or admin, ban them from the Community — so that typos and no-shows are cheap to fix and troublemakers stay out.
18. As an Organizer, I want to confirm an Entry over Capacity, reorder the Waitlist, and confirm waitlisted people by hand with a notice to them, so that I stay in charge of who plays.
19. As an Organizer, I want freed places to go automatically to the next reachable waitlisted person while registration is open, so that seats fill themselves and nobody is confirmed without having agreed to it when they queued.
20. As an Organizer, I want to post Announcements to my Event and, if I connect a Discord webhook, have them appear in my server, so that everyone who should know does.
21. As an Organizer, I want to be told at once when someone in my bracket withdraws, so that I can substitute or restore them before anyone plays on — until I do, their unplayed matches are walkovers.

### Organizer — invite links

22. As an Organizer, I want to create invite links and codes (codes only where the page itself is visible, so links only on a private Event) — single-use, multi-use, or unlimited — for a Track or the whole Event, each with its own time window, and — for a single-Track link with a use limit on a capped Track — the option to reserve its seats, so that invited players, early-access groups, and late arrivals get in without special cases.
23. As an Organizer, I want to send a claim link for an Entry I entered by name, so that the person can take it over, manage it, and be notified.
24. As an Organizer, I want to revoke any invite link, undo a wrong claim, and sanction a person on this Track, or lift it, so that a leak, a mix-up, or a troll is fixable.

### Organizer — Track tournaments

25. As an Organizer, I want to attach a tournament to a Track at any time, following the Track's Discipline and Visibility, so that the Track becomes a competition when I decide.
26. As an Organizer, I want confirmed Entries to flow into the draft Roster by themselves until I pin it — by pressing "pin" or by publishing — so that registration never breaks a bracket I have settled (unless I arm automatic publication, which applies them itself) and needs no work before I do.
27. As an Organizer, I want seeds assigned randomly (reshuffled freely) or by confirmation order (later, by Ranking), with any players I choose held at fixed seeds, so that I can seed the top players and still let everyone else flow in.
28. As an Organizer, I want to see the pending changes between the Track's confirmed Entries and a pinned Roster, and apply them all, one by one, or as a substitution into a withdrawn Participant's slot, so that I control every change after I have looked (unless automatic publication is armed).
29. As an Organizer, I want to have the tournament published automatically at a time I set (by default at the registration close or the Track's start, whichever comes first), after seeing what that will publish, so that a hands-off weekly runs itself.
30. As an Organizer, I want publishing to close the Track's public registration and freeze the bracket, and unpublishing (before any result) to let me change the bracket again, so that players never see it change behind their backs.
31. As an Organizer, I want to see, before republishing, whose first match changes — and have exactly those players notified — so that a necessary change is communicated precisely.
32. As an Organizer, I want to substitute a walk-in for a withdrawn player who has not played yet, even during play, and to restore a player who withdrew by mistake with their results intact, so that a no-show or a misclick does not force a walkover.
33. As an Organizer, I want to detach a tournament from its Track while no result exists, so that a wrong start is recoverable.
34. As an Organizer of a standalone tournament, I want to make it private (visible to me only) or unlisted, so that a test bracket stays out of sight.

### Registrant

35. As a Registrant, I want to register from the Event page with only a display name, without signing up, when the Track allows it, so that joining takes seconds.
36. As a Registrant, I want to see my status at all times — forming (N of the minimum, with the Track's registration opening time shown until registration opens and its close thereafter; "waiting for the captain to register" ("waiting for the staff to register" on a Squad-linked Entry) once the minimum is reached while registration is open), confirmed (on a Track without a tournament), in the published bracket, confirmed and awaiting the Organizer's decision, confirmed before the bracket is published, not in the bracket, waitlisted with my position, or holding an Offer with its deadline — so that I never have to ask.
37. As a Registrant — or, on a team, its captain or the Squad's staff; a teammate leaves instead — I want to cancel my Entry, and to register again later (as a new Entry) if I change my mind, so that my place goes to someone else in the meantime.
38. As a reachable Registrant — or, on a team, its captain or the Squad's staff — I want to join the Waitlist of a full Track and be confirmed automatically when a place frees — or, if I choose, be asked first and given a deadline to answer — so that I get in fairly without watching the page.
39. As a Registrant, I want to register through an invite link or code, and to claim an Entry entered for me, so that invitations work for me.
40. As a Registrant, I want to see Announcements and changes relevant to me on the page and, if I am reachable, wherever I chose to receive them, so that I stay informed.
41. As a Registrant, I want to be told when I register where my display name will appear, so that I choose it knowingly.
42. As a Registrant in a Track tournament, I want to see my next match, so that I know when I play.

### Spectator

43. As a Spectator, I want to open an Event page or a Share Link without an account and see it update live — and, while the Organizer revises a published bracket, see that it is being updated (or the last publication, if the Organizer chooses to keep showing it) — so that following along is effortless.
44. As a fan with an email account, I want to follow a Community and see its four activity kinds — an Entry confirmed on a public Event, a public tournament completed with the team's placement, a Squad member joined or left, and a move in a public Ranking's standings — so that I keep up with a team without watching its page.

### Organizer — teams (ADR 0028, 0029)

45. As an Organizer, I want to set a Track's minimum and maximum of playing Entrants per Entry and its registration requirement, so that a team Track admits teams of the size my competition runs and only the people I can reach.
46. As an Organizer, I want to list a Track's forming Entries as recruiting and make teams from them, so that people who came without a team still get to play.
47. As an Organizer, I want to enter teams by name — one team per line, the first name the captain's — so that teams that formed in Discord are on the list without registering themselves.
48. As an Organizer, I want to set a Track's swap deadline — at the bracket's publication, at the team's first result, or never — so that lineups settle when my competition needs them settled.
49. As a Community's owner or admin, I want to ban a Community, so that its Squads — and those of every Community under it — cannot enter my Community's Events.
50. As an Organizer, I want Entries linked to a Squad of my Community, its ancestors, or its descendants marked as the host's team on the bracket and the registrant list, so that nobody mistakes the host's team for an outside one.
51. As an Organizer, I want to change any Entry's lineup at any time — add a person by typed name or from the recruiting list, remove one, override the ringer rule — so that a team in trouble on the day can still play.
52. As a Community's owner or admin, I want to lift a ban my Community set, so that a person or a team banned by mistake can enter again.

### Captain

53. As a Registrant on a team Track, I want to form a team and issue a join link, so that my teammates join with one tap.
54. As a captain, I want to invite Entrants of recruiting Entries and accept requests to join, so that my team fills without a second mechanism.
55. As a captain, I want to register my team once it has the Track's minimum of playing Entrants, so that we take a seat only when we can play.
56. As a captain, I want to hand the captain flag to a teammate, so that someone reachable acts for the team when I cannot.
57. As a captain, I want to swap a player before the swap deadline, so that a drop-out does not leave us short-handed.
58. As a captain, I want to see which teammates are reachable — never their participant code or an address — so that I know who gets our notices.
59. As a Squad's staff, I want to enter the Squad in a Track whose maximum is smaller than the Squad with "choose up to N", so that the lineup is mine to pick.
60. As a captain or a Squad's staff, I want to list my forming team as recruiting, so that people looking for a team find us.
61. As a captain or a Squad's staff, I want to enter "last time's team" in a new Event, so that re-entering is one step.
62. As a captain, I want to promote my ad-hoc team into a Squad of my Community, so that the team persists after the Event.
63. As a captain or a Squad's staff, I want to rename my team, once every seven days, so that a typo or a new name does not need the Organizer.

## Implementation Decisions

### Domain model

- **Community** (ADR 0023, 0028): name, its one owner, an optional designated successor, an optional parent with its ancestor ids and depth (at most three levels), Visibility (unlisted by default, private, or public), a profile (description, logo, external links, a label the owner chooses), a suspension marker, and a deleted marker (the row is kept, name only, once deleted). **Membership**: Community, user, role (owner, admin, or organizer; staff is defined, not built), joined instant. **Squad** (Community, name, Discipline hint) and **squadMembership** (Squad, user, Player, label, joined and left instants — kept after leaving, since lineup history is read from Entries). **Affiliation**: two Communities and a state. **Follow**: user, subject kind and id, email flag. Every Event and standalone tournament is owned by a Community; a person's first Community is created with their account, named after them, and may carry the person's own Squad.
- **Event**: owning Community, name, description, start and end (required, UTC), IANA timezone, mode (in person or online), area, exact address or online link, the audiences of the registrant list and the exact address, Visibility (unlisted or private; public reserved), default registration requirement, lifecycle state (draft, published, cancelled) with its publication, cancellation, and last suspension instants, whether a suspension is in force, a stop count (raised by every suspension and by cancellation), slug, a tombstone while a batched deletion runs (Tracks and tournaments carry one too), and an optional Discord webhook.
- **Track**: name, optional Discipline, optional Capacity, optional start time (defaults to the Event's start), optional registration window (opens, closes — publication pulls the close earlier), setting (open, invite-only, hidden), registration requirement (defaults to the Event's; the three-step ladder of ADR 0029 — anonymous allowed, account required, Squad-linked teams only), a minimum and an optional maximum of playing Entrants per Entry (unset, the maximum reads as the platform cap wherever it is a gate; 1/1 on a one-player Track, which shows none of it; the platform cap is 32 Entrant rows per Entry), the recruiting switch (off where the maximum is 1), the swap-deadline setting (at publication; at the team's first result, the default; never), and Offer hold time. Its scheduling state — the next due instant, indexed, and whether the Organizer has had each outcome summary — lives in a separate per-Track document (the Event has none: its instants are due instants of its Tracks, and Event-wide changes lower every Track's), and its displayed counts in a sharded counter, so registrations never write the Track.
- **Entry** (ADR 0029): Track, state (`forming` while it has no seat; `confirmed`, `waitlisted`, or `offered` with a deadline and the Event's stop count when offered; ended as `cancelled`, `removed`, or `lapsed`), team name (and whether the Organizer's rename locked the Entry), optional Squad link, an optional pointer to the Entry it continues (set when "last time's team" is used; team Rankings read it as a tie-breaker only, ADR 0030), its Participant once it is on a Roster, a denormalized count of active playing Entrants, whether it is listed as recruiting, confirmation instant, waitlist position, optional Grant it was created through, the automatic-acceptance choice, and which outcome notices it has received ("did not get a place", "not in the bracket", "no team formed"), each sent at most once. Entries are never deleted individually and never revived: each registration is a new Entry. On a one-player Track an Entry has exactly one Entrant, whose name it shows.
- **Entrant** (ADR 0029): Entry, Track (denormalized), identity (a user — an account or an anonymous identity — or none, for a typed name; and whether its identity was deleted), optional Player (set at once for an account, at claim for a typed name — no ghost Players from typos), display name (and whether the Organizer's rename locked it), `playing` (on by default; the staff turn it off on a Squad-linked Entry) and `captain` flags, a label copied from the Squad membership, the Grant it came through, a former code where a merge changed it, the instant of each state change, and a state: `invited` or `requested` before consent, `active`, then `declined`, `left` (with a pointer to the Entry the person moved to, when they moved), or `removed`. Rows that are records (`active` and after) are never deleted; `invited`, `requested`, and `declined` rows are not records, never appear on the Organizer's registrant list, and go with the account; while pending, `invited` and `requested` rows count against the Entry's maximum apart from its active rows, and `invited` ones against the sender's daily limit too (an anonymous invitee's row also counts against that identity's holdings cap).
- **Sanction** (one `sanctions` table, ADR 0029, replacing per-Track blocks and ban rows; ADR 0028's Consequences name this table): scope kind (a Track, or a Community and so its descendants), the Track or Community, target kind (a person, the primary form, or — at Community scope only — a Community), the person and the source Entrant row it was made from (present for a person target — the Entrant row absent for a Squad member banned from the ban preview —, absent for a Community target, whose row carries the target Community instead), instant, and an ended instant once lifted (rows are kept); a Community-target row is set by the banning Community's owner or admin from the ban preview or the Community page. Dormant — user id cleared, email tag, key version, expiry, the code the person had — once the person deletes their account.
- **Access Grant** (action, scope — the Event, a Track, or one Entry, a team's join link (ADR 0029); a Community or one tournament for the governance actions; one Squad for joining it —, secret, optional code unique within its Event, whether its code was deleted when the Event went private, use limit, reserving flag and cached contribution, optional end, revocation instant, withdrawing mark); **Announcement** (its own document: text, audience, edited flag); **Activity** with one subject row per subject; per-recipient **delivery** rows; stored **previews** of two-phase operations (indexed by secret and by expiry).
- **User** (display name, former names with their instants, delivery settings, or, once merged into another account, only an alias mark; a missing row is the deletion marker), **verified email** (one per user, normalized, indexed by both), **verification code** (hashed code, address, requesting identity, purpose, expiry, attempts), **Player** (non-personal, created at a person's first Entry and written on its Entrant row, kept after deletion and never deleted — a merge marks one row an alias of the other, ADR 0030), **suspension** rows (platform-wide, per person; dormant as sanction rows are — user id cleared, email tag, key version, expiry, the code the person had — once the person deletes their account). There are no participant-number rows: the code is derived (ADR 0028, Identity below).
- **Tournament** gains an owning Community in place of its Organizer, an optional Track link, a held-on date (the Event's where attached; the creation day on a standalone tournament, editable — the date Rankings place it by, ADR 0025), a seeding order (random with a stored salt; confirmation order on Track tournaments; manual, as today, once the Roster is stored; later Ranking), fixed seeds, a pinned flag, its automatic publication (off, armed, or failed; an explicit time if the Organizer set one, otherwise none stored; and, once failed, the time that was in force when it failed), and its **last publication** in its own row (structure, seed order, and which Entry each Participant stood for, by id; overwritten on each publication). **Participant** gains an Entry link (required on Track tournaments) and `creditedPlayerIds` — the Players credited with its placement, written when the tournament completes and extended when a credited typed-name Entrant is claimed afterwards (ADR 0029); its Entrants are read through the Entry; its display name is its own label.
- Whether an Event is upcoming, ongoing, or over is derived from its times; a query that gates view on time compares with the server's time itself, and settle materializes the rest (lapses, returns, Grant releases, outcome notices) when their instant is processed (ADR 0019).

### Identity (ADR 0013, 0015)

Registrants use the same Convex Auth identity and `users` table as Organizers; roles are relations: an Organizer is a member of the Community that owns the Event (ADR 0023) — "the Organizer" throughout this document means those members, and a notice to the Organizer reaches the members at the time it is sent — and every Organizer is an account with a verified email (ADR 0024); the anonymous identity exists on the Registrant side only. Account sign-in with a verified channel (a confirmed email address to begin with) ships first in this feature line, since both depend on it (owner decisions, 2026-09-30 and 2026-10-14). Registration requirement per Track (the Event's value by default) is a ladder of one setting that applies to every Entrant of every Entry (ADR 0029): _anonymous allowed_ (anonymous Entrants; a captain may type a teammate's name with a claim link), which the Organizer turns on after the page sets out what it gains (a walk-in registers in seconds from a QR code, no email needed) and what it gives up (no notices outside the app, no Waitlist, the Entrant tied to one browser, one person able to register several times, sanctions easy to evade) ⊂ _account required_ — the default: every Entrant is an account with a verified email, that is, reachable; a typed name only by the Organizer, whose entries are exempt — ⊂ _Squad-linked teams only_ (every Entry links a Squad, whose members are accounts already). Any state that waits on a later message — the Waitlist, later approval — requires reachability regardless. Under a Community tree the registration screen names the Community and its root — "T, part of R", the chain when it is longer — and the privacy notice says that the ancestors' owners and admins are also Organizers of the Event (ADR 0028). Organizer-facing data never carries user ids: people appear under an eight-character code, `HMAC(server secret, root Community id, identity id)` — two blocks of four, 40 bits, keyed and versioned like the email tag, computed in the guard that renders Organizer-facing lists and stored nowhere as a person's attribute (a former code is kept on Entrant rows after a merge, and a dormant sanction row keeps the code the person had, below) (ADR 0028) — the same across every Event of the Community tree sharing that root and uncorrelatable with any other tree's, so a tree's governors see one person as one code across its Events and Tracks (with, per Event, how many Entries each code holds, and the person's former names), a hand-over, a move or a release changes the code with the root, codes are not sequential and so leak no headcount, and nobody correlates a person across trees except through their public Player page (Further Notes). Chat surfaces authenticate as a linked user through `convex/auth.ts`, with Organizer and Registrant scopes, and confirm two-phase operations with their human (MCP elicitation).

### Account sign-in and deletion (ADR 0021, 0022)

Decided in the sign-in grilling of 2026-10-13/14. **Sign-in** is a six-digit one-time code sent to an email address — no password: a code is bound to the session that asked for it and to its purpose (sign-in, email change, deletion — the email says which), expires after ten minutes, is single-use, allows five wrong attempts, and is superseded by the next code for the same address; sending is limited per address (once a minute, five times an hour) and per requesting identity alike, and every request first passes a Turnstile check (ADR 0027), which is also where a browser without an identity gets one, since the code is bound to a session; the email carries fixed wording, the code, and its purpose, never user-typed text — and a request answers the same for every address, so nothing reveals which addresses have accounts. Addresses are compared lowercased and NFC-normalized and stored as typed, for sending. Convex Auth v2 has no such provider, so `convex/auth.ts` builds one on the core (`bindProvider`, `completeSignUp`, `completeSignIn`) with cobracket's own table of hashed codes, sent through Resend from a dedicated sending domain verified before this slice; cobracket's provider keys the core's account by the user id (the core's `USE_USER_ID_AS_ACCOUNT_ID` choice; the core itself keys accounts by provider and account id) and the verified email lives in cobracket's own table, so a deleted account's address can sign up again. Providers that yield a verified email (Google, Discord) can be added later behind the same entry point. An account holds one email; changing it verifies the new address and then removes the old, and a change to an address another account holds is refused (two email accounts never merge; transferring ownership is the remedy when one person ends up with two). Because a stolen or forgotten session could otherwise take the account for good, the old address is told of the change and receives a link, valid seven days, that reverts it — reserved means nobody can verify that address meanwhile, not as a sign-up, an upgrade in place, or another account's change; reverting restores it and ends every session — and the account cannot be deleted while a revert window is open. A further change inside the window opens no new window: the first address stays the reserved one, its link reverts the whole chain, and the window still ends seven days after the first change, so a stolen session cannot outrun the revert by changing twice. A sign-in from a new device needs no separate notice: its code lands in the account's inbox. A session already signed in under an email account is not offered the sign-in form: it signs out first ("not you?") or changes its email. Sessions persist on the device until thirty days of disuse; an email account can sign out, an anonymous identity cannot (signing out would be losing it). The form, the merge preview, and the conflict screen say that one email is one person — a parent registering children uses the Organizer's entry by name. The sign-in and registration screens link to the privacy notice.

**Who needs it.** Registrants, per Track, as the Identity section says. Everyone on the Organizer side, always (ADR 0024): creating a tournament, an Event, or a Community, holding a membership, or accepting a Grant that confers an Organizer capability needs an account, so the web UI's Organizer pages begin with the sign-in and `getOrganizer` answers an Organizer capability only for a verified account. An account's email can be changed but never removed while the account is a member of any Community, and a hard bounce prompts re-verification and never unpublishes anything. MCP tokens are issued to accounts, which every Organizer is, and act as the person in every Community they belong to.

**The registration form** embeds the sign-in on the Event page, with no navigation (an invite link's secret stays in the page): email, code, name, register. An account-required Track requires the email; an anonymous-allowed Track makes it optional under one line saying what registering without it gives up (the Entry tied to this browser, no notices outside the app, no Waitlist) — no choice buttons — and makes it required once the Track is full, since the only outcome left is the Waitlist (on a team Track the test is the captain's, asked when the Entry registers into a full Track — "sign in to wait" — and never of teammates, ADR 0029). A seat belongs to a reachable person, never to a form in progress: there is no pending or unverified Entry state and nothing is held while a code is in flight; two people verifying for the last seat both become reachable and the registration decides, serialized on the seat document. The form stays open while the code travels (resend after a minute, or change the address), a code arriving after the close completes the verification and the registration is refused with the reason, a person already signed in sees only name and register, and a session signed in under another email shows "registering as a***@x — not you?", which signs out into the email step. The name step is pre-filled from the account and editing it sets a Track-specific name. Claim links stay exempt from the requirement and show the optional field. A person who already holds an Entry sees their status instead of the form.

**Signing in with a known email merges the browser's anonymous identity into that account.** One entry point — email, then code — and the server decides: an unknown email attaches to the current identity in place (the row is upgraded; every Entry follows, and the account's first Community is created); a known one merges. The code is spent by the verification, so the verification yields a short-lived proof (ten minutes, bound to the session) that the merge commit requires; two browsers verifying the same new address at once serialize on the verified-email table, and the loser lands in the merge path. With nothing to merge the sign-in just completes and the empty anonymous row is deleted rather than kept as an alias. Otherwise a preview lists the anonymous identity's Entrant rows (ended ones included), says that their Organizers will see them as this account's (naming how many Community trees, named by their roots, will see the code change on those rows, and so learn that the two were one person), lists the sanctions on the anonymous identity that the account takes on, says that public results reach its Player page, and offers two choices: bring them, or cancel (the cancel screen suggests a private window or another browser profile; a browser holds one identity, so no "sign in without them" exists). An anonymous identity owns nothing on the Organizer side (ADR 0024), so the merge is one transaction, which the anonymous holdings cap keeps inside Convex's limits (Performance): Entrant rows re-point to the account, and their Player link follows: the merged identity's `players` row is never deleted — it stays as an alias of the account's (reads resolve the alias, as `users` aliases resolve; Revisions and chains hold Player ids as stored inputs, ADR 0030), and when only the merged identity has one, that row becomes the account's; a merge triggers recomputation of the Ranking Seasons that counted either; the person's code changes with the identity id, so the former code is stored on their Entrant rows and the Organizer's list says it changed (ADR 0028); sanctions on the person are unioned without removing any existing Entrant row (the Organizer, told, decides); the merged identity's Entrant rows that followed its account name get that name as their Track-specific name, so nothing changes on screen (a later rename of the account does not reach them); the anonymous row stays as an alias — stripped to the mark, holding no name or setting — marked merged into the account, so recorded actor ids need no rewrite, and `resolveSession` answers an alias as signed out, so the old session never authenticates or grants access again. Two active playing Entrant rows on one Track are a conflict the preview asks about per Track with no default, showing which is further along (results, then published, then pinned, then confirmed); the row not kept ends as `left` — its Entry cancelled when it was the last playing Entrant, which on a one-player Track is the ordinary cancellation — the other team and the Organizer told (ADR 0029). The operator's suspension of a person (ADR 0027, Abuse prevention below) refuses a suspended anonymous identity the merge, offering only cancel, and the dormant rule below covers suspensions as it covers bans.

**Players.** A `players` row holding no contact data — still a key that links one person's records, so personal data in law — is created at a person's first Entry and written on their Entrant row; it is the key Rankings aggregate on and a Player page shows, and it survives the account (a person who deletes and signs up again is a new row, and Rankings treat the two as two people — ADR 0025). The row is never deleted: a merge marks it an alias of the surviving row, and reaping keeps it (ADR 0030) — a published Revision must never point at a missing key.

**Names.** The account-rename rule of 2026-09-30 stands: a rename reaches every Entry following the account name, past ones included, when the person so chooses; Organizer renames lock, Track-specific names stay. Records show one name — the current one; former names are the Organizer's history, never displayed beside it, and an Organizer sees only the former names the person used while holding an Entry with them (read from the names' instants against those Entries' lifetimes; the current name is always shown, so the Organizer can tie the name they knew to it). After an account's deletion its names stay as they were (a person may rename before deleting; that is theirs to do). A Player page gets a switch to hide itself, in its own feature line, and is hidden by default once the account is deleted (below); offensive names are an Organizer's rename and lock or the operator's suspension, not a display rule — and the Organizer's rename and lock work on an Entrant row whose person has deleted their account too, so a name changed just before deletion is theirs to fix.

**Deleting an account** is two-phase: a preview lists the impact (the Communities the person leaves and who becomes their owner, the Communities that end with them and the Events of theirs that will be cancelled, brackets that will stop, Entries that will end, tournaments that go, what cannot be recalled) and offers one choice — keep the Player page visible, off by default, since a profile that aggregates one person's results is not a record the way a bracket is, while the `players` row stays as the Rankings key either way — and a fresh email code confirms it (an anonymous identity confirms with its session); there is no grace period, and a deletion is refused while an email change's revert window is open (above). The first transaction deletes the `users` row (display name, former names, settings), the verified email, and the account's MCP tokens, so sessions die (at the app layer: `resolveSession` answers a missing user as signed out, since the core keeps rotating tokens for thirty days) and a missing row is the marker every later write and delivery to that person checks; everything below runs afterwards in batches behind that marker, as an Event's deletion runs behind its tombstone — each Event of a root Community they were the sole member of cancelled as its own Event-wide operation under the per-Event caps (Performance), their Entrant rows, memberships and Squad memberships, Follows, in-app deliveries addressed to them, code rows, rate-limit rows, and stored previews paged in bounded batches — since an email account has no holdings cap and a deletion must never fail for owning too much (nothing is paged for participant codes: there are no rows, the code is derived — ADR 0028). Rows keyed by an alias of the account (its deliveries, which the merge left in place) are deleted in the same batches, and the alias rows themselves go in the last batch, once nothing is keyed by them; until then an alias whose account row is missing reads as deleted too. Records are never edited: names stay in Entries, Participants, brackets, results, and notices (which resolve people through the Entry at read, so hold no copy); the identity on an Entrant row is cleared, while actor ids on results and Activities stay and resolve to "deleted account". The person's unended Entrant rows in Events not yet over end as `left` through the one Entry-state module (ADR 0029) — the Entry is cancelled only when they were its last playing Entrant, which on a one-player Track is the ordinary cancellation: the seat moves on, derived walkovers follow; the Organizer and the team are told; their Entrant rows in Events over lose their identity, are marked identity-deleted — distinct from never claimed, so no new claim Grant can be issued for them — and stay with everything else; their identity-deleted rows are no longer offered by the Entry's claim link ("which one are you?"), and the Entry's claim Grant is revoked only when it has no other claimable typed-name row; their Squad memberships are kept as left rows (ADR 0028's amendment of ADR 0022); settle skips an Entrant whose user row is missing. On the Organizer side (ADR 0023) the person's memberships end: a Community with other members keeps everything and, if the person was its owner, ownership passes to the member they designated, else to the longest-standing member, else — for a child Community — to the parent's owner (ADR 0028), who is told; Grants belong to the Event and stay. A root Community whose sole member they were ends with them (a child's ownership passes upward instead; a detached child whose sole member was the same person ends as a root does) — its child Communities are detached as roots first and the row stays as a deleted marker holding the name, so pages still say who ran its Events — and for its Events only capabilities go: the Organizer attribution becomes "the Community's account was deleted", the Discord webhook is deleted after the cancellation notices went out, the Community's Grants are revoked, its sanction rows and dormant rows are deleted (a detached child first receives copies of the bans it inherited that target account-holding people; dormant email-tag rows stay with the frozen parent, ADR 0028). Its drafts are deleted. An Event that is over is kept whole, results or not. One not yet over is cancelled by the system with the usual notices in their own wording (no Organizer remains to record results or confirm anyone): with a recorded result it is kept forever; without one, the cancellation writes a removal instant — the later of the Event's end and seven days after cancelling — that an internal function acts on, deleting the Event unless a tournament of it has a result by then. The "over" rule applies to Events already over at deletion. A standalone tournament with a recorded result is kept (a live one stays as it stands, which the preview says); one without is deleted. All Event content stays under its frozen Visibility — description, area, exact address, online link, Announcements and other people's inbox copies of them — since nobody new gains sight of it; the preview offers to clear content first, and a request afterwards — about content, or about a name in records — is for the operator to redact, a name through the `players` row across every record of that person, as a pseudonym fixed per Player (ADR 0027). There is no archived state. A cleared browser is not a deletion: a lost anonymous identity is reaped once its session has expired, thirty days after its last use, since nobody can use it after that (ADR 0027; it owns nothing on the Organizer side, ADR 0024), and reaping never cancels an Entry (ADR 0022's rule stands): it removes the identity from the identity's unended Entrant rows, which stay as typed-name rows the Organizer can act on — rename, remove, or claimable by a claim link the Organizer issues — and the Entry stays; rows in Events over lose their identity the same way and stay, shown to the Organizer as identity-less. Account deletion is the one that ends rows as `left` and cancels the Entry when the person was its last playing Entrant.

**Sanctions survive deletion.** For email accounts under a Community-scope sanction — a ban — (or, once it exists, an operator suspension) at that moment, and for nobody else — an anonymous identity's ban ends with it, the known gap of free identities — the existing row goes dormant: user id cleared, a tag `HMAC-SHA256(server secret, canonical email)` — the address lowercased, NFC-normalized, its `+suffix` stripped and, for Gmail domains, its dots removed, so a plus-suffix does not evade the tag — the key's version, and an expiry twelve months from deletion; an email change made under a sanction tags the old address at the change as well. Every email verification looks its tag up and re-attaches the dormant rows to the new user, who is told and given a route to the operator (a reassigned mailbox can inherit a stranger's ban); an account already banned by the same Community keeps one row. Track-scope sanctions are not carried: one is a Community's judgment about one Track, which it escalates to a Community-scope sanction when it should follow the person. A dormant row keeps the code the person had, so the Community's list still recognises the person; the code is derived from the identity id (ADR 0028), so the new identity's code is simply its own and nothing is reconciled at re-attachment. The key lives in a deployment environment variable with a copy kept outside the deployment, versioned so rotation keeps old rows until they expire; the deploy never generates it (unlike the auth keys) once dormant rows exist, so a lost key is noticed rather than a silent amnesty, and a leaked version's rows are dropped. A Community's end deletes its sanction rows (a member's deletion ends none), not the operator's suspensions; erasing a tag on request is the operator's call (a suspension's stays, a Community-only one is erased once the person is identified — by the operator computing the tag of an address proven outside the sign-in flow, since verifying in cobracket would re-attach the rows). The privacy notice and the ban notice say so.

### Communities and roles (ADR 0023, 0024)

Decided in the grilling of 2026-10-14. **Ownership.** Every Event and standalone tournament is owned by a Community, and bans, participant codes (derived per Community tree, ADR 0028), Squads, and (later) Rankings are the Community's. A person's first Community is created with their account and named after them; it is an ordinary Community — renamable, able to take members, leavable — and a person creates more at will; one who belongs to none gets a new one when they next create something. "The Organizer" of an Event is any member of the owning Community with the capability in question — an owner or admin of an ancestor Community included (ADR 0028); one guard function answers it for every public function (ADR 0020). Members see everything the Community runs, past Events and their registrant lists included — never a Registrant's email address — and the invitation screen says so. A member may register on their own Community's Tracks and record their own results (ADR 0005 records who did). An ancestor's ban binds a member registering on their own Community's Track as it binds anyone — the ban gate reads every Entrant, Organizer self-entries included, and the child cannot waive it; a Community ban does not apply to the same people entering ad hoc, which the preview says, since the person ban is what follows people (ADR 0028). The Organizer's home groups Events and tournaments by Community once the person belongs to more than one (layout: the UI/UX pass).

**Roles.** A membership row carries a role; a capability table in `convex/model` maps roles to capabilities, and every finer permission is a row or column of that table, never a per-member flag. Built in the Communities slice: _owner_ — exactly one per Community —, _admin_ (member management and Event hand-overs, but not Community deletion or ownership transfer; with the owner, the tree's governance reaching down to descendants, so neither governance nor member management depends on one owner), and _organizer_; defined for later: _staff_ (results, Entries, the Waitlist, and check-in only). The table is in ADR 0023; ADR 0028 adds four rows, marked so in the table: create, move, release, and delete a child Community and name its owner (owner, admin — applying downward); create and delete Squads, edit their players and labels (owner, admin, organizer); operate Squad-linked Entries — register, lineup, Offers, cancel — (owner, admin, organizer, staff); plus remove a player from a descendant's Squad (owner, admin). "The staff" in the team sections of this document means the Community's members acting for its Squads and Squad-linked Entries, whatever their role, ADR 0023's `staff` role included. The owner — and an admin, for member management — invites, removes, and re-roles members; the owner alone renames, transfers ownership (to a member, who is told), and deletes the Community (a child may also be deleted by its parent's owner or admin, ADR 0028); an organizer does everything on an Event, cancelling and deleting included, and leaves at will; the owner leaves only after transferring. The owner may designate a successor; on the owner's account deletion ownership passes to the successor, else to the longest-standing member, else — for a child Community — upward to the parent's owner (ADR 0028), and a root Community with no other member ends with the account (Account sign-in and deletion). A one-off helper is not a member: a Grant with the action "record results on this tournament" (a window, a use limit, revocation; it grants view of that tournament's organizer surface only).

**The tree (ADR 0028).** A Community may be the child of exactly one other — no cycles, at most three levels; the parent, its ancestor ids, and the depth are stored on the row — and a child is created by the parent's owner or admin, who becomes its owner or names another member of the parent as its owner. Ownership is the only relation that forms a tree, because everything that must be unambiguous hangs on it: the parent's owner and admin roles apply to every descendant as to the parent (they re-parent, delete, and re-role a child, remove players from its Squads, and see its registrant lists — one person as one code, since the tree shares a root), while organizer and staff roles are confined to their node, so a parent who wants to help run a child's Event joins it. A move — a node with its children, to another parent — is an Access Grant with the action "move a Community under another", in the direction member invitations take: the receiving side (its owner or admin) issues it and the owner or admin of the node's current parent accepts — the node's own owner when it is a root — (the same person governing both does it in one step; a move out to the root is instead the parent's release, which needs no Grant and not the child's consent, and a child's owner cannot leave the parent without release: they ask, or re-create); the Grant is single-use, lasts seven days, is revocable, and stores its secret hashed like the other governance Grants; a move that would exceed the depth is refused with the reason and the ways out — move to a shallower parent, detach children first, or stand as a root; a move or a release is recorded as an Activity on the moved node, so its page says where it came from, and changes the code of every person on the subtree's registrant lists with the root (Identity). Structural changes are notified: a move, a release, and a child's deletion reach the parent's members (ordinary notices stay with the owning node's members; ancestors learn by looking), and when a root joins another tree, Registrants of its Events that are not over are told that who sees their lists changed, as a hand-over's notice does, finished Events getting the list Activity only. Deleting a Community is refused while it has children (below); the deletion of a root's sole member's account, which cannot be refused, detaches the children as roots and freezes the parent (a child's ownership passes upward instead). Succession of a child's owner resolves upward — designated successor, longest-standing member, the parent's owner — and a root with no member other than its absent owner and no designated successor can be claimed under the absence rule (Abuse prevention) by a child's owner as the last candidate.

**Squads (ADR 0028).** A Squad is a standing list of Players a Community keeps for competition — several where it fields more than one unit, at most 20, each of at most 100 Squad members — named by the Community's name plus its own where the Community has several; its Discipline is a hint for the registration form, never a constraint. Joining needs an account and is standing consent to be entered in tournaments by the Community's staff ("the staff may enter you in tournaments; you are told every time and may leave any time"), and membership is public — on the team page and on the person's own Player page (a hidden Player page shows the name without a link, as Rankings do) — which the join screen says. Joining is an Access Grant with the action "join this Squad", with the mechanics of the Community invitation (a use limit, a seven-day window by default, revocation; whoever opens it signed in joins once they accept the join screen), issued by whoever may edit the Squad; promoting an ad-hoc team issues one single-use such Grant per account Entrant, delivered as a notice. It confers no permission: the Squad is a list of Players, the staff a list of members, and one person may be on both. Each Squad member may carry one free-text label of at most 20 characters (coach, manager, sub, analyst — suggestions, not a vocabulary), set by whoever may edit the Squad (owner, admin, organizer), display-only, treated as a name for reporting and redaction. A Squad member leaves at will and whoever may edit the Squad removes at will; nobody is held on a Squad, and the membership row is kept after leaving, since lineup history is read from Entries. **Affiliations** are mutual, permission-free links between two Communities, shown on both pages and sharing no permission, ban, or code — leagues, federations, circles of clubs; at most 50 per Community; a request is rate-limited per account and expires, and a declined one is not repeated. The test for parent versus affiliate: "would you accept their bans and let their governors see your registrant lists?" — yes is a parent, no an affiliate.

**Bans (ADR 0028)** are the Community-scope sanction rows (Entries, below). A Community's ban applies to its Events and to every descendant's, which cannot lift it but may add their own — read along the ancestor ids. Its target is a person (the primary form: it follows the email tag) or a Community (that Community's Squads and every Squad in its subtree cannot be entered in the banning Community's Events; the ban preview offers to ban the current Squad members as people too, since a banned team can re-form under a new Community; a Community ban does not follow a former descendant once it is detached, released or moved out). Inherited bans are visible read-only to the child's owner and admin, labelled "ban by <ancestor name>". Re-parenting applies the new ancestry's bans to new registrations only — existing Entries stay, and the move preview counts them, as a hand-over's does; a detached child — released by a living parent or set free by a root's sole member's account deletion — receives copies of the bans it inherited that target account-holding people, each copy carrying its origin and expiry, dormant email-tag rows staying with the parent, frozen or not. Bans touch neither memberships nor Squads: they are registration gates, told to the banned person only, when they try to register; how a team's registration is refused without naming the member is under Entries.

**The Community page** (`/c/:id`) is one template whose sections appear when they have content: a competitor face shared with the Player page (Squads, tournaments entered, placements, standings in public Rankings — public tournaments and public Rankings only, `canDiscover`, as the Player page), an Organizer face (Events hosted, Rankings published), structure (members with their roles, shown unless the owner hides the section, a hidden Player page leaving the name without a link; child Communities; affiliates), and a profile — a description (links carry `nofollow ugc`), a logo (the first user-uploaded image: image types only, at most 512 KB, hidden while a report is under review and removed as the sanction, since redaction does not apply to images), a list of external links, and a label the owner chooses (team, organization, league, personal — defaulted from the structure, no effect on permissions, shown with "owns N teams" beside it where N > 0; a solo first Community that adds a Squad reads "Taro's team Alpha", and the UI says to rename or create a child for a brand name); sponsors are text and links in these, with no model of their own. The Player page (`/p/:id`) lists the person's Squads by default — one switch hides both the Player page and the Squad listings, leaving the name without a link on team pages — and shows the Communities the person runs only when the person turns that on (off by default). The page has a Visibility of its own: unlisted by default, private (members only), or public, with the directory. Team-name impersonation gets no reservation and no verified badge (ADR 0027: the operator decides what is allowed, never who someone is; handles stay deferred): the structural tell is that a Squad-linked team in a bracket links to its Community page while an ad-hoc team links nowhere, and an impostor Community shows an empty history and no followers; reports and the operator's redaction handle the rest. The operator suspends a Community as it suspends a person (Abuse prevention).

**Follows (ADR 0028, amending ADR 0014).** Following a Community is the first explicit Follow: a subscription row the subscription function consumes, so the Community appears in the follower's home list and its public activity reaches them — exactly what its page would show that follower if opened now — in four fixed kinds: an Entry confirmed on an Event whose Visibility is public, a tournament completed with the team's placement (a public tournament, `canDiscover` — the page lists no other), a Squad member joined or left, and a move in a public Ranking's standings. Three of the four deliver only once an Event, tournament, or Ranking can be `public`, which Visibility reserves until a directory exists, so until then a Follow delivers Squad changes alone. Per-match results are never delivered (email would become spam and producer-side fan-out unbounded), nor registrations on unlisted Events (that would hand out their links). Following requires an email account (an anonymous identity has no address and is reaped), is allowed only on a page the follower can view and re-checked at delivery (ADR 0014's dynamic audiences), is in-app always and by email only where the follower turns it on per Follow, and ends with the Community's deletion or the follower's account deletion. Members need no Follow — the relation already subscribes them, and the function deduplicates. The follower count is public; an account holds at most 500 Follows. Announcements from a Community to its followers are not built; the owner decides whether they ever are.

**Invitations** are Grants with the action "join this Community": role fixed at issuance (organizer or admin; an owner-to-be is not offered — ownership transfers to an existing member), use limit, window (seven days by default), revocation; the owner copies the link into Discord or a DM, and whoever opens it signed in joins at once (an existing member sees that they already belong). Nothing is emailed to a typed address (ADR 0018).

**Hand-overs.** An Event or standalone tournament moves to another Community through a Grant with the action "take over this Event", issued by the owner or an admin of the current Community — a two-phase operation whose preview lists what is below — and accepted by the owner or an admin of the receiving Community, who chooses which of their Communities takes it (a person who holds one of those roles on both sides issues and accepts in one step); it is single-use, lasts seven days, and is revocable. Allowed in every state but suspended or being deleted. The commit writes the new owning Community and records the hand-over as an Activity with an everyone-who-can-view audience; the rest follows in bounded pages behind that write, as a cancellation's notices do: Registrants of an Event not yet over receive a person-addressed notice that the Event is now run by the receiving Community (an Event already over gets the list Activity only), and the Discord webhook is deleted — its URL belongs to the old Community's server. Participant codes change with the root Community automatically, since they are derived (ADR 0028), so nothing is paged for them; the receiving Community's list shows the Entrants under its own tree's codes. Track-scope sanctions, Grants, Announcements, Activities, results, and the slug stay with the Event; the preview counts the unended Grants the old Community issued (the new one may revoke them), the active Entries with an Entrant — or a Squad's Community — that the receiving Community or its ancestors ban (those bans apply to new registrations at once and to existing Entries only by its own removal), and the webhook. Members of the old Community lose the Event's organizer views on commit; their stored previews fail at commit; the person-addressed notices already in their inboxes stay.

**Deleting a Community** is its owner's — or, for a child, the parent's owner's or admin's (ADR 0028) —, two-phase, and refused while a published Event of it is not over, any Event of it is suspended (cancel or hand over first), or it has child Communities (move or release them first, ADR 0028); the account deletion of a root's sole member is the one path that cannot be refused and keeps the cascade of ADR 0022, detaching the children as roots (a child's ownership passes upward instead). The preview lists drafts and resultless standalone tournaments (deleted), Events and tournaments kept under the frozen name, members (told; memberships deleted), Squads (ended; their memberships kept as left rows, as after a member's deletion), their Entries in Events not over (kept with their name and Entrants, the Squad link inert, so each takes a captain by ADR 0029's succession rule, its Entrants told), affiliations and Follows (ended), unended Grants (revoked), webhooks (deleted), sanction rows and dormant rows (deleted). The row stays as a deleted marker with the name. No undo (ADR 0011). The last member leaving follows the same rules — which is why the sole owner's exit is the deletion itself. A Community's name is not unique and is not reserved (ADR 0028); handles stay deferred, and the Community page is ADR 0028's (above).

### Abuse prevention (ADR 0027)

Decided in the anti-spam grilling of 2026-10-14/15; limits sit where something reaches other people, and the operator decides what is allowed, never who someone is.

- **Robot check.** Cloudflare Turnstile guards registering without an email (claim links included) and sending a sign-in code, verified inside the sign-in action; an anonymous identity is minted only there, never on page load, so Spectators have none. No per-IP limits.
- **Limits.** Per account: 10 owned Communities, 100 Events and standalone tournaments created and 60 published per day (together), 10 reports per day; per Community 20 Rankings; per Season 1,000 counted tournaments; per Revision the top 5,000 Players; per Event 100 Announcements a day, at most 3 of them also by email (the Organizer ticks "also by email" and sees what remains); per anonymous identity 100 Entry and Entrant rows together. From ADR 0028 and 0029: per Community 20 Squads, 100 players per Squad, 10 child Communities (so a tree holds at most 111 nodes and every subtree enumeration stays bounded), 50 affiliations; a team name — a Squad's, and an Entry's — is at most 40 characters (a default built from the Community's name is cut to fit) and a Squad label 20; per account 500 Follows (owned Communities keep the 10, counted over the nodes a person owns) and 50 team invitations a day; one unended join link per Entry; 32 Entrant rows per Entry. The operator raises one account's limits on request. The per-Event caps under Performance are size limits and stay.
- **Content and reports.** No pre-moderation. Every page with user-written content (Event, Community, Ranking with its reason text, Announcement, names) has a report button for email accounts; a report has a type (phishing, harassment, other), reaches the operator's queue only, counts once per reporter and subject, is never shown to the reported side, and keeps nothing after the reported person's deletion. Every page is `noindex` while not `canDiscover` (ADR 0019), and links in user content carry `rel="nofollow ugc noopener"`. The Community logo is the first user-uploaded image (ADR 0028): image types only, at most 512 KB, hidden while a report on it is under review, and removed as the sanction, since redaction does not apply to images.
- **Suspending a Community** (ADR 0028), as the operator suspends a person: the page shows the reason only, its Squads cannot be entered and no Entry is created for them — its existing Entries keep their name and Entrants, their Squad link inert while the suspension lasts (and after the Community's deletion), so each takes a captain by the succession rule and only one with no account or anonymous Entrant falls under the "Entry nobody can act for" rule (Entries) —, its Rankings are not published, Follow deliveries stop, and its Events are suspended with it; children are not suspended with their parent. Lifting restores all of it.
- **Suspending a person.** The person signs in to the reason, a route to the operator, their own data, and deletion only; every Event of a Community whose sole member they are is suspended with them, a Community with other members carries on without them, their Entries elsewhere are left to those Organizers, and a deletion leaves the suspension dormant under the email tag (Account sign-in and deletion, above). Lifting restores what it suspended.
- **Suspending an Event** (ADR 0019's gate): its pages, Share Links, Grants, registration, Announcements, deliveries, and webhook stop; the Organizer views but cannot edit, delete, or hand it over; Rankings skip its tournaments. Nothing is deleted, and lifting restores everything.
- **Redaction.** The operator replaces a name the person cannot edit, through the `players` row, with a pseudonym fixed per Player ("Player K7Q2") in every record, and redacted text with "hidden by the operator"; the Organizers concerned are told.
- **Lost mailboxes and absent owners.** No account is recovered on proof of identity. Absent-owner succession: a designated successor — who must be a member; the designation lapses when they leave — may request ownership at any time; a member without a designation may request it after 30 days in which the owner did nothing in a session (a session that merely stays signed in is not activity); when a root Community has no member other than its absent owner and no designated successor, a child's owner is the last candidate. Every request is a 14-day notice: the owner's address is told and ownership moves after 14 days unless the owner signs in and cancels. Several requests are served first-come, the others seeing theirs pending. An owner suspended by the operator counts as absent from the first day and cannot cancel. There is no re-application ban — a hostile successor is un-designated by the owner — and an organizer's work (running Events, recording results) continues meanwhile. A childless root Community whose sole member lost their mailbox is not recoverable (a root with children passes to a child's owner under the absence rule; a child's parent names its new owner — ADR 0028).
- **Reaping.** An anonymous identity records its last use when its session refreshes and is reaped thirty days after it, when its session has expired.
- **Operator tooling** is internal functions and a minimal operator page, outside the operations API.

### Entries (ADR 0013, 0016, 0029)

An Entry is the unit that takes a seat on a Track, and an Entrant is a person on it; a one-player Track is an Entry with exactly one Entrant, so the code has one path (ADR 0029). Self-made Entrants carry an identity; Entrants entered by name carry none until claimed. A person is an active playing Entrant on at most one Entry per Track, forming Entries included — checked by every act that activates a person (opening a join link, accepting an invitation, a request accepted, claiming, turning `playing` on, the Organizer's lineup change), and "leave A and join B" is offered as one step (claiming while active on a self-made Entry offers to leave it first); registering again after an Entry ended creates a new Entry, at the back. An Entry needs someone who can act for it: an ad-hoc Entry has exactly one captain while any Entrant with an identity is active — a playing Entrant; the flag passes to the longest-standing active account Entrant, else to an anonymous one on an anonymous-allowed Track — and a Squad-linked Entry has no captain while its Squad link is live, its Squad's staff acting for it (ADR 0028's capability) and the suspension rule giving it one once the link is inert; an Entry nobody can act for ends while it is waiting and stays while confirmed, the Organizer told. An Entry that has taken a seat and whose last active playing Entrant leaves ends as cancelled (a forming Entry ends as cancelled when its last Entrant leaves or is moved out by "make teams" — the moved Entrants are `left` with a pointer to their new Entry — and cannot be listed as recruiting while it has no playing Entrant) (on a one-player Track "leave" is "cancel"); when the Organizer removes the last one, the preview asks whether to remove the team. The Organizer may add, rename, and remove any Entry or Entrant, including an Entry with themselves as captain; Organizer entries — pasted as one team per line, the first name the captain's row — skip the window, the Track setting, Capacity, the registration requirement, the minimum, others' sanctions, and a live or completed tournament (a walk-in during play takes a withdrawn Participant's slot by substitution, or stays confirmed and not in the bracket), but are subject to the Event being cancelled (except on a Track whose tournament has been published and not deleted), suspended, or tombstoned, the Roster limit, the maximum, and — for every Entrant with an identity, the Organizer's own row included; a typed name has no person to check — one active playing Entrant per Track; the Organizer adds people by name or from the recruiting list, never by code. A claim is the claim Grant scoped to an Entry — "which one are you?" — and claiming a captain's row grants the captain's powers. Only the Organizer can undo a wrong claim — refused with the reason, like restoration, once the Event's lifecycle would no longer allow a claim: a two-phase reset at the Entrant that ends the wrong claimer's row (optionally sanctioning the person), re-enters it by name in the same place — named with the name the Organizer last gave it, so nothing the wrong claimer set carries over (its Participant's label follows) — with a fresh claim link; for a captain's row it also restores the team name, revokes the join links issued since, and lists the removals since; the Entry, its seat, and its Participant stay where they are, on a one-player Track too. A claim tells the Organizer, and an Entrant the Organizer entered stays exempt from the Track's registration requirement after it is claimed. An Entrant carries a display name only (trimmed, at most 120 characters, duplicates allowed), which by default follows the account name — each user carries a display name, pre-filled from their first registration, so nobody types it per Track — unless the person sets a name for that Track (a sponsor tag, say) or the Organizer renames it; a typed-name Entrant carries the name entered for it. An Entry's team name is at most 40 characters — the Squad's display name by default for a Squad-linked Entry (ADR 0028: the Community's name, plus the Squad's own where the Community has more than one), the Entrants' names joined for an ad-hoc one — and the Organizer's rename locks the Entry, as it locks a person's name — a captain or the staff may rename the team once every seven days, as an account is renamed, and the Organizer's lock is on the Entry and survives a captain-flag hand-over; person names are unchanged by teams. Contact data lives on the user as verified channels. Renaming the account asks whether the new name applies to future registrations only or to every Entrant row, past ones included; either way a name the person set for its Track, or the Organizer renamed, stays. An account rename is allowed once every seven days (plus one correction within an hour of a rename), and each rename records the previous name, which the Organizer sees in their participant list, so renaming never hides a person from an Organizer. Registration warns that an anonymous Entrant is tied to this browser, and the Organizer sees likely duplicates.

Entries are never deleted individually, and Entrant rows that are records never are. The captain or the staff cancels the Entry (asked to confirm first when it is in a bracket that has been published) and an Entrant leaves; the Organizer removes either; an Offer that is declined or expires lapses the Entry. One sanction row replaces the per-Track block and the Community ban (ADR 0029): a target (a person, with the Entrant row it was made from when one exists, or, at Community scope only, a Community), a scope (a Track, or a Community and so its descendants), the Track or Community, and an instant, so the gate is one lookup per scope kind. The Organizer may sanction the person behind any Entrant row that had an identity — two-phase, since it ends their view: a Track-scope sanction ends the person's active and invited rows on that Track as `removed` and their view through its Grants (the team may become short-handed; the person is told only that they were removed from the team), and a Community-scope one — a ban, set by the Community's owner or admin (ADR 0023's table) — bars them from all of the Community's Events, present and future, and its descendants' (Communities and roles); either is stored per person and scope and never shown to anyone else. A sanction can be lifted — a Track-scope one by any Organizer of the Event, a ban by the banning Community's owner or admin: lifting sets the ended instant on the row, which is kept, reinstates nothing (ended Entrant rows stay ended, and a captain flag that moved does not pass back), and is told to nobody. The sanction list shows the Entrant's name and the derived code, never a user id. A typed-name Entrant has no person and so cannot be sanctioned, only removed; the removal preview offers a sanction on each Entrant with an identity (an account or an anonymous one) and says so, and says that a Community ban on a team is evaded by the same people entering ad hoc — the person ban is what follows people. Sanctions are never disclosed to third parties: the person is told the true reason when they act themselves (joining, accepting) and the captain and staff are told nothing, while a captain or staff adding someone — or pressing register for an Entry that holds such a person — is told only "X cannot be included" — the one wording for a ban, a sanction, suspension, "already active on this Track", and "already on another Squad's Entry here" (an Entry in the same tree may be named), checked once when the addition is submitted, never while names are typed, and chooses to go on without X or to stop, while X is told the true reason privately; a Community ban on the team itself is said plainly, since the staff are the party. Sanctioned people receive only notices about their own status on that Track. Ended Entries are visible to the Organizer only. If an ended Entry's Participant row exists — on a pinned Roster, or still recorded in the last publication — the Participant is withdrawn and the Organizer is told at once (judged on the state at the end of the transaction, so a re-point never raises a false alarm). An Organizer's rename made while a person is on the Entrant row locks the name for that person on that Track: they cannot rename it back, and a new Entrant row they make there inherits it. List Activities about ended Entries are shown to the Organizer only. Entries of a cancelled Event are kept.

### Teams: forming, registering, lineups (ADR 0028, 0029)

**Forming, then registering.** An Entry starts `forming`: no seat, any number of Entrants, outside the seat equation, the Grant use counts, the Roster limit, the Waitlist, and the registration window (a forming Entry may be created and filled before the Track opens; the window gates registering, not forming). The Track declares the number of playing Entrants an Entry needs — a minimum and an optional maximum, the platform cap being 32 Entrant rows per Entry; a one-player Track is 1/1 and shows none of this. Lowering either bound is always allowed and registers nothing by itself (a forming Entry that reaches the minimum because it was lowered is told "you can register" under the same rule — only while registration is open); raising either is two-phase, and the preview of any Track-setting change lists the forming Entries it affects. There is no mixed Track: a Track is for Entries of one size range, and a person who wants to play alone on a team Track is an Entry of one, forming until it finds teammates. The maximum bounds playing Entrants; non-playing Entrants (coach, manager) exist only on Squad-linked Entries and count against the row cap alone. Registering is always an explicit act of the captain or the staff — the Community's members acting for its Squads and Squad-linked Entries, whatever their role (ADR 0023's `staff` role included) —, allowed only once the Entry has at least the minimum of playing Entrants; it runs the decision function once (confirmed, waitlisted, refused with the reason — a refused registration leaves the Entry forming, to register again once the reason is gone), is idempotent, and the first team to press "register" takes the last seat. When the count reaches the minimum while registration is open — or registration opens while the count is at the minimum or above — the captain — the staff, on a Squad-linked Entry — is told "you can register" and the other Entrants see "waiting for the captain to register" ("waiting for the staff to register" on a Squad-linked Entry), and the captain's acceptance of a request that reaches it while registration is open offers "accept and register" in one tap (an invitee's acceptance registers nothing; before the opening the Entry shows the opening time instead). Entries still forming when the tournament goes live (or the Event ends, on a Track whose tournament never went live or that has none) end as lapsed, "no team formed". A Track may list its forming Entries as recruiting — an Organizer switch, off where the maximum is 1: the list shows each recruiting Entry's team name, its Entrants' display names (nothing else: no code, no reachability) and its count against the minimum to the Organizer and to viewers who hold an active Entry on that Track (anyone else sees only how many Entries are recruiting), never on the registrant list; a captain or the staff lists their Entry, and listing it is consent to be placed on a team by the Organizer and to appear on that list, both of which the listing screen says; it is "looking for group" without a second mechanism. The Organizer's "make teams from the recruiting list" moves whole Entries, names them Team 1…N, and makes the longest-standing account playing Entrant captain, else the first row.

**Short-handed.** An Entry that took a seat and then fell below the minimum is "short-handed" in the UI — a fact about a seated Entry, not a state. The format engine has one predicate, _absent_ — the Entry has ended or its playing Entrants are below the minimum — with the derived walkover behind it (Track tournaments, below): nothing is recorded until a result depending on it is, the opponent is not told automatically (counts move), the pending match is not shown as a walkover while it is only derived — once a dependent result records it, the walkover is labelled "short-handed", and the UI word for _absent_ is "short-handed, cannot play" —, the Organizer is warned and the captain (the staff, for a Squad-linked Entry) is told that the Entry is short-handed, and an automatic publication includes short-handed Entries and lists them in its preview, and publishing by hand warns about them. A swap is one act — A out, B in — so no instant of short-handedness is created when B's consent already exists; otherwise it is a removal and an invitation with a short-handed interval between.

**Consent.** A person becomes `active` only by their own act — opening a join link, accepting an invitation, having their request accepted, claiming a typed name — or, for a Squad member, by the standing consent given on joining the Squad (Communities and roles); a Squad larger than the Track's maximum gets a "choose up to N" step, and "last time's team" the same. A person who left an Entry returns to it only by their own acceptance; leaving the Squad ends the standing consent. Promotion of an ad-hoc team into a Squad is an invitation to each account Entrant — a single-use "join this Squad" Grant delivered as a notice, each counting against the sender's 50 team invitations a day — never an automatic add. A Squad-linked Entry's Entrants come from the Squad; staff may add nobody else — the Organizer may. The registration requirement ladder (Identity) applies to every Entrant; under _anonymous allowed_ a captain may type a teammate's name with a claim link, so a four-player team is not stranded at three on the day; under _account required_ a typed name comes only from the Organizer.

**The join link** is a register Grant scoped to one Entry — the scope ladder is Event > Track > Entry — issued by the captain (an account, or an anonymous captain on an anonymous-allowed Track — narrower than a public QR code) — a Squad-linked Entry has none, since its Entrants come from its Squad and a guest joins the Squad first: one unended per Entry (re-issuing replaces), link-only — it is never given a code — and outside the Event's register-Grant cap (Event-wide Grant operations are paged); it stores no end and ends with the Entry or the swap deadline; it admits a person through the activation function — the per-person gates, the maximum, the deadline — not the registration decision, so it works on a Track whose tournament is live; it admits while playing Entrants are below the maximum; a removal does not free its use (re-issue to admit another); it appears in the Organizer's Grant list and can be revoked there, and the captain who issued it may revoke it outright; and it cannot be issued on an invite-only or hidden Track or in a private Event, where the Organizer's claim link, the Squad's standing consent, and invitations to recruiting Entries remain. **Invitations and requests** are Entrant rows — `invited`, or `requested` when the person created it: the same row from the other side, which the captain accepts or declines one at a time (a Squad-linked Entry takes no requests: its Entrants come from its Squad). Invitations go to a closed set (Entrants of recruiting Entries on that Track, last time's Entrants) and are sent by a captain, never for a Squad-linked Entry, whose Entrants come from its Squad, carry fixed wording with the Event's and Track's names (the team name on opening, with a report button), need an account to send (pushing a notice at someone is an account's act), and none at the recipient, who is reached in-app as an existing Entrant (by email where they have one), count 50 a day per account, are capped at the maximum while pending (counted apart from active rows), and are withdrawn — pending requests too — when the Entry reaches its maximum; an invitation gives view of the Entry and Track as a Grant does. A person has at most one unended Entrant row per Entry, and a `declined` row blocks only re-invitation from that Entry.

**The swap deadline** is the Organizer's, with three settings and no new instant: lock at the bracket's publication; lock at this team's first match result, a recorded walkover included (the default); never lock — under which, once the Track has its first result, a person who was on any Entry of the Track cannot join another (the ringer rule; the Organizer may override it), and any lineup change after the Track's first result is notified to the Organizer and recorded on the bracket's activity. Entrants may always leave; the Organizer may always change a lineup — "the Organizer's lineup change", distinct from Substitution, which re-points a Participant to another Entry, the way a no-show team is replaced by the next waiting one. After the deadline the Organizer adds people by typed name or from the recruiting list only. **"Last time's team"** is offered to the previous captain or staff: Squad-linked → active rows for those still on the Squad; ad-hoc → invitations; typed names listed for re-entry; the new Entry carries a pointer to the one it continues, which Rankings read as a tie-breaker only (ADR 0030).

**Lineups.** The playing lineup of a completed tournament is part of its published result (owner decision, 2026-10-15): who played is a public fact of a public tournament, as the name in a one-player bracket is. A match's lineup is the active playing Entrants of each side at the instant its result is recorded, and a team's placement is credited to every person who was on the lineup of at least one of its matches — not "active at completion", which would drop a semi-finalist who left before the final; a bench player who never played still shares the placement, a known imprecision that per-match lineups, if ever recorded, refine without changing the definition; the Organizer's maximum is the cap on it. The Participant stores those Players as `creditedPlayerIds` when the tournament completes; a credited typed-name Entrant claimed afterwards adds its Player id to the set; Rankings and Player pages read the set (ADR 0030). Registration says so ("your name is visible to everyone who can see this tournament's results, and your teammates and anyone holding this team's join link see it before the Event"), and a Player's lever is hiding their Player page, which leaves the name in the result without a link, as everywhere; the registrant-list audience governs the view before and during the Event only (Visibility).

**Visibility and notices.** The bracket shows team names only; the registrant list shows the team and its active Entrants; forming Entries' Entrants are in the Registrants audience, not the confirmed one; Waitlist names stay hidden; an Entry linked to a Squad of the owning Community, of one of its ancestors, or of one of its descendants (never of a sibling branch) is marked "the host's team" on the bracket and the registrant list (ADR 0028). Notices for an Entry reach the captain and the account Entrants — the staff folded per Entry per day — paged by Entrant count; an Entrant's own changes reach the person and the captain. A team's placement appears on each credited Entrant's Player page "as a member of <team>". Account deletion ends the person's unended Entrant rows in Events not over as `left` (the Entry cancelled only if they were its last playing Entrant) and leaves their rows in Events over without identity (Account sign-in and deletion); reaping instead strips the identity from its unended rows, which stay as typed-name rows, and cancels no Entry; a suspension moves the captain flag to the longest-standing active account playing Entrant, and the flag does not pass back when the suspension is lifted; a merge ends the duplicate row where one person held two on a Track, the other team told. Restoration (Track tournaments) re-enters the Entrants as typed-name copies with the Entry's claim link. The captain's and the staff's view of the lineup shows each Entrant's name, state, and whether the person is reachable — never the participant code or an address; the Organizer's list shows name, code, and reachability. Short-handed Entries and "no team formed" are the only new outcome wording; "withdrawn" keeps its meaning. The operator's redaction (Abuse prevention) covers team names.

### Capacity, Waitlist, Offers (ADR 0015)

Capacity is per Track; unset means unlimited. A seat is per Entry, whatever its Entrant count, and a forming Entry holds none (ADR 0029). A confirmed Entry keeps its place until it ends; Capacity cannot be lowered below confirmed Entries plus outstanding Offers plus unused reserved seats. Public free seats are Capacity minus those three. On a Track with a tournament, no path — over-Capacity confirmation and Grant arrivals included — confirms beyond the Roster limit (128), and an Organizer's confirmation beyond Capacity counts outstanding Offers and unused reserved seats against it too, so it never takes a place someone already holds a claim to. Changing a Track's Offer hold time applies to Offers issued afterwards, and its registration requirement to registrations afterwards; existing Entries keep their state. A pasted list of names (story 16; one team per line on a team Track) is a batch of Organizer entries, at most 500 rows — Entries plus Entrants — per mutation (the client sends a longer list in chunks): on a Track with a tournament it enters names up to the Roster limit as counted for Organizer entries (outstanding Offers and unused reserved seats included) and refuses the rest, listed; two fixed seeds on one position are refused.

Only an Entry with a reachable captain or staff joins the Waitlist (an Entry whose Squad link is live always has one; an anonymous captain, or one without a channel, takes a free seat or is told to add an email or pass the captain flag to a reachable teammate — the captain hands the flag to any active account Entrant, and a suspension moves it to the longest-standing one); Entries with nobody reachable behind them never wait (ADR 0015, 0029). While the Track accepts registrations, a freed seat goes to the next waitlisted person: by default, and as the joining screen says, they are confirmed at once and told (a one-tap cancel follows the notice); a person who chose to be asked first receives an Offer instead, held for the Track's hold time (an Organizer setting per Track — 1, 6, 24, or 48 hours, 24 by default). An Offer can be taken — accepted with the captain's or the staff's session, who alone may also decline it (a non-captain Entrant may only leave), or at once if the captain or the staff switch to automatic acceptance — while its deadline has not passed, it has not been returned, its Entry has not been removed (a withdrawing Grant's derived removals included), and its Track is accepting registrations now, the one predicate settle issues Offers under, checked with the server clock; the entry gates (the Track setting, the Grant the Entry came through, one active playing Entrant) were passed on joining the Waitlist and are not asked again, with one exception — the minimum: a waiting Entry whose playing Entrants have fallen below it (an Entrant left, or a Track-scope sanction ended their row) keeps its place but is passed over when a seat frees, and an Offer it holds can be taken only once it is back at the minimum (its join link works meanwhile); its captain is told "below the minimum; add a player to keep your place" (ADR 0029); crossing the minimum in either direction is a seat input that schedules settle (below), so a team that restocks while a seat is already free is confirmed at once, and the close-time fill passes such an Entry over the same way, while the Organizer's by-hand confirmation may still seat it, warned as short-handed. A Track-scope sanction ends the person's rows, not the Entry. Declining offers the seat onward at once and lets the person either leave or queue again at the back (a new Entry, subject to the registration gates then); expiry lapses the Entry and sends a one-tap invitation to queue again at the back. An Offer ends in one of two ways only: it lapses when its deadline passes while it could be taken, and otherwise it returns to the Waitlist with its place kept — whenever its Track stops accepting first, for any reason — and the captain or staff are told; when both could apply, the return wins, so no timing turns a return into a lapse. Returns are derived from stored state, processed or not, and never depend on the operation that caused them: an Offer counts as returned when its deadline falls after an effective close that has passed, when its Track's tournament is live or completed (states that never revert), or when its Event's stop count has risen since it was offered — a count, not an instant, because settle reads the Event it issues under, so any suspension or cancellation that commits after an Offer's settle raises the count that Offer recorded, whatever the functions' clocks said. Settle then writes the Entry back to the Waitlist and sends the notice (for a cancellation, the cancellation notice covers it). Two single-Track operations write returns themselves, bounded by the Offer cap: the attach clamp, which returns only the Offers beyond it, and any operation that moves a passed effective close later — reopening, moving a passed Track start later while the publish time is derived from it, or disarming by hand or by deleting or detaching a tournament whose automatic publication is armed or failed — which first writes the returns that close implied, so an Offer once cut off never becomes outstanding again (a cancellation's own disarming needs none: its stop count already returns every Offer). An opening that has passed is never moved; closing is how registration stops. Whenever anyone waits, public free seats are zero — a freed seat reaches the public only through an empty Waitlist, and holders of Grants that do not reserve join the Waitlist too; after the close the Organizer confirms waitlisted people by hand, and they are told. When the tournament goes live, or the Event ends, the people still waiting are told they did not get a place and, at go-live, confirmed people left out of the bracket that they are not in it; their Entries stay as they are (the Organizer can still confirm a waiting one by hand). Any operation that creates or confirms an Entry after such a moment tells its person itself and records it. Settle first writes the pending returns, then pages the notices, recording on each Entry the notice it received, so none is repeated or skipped whatever the order and a tournament going live after the Event's end still tells the people left out of its bracket; when nothing remains to tell for a moment, it tells the Organizer once, recorded per moment on the Track's schedule document. An Offer past its deadline counts as lapsed for every gate, processed or not, unless it counts as returned. A single-Track Grant with a use limit, on a capped Track, may reserve its seats — a flag, not a count — so its holders never wait: its unused reserved seats are its remaining uses (never below zero), and none once it has ended for good (revoked, its window over, or its Event cancelled or over; a draft or suspended Event, or a window not yet open, keeps them counted). A self-cancellation frees a use and so the seat; a removal does not, and its seat goes to the Waitlist. Invitees beyond its use limit take a second link that does not reserve and queue like anyone else. So public free seats are Capacity minus confirmed Entries, outstanding Offers, and unused reserved seats, each seat counted once. Confirmation instants and waitlist positions are stored explicitly. Waitlist positions are sortable keys, suffixed with the Entry's id so no two tie, and a move reads the gap it lands in by index range, so it writes only the moved Entry and concurrent moves into one gap conflict. The Organizer may move one waiting Entry to another position — always two-phase, since any move changes someone's place (its digest covers the moved Entry and its new position, not the Entries it passes) — and only the moved person is told, everyone else seeing their current position in their status; an outstanding Offer is unaffected (the order decides only who is offered next, and a returned Offer rejoins at its Entry's current position). Automatic acceptance — the default — is performed by settle, which confirms such a person directly in the transaction that would otherwise issue their Offer; switching to it while holding an Offer accepts that Offer.

**Settle function.** One settle function per Track keeps the seat machinery converged, and it always runs as its own scheduled internal mutation, never inside another operation: scheduled by the cron over due instants, or immediately by a mutation that lowers a due instant, as follows. Every mutation that writes something settle reads, other than a registration consuming a free seat — a seat input (cancelling, removing, sanctioning, reordering the Waitlist, accepting or declining an Offer, a waiting Entry's playing Entrants crossing the minimum (an Entrant activated, left, removed, or sanctioned), Capacity, a Grant's issue, window, use limit, or revocation), an instant (a window, a Track's start, the Event's times), automatic publication (arming, re-arming, disarming), the tournament (attaching, detaching, deleting, publishing, unpublishing, going live), or the Event's lifecycle (publishing, returning to draft, cancelling, suspending, lifting) — lowers the stored next due instant of each Track it affects to now when it is later or absent (no due instant counts as later than any) (an Event-wide change: every Track of the Event, which the per-Event Track cap bounds), and only when that write changed it also schedules the settle immediately (`runAfter(0)`, which runs only if the mutation commits). The schedule document is therefore the only pending marker: a burst of changes schedules one settle, and a settle that fails is retried by the cron like any other due instant. A mutation decides only what it must itself — a registration's seat check — and every gate and the seat equation read the clock directly (the seat document plus its time corrections): an Offer is outstanding while its deadline is in the future and nothing has returned it (see the Offer rules above), and an Event is over once its end has passed. So nothing needs catching up before a decision, and no operation — cancel, remove, sanction, revoke, close, suspend — ever depends on settle succeeding. Under an Event's or a Track's deletion tombstone every mutation on it other than the deletion's own batches (and settle deleting its schedule document) is refused — internal ones, such as delivery writers, do nothing rather than throw, so the deletion's own batches write its deletion notices — and those batches never lower or create its schedule documents, so nothing is due there (a tournament's own tombstone, below, affects only the tournament). Settle issues Offers, lapses those whose deadline passed while they could be taken, sends the notices for returns read from the clock or stored state, records the resulting Activities ("not in the bracket" at go-live, "did not get a place" at go-live or the Event's end), performs an armed automatic publication when it is due, and stores the Track's next due instant (an Offer deadline, the effective opening and close, a Grant window's end, the Event's end, the effective publish time) — writing it only when it changes. The cron runs every few tens of seconds, reading only schedule documents that have a due instant (a range bounded below, since Convex orders a missing value before every number) and are due a few seconds before now — a due instant just lowered to now already has its own immediate settle, and reading up to now would make the cron conflict with every such write — and is specified by the properties it must keep, pinned by tests: every due instant of a healthy Track is processed within about one interval; one failing Track never delays another (each settle is its own scheduled mutation, and the cron never computes a next due instant itself); a failing settle is reported to the operator and retried with bounded exponential backoff that resets after a success or when the due instant changes; and per-tick work is bounded, continuing from a cursor; a settle with more work than one bounded page (Activities for a long Waitlist when the tournament goes live) writes a page and leaves its due instant at now. A Track that should not be processed simply has no due instant: settle stores none while its Event is suspended, writes nothing under a deletion tombstone but the deletion of its own schedule document (whose first transaction deletes the affected schedule documents and the cron's records for them), and never inserts a schedule document for a missing Track; lowering skips a Track under a deletion tombstone, and settle deletes the schedule document of a Track that is tombstoned or missing. Deleting a tournament alone tombstones only the tournament — its automatic publication off, its Track's settle scheduled, and the tournament excluded at once from every lookup (Participants by Entry, withdrawal alarms, Registrant status, the Roster limit, one tournament per Track, claim Grants' post-Event extension), so a new one may be attached meanwhile. While automatic publication is armed or failed, the effective close is the earlier of the Track's close and its time — derived, never written — so cron lag cannot let anyone in late and a failure keeps registration closed, as Registrants were told. Seats freed before the effective close are filled even when settle runs after it, and seats freed after it are not — the one exception to settle acting only under the predicate above: the first change at or after the effective close to the seat equation's inputs (the seat document or Capacity — a cancellation, a removal, a revocation, a confirmation through a Grant or by the Organizer) or the first settle after it, whichever commits first, records on the seat document, for that close, the seats free at it (the seat equation evaluated at that instant, Offers outstanding just before it counted as taken) before making its own change; every later confirmation that takes a free seat lowers that record, and any operation that moves a passed effective close later clears it. The first settle after the close consumes it: unless the Event was cancelled or suspended at or after the close (read from its cancellation instant and its last suspension instant, so no record or clearing of one can hide it) or the tournament is live, it walks the Waitlist in order for at most that many seats, never more than are still free — a person on automatic acceptance is confirmed with the effective close as their confirmation instant, a person who chose an Offer uses up a seat without being sent one (it would already be returned) and keeps their place, as an on-time Offer returned by the close would have left them, a person whose outstanding Offer the close returned is passed over, since that Offer's seat was counted as taken, and an Entry below the minimum is passed over, keeping its place (Teams) — and then sets the record to zero; it stays, so no later change or settle records that close again, until an operation that moves the close later clears it. An automatic publication pins only after those confirmations are written, so cron or retry lag never costs a waiting person a seat they were due before the close, and never hands out a seat that freed after it — a stale, earlier due instant still pending included. Automatic publication takes only Entries confirmed at or before its time (Grant and Organizer arrivals may come later); fixed seeds on later Entries are ignored, and those Entries become pending additions. Settle never throws on expected conditions (a deleted Track, a tournament that cannot publish); it records an Activity for the Organizer, except under a deletion tombstone, and any refusal to publish an armed automatic publication — whatever its cause — makes it failed, so no refusal repeats on later ticks. Suspending an Event writes the Event (suspension in force and its instant, stop count raised) and lowers its Tracks' due instants, and nothing else; lifting clears the flag; its outstanding Offers count as returned from then on, deliveries are held, and settle stores no due instant while it is suspended (automatic publication stays armed); `canView` shows a suspended Event to its Organizer only (its effect on a live tournament is part of the pending operator workflow). The operator can purge held deliveries before lifting; lifting first marks every armed publication whose time has come as failed, in the lift itself, then schedules the Tracks' settles and resumes deliveries — deliveries to places are re-rendered from current content (a deleted Announcement is not sent, and those for an Event already over are dropped, with a note to the Organizer), while in-app notices stay as written.

### Registration window and the decision function

Each Track stores optional opens and closes instants (UTC). Public registration is open when the effective opening ≤ now < the effective close: the opening is the later of the Track's opens and the Event's publication; the close is the Track's close (unset means the Event's end, so a plain Track keeps accepting at the door). Manual open and close write these instants; an opening that has passed is never moved. An automatic publication counts as the close while armed or failed; any publication, and re-arming from failed, writes that effective close into the Track's close, a publication also capping it at its own instant. Moving a close later is refused while the Track has a published tournament — reopening is exactly moving it later afterwards. Moving a close or an opening lists the Grants whose window ends at the old instant, warning when their holders would be stranded (invite-only or hidden Tracks, private Events); Grants never move with it. An ended Grant presented while the public window is open is ignored, and the person registers publicly. Clients display the state from the instants, the publication state, and a server-time offset; mutations decide with the server clock. When a Track's close is left at the Event's end but its tournament will publish automatically at the Track's start, the Organizer is warned that door arrivals will need invite links or the Organizer's own entries.

Whether an Entry may register or a person may claim, and with what result (confirmed, waitlisted, refused with a reason), is decided by one pure function. A forming Entry is outside it until its captain or staff registers it, at or above the minimum (Teams); admitting a person onto an Entry — a join link, an invitation, a request, a claim — is the _activation function_, a distinct pure function over the per-person gates, the maximum, and the swap deadline (a claim passes only the per-person gates, since it takes no seat), which works on a Track whose tournament is live (ADR 0029). `canView` comes first, so anyone who may not see the Track gets the same "not found" as for a missing one. For a person presenting a register Grant, the Grant's window replaces the Track's and the Grant passes its own Track's invite-only or hidden setting (an Event-scope Grant passes invite-only Tracks, never hidden ones); a full Track admits them only through a Grant that reserves its seats. Absolute gates: the Event is a draft, cancelled, over, being deleted, or suspended; the Track's tournament is live or completed; for public registration (without a Grant), the Track's tournament is published — a second guard beside the close, since a registration decides with the clock its function started at and may commit after a publication; the Track's registration requirement for every Entrant; the Waitlist's; a sanction on any Entrant at either scope, or a ban on the Entry's Squad's Community, read along the ancestor ids; one active playing Entrant per person per Track, forming Entries included; the minimum of playing Entrants; the Roster limit on a Track with a tournament. Claims take no seat: they are subject to the gates that concern the person (a sanction, one active playing Entrant, the Event's lifecycle, suspension) but not to windows, publication, or a live tournament; only Entrant rows of active Entries can be claimed.

### Track tournaments (ADR 0016)

A tournament may be attached to a Track (at most one per Track) at any time; while attached, its Discipline and Visibility follow the Track, and the Track's Capacity is capped at the Roster limit (unset behaves as the limit, waitlisting beyond it). Attaching is previewed: it clamps Capacity to the limit, returning Offers and lowering the use limits of reserving Grants beyond it (both listed); if more Entries are confirmed than the limit, the Organizer pins at once the Entries they choose, up to the limit, and the rest stay confirmed as pending changes and are told they are not in the bracket when it goes live. Tracks that need a larger bracket (majors) wait for phases or pools, outside this feature line.

- **Structure changes only in draft**: Roster membership, seeding, format, and bracket generation. Labels — including Participants' display names — change in every status. Unpublishing returns a published tournament to draft, which is possible exactly while no result exists. This applies to standalone tournaments as well.
- **Substitution** re-points a withdrawn Participant with no recorded result to another confirmed Entry, taking the new Entry's name, in draft, published, or live, as a two-phase operation; it checks results in the same transaction. **Restoration** gives a withdrawn Participant, results and all, back to its people: the Organizer re-enters its Entry in place — every Entrant as a typed-name copy, the Participant's label, the ended Entry's confirmation instant and Grant link, exempt from reachability — with the Entry's one claim link, which asks "which one are you?" — refused, with the reason in the preview, once the Event's lifecycle would no longer allow a claim — which also lands in the inbox of each original account behind one of the Entry's typed-name rows, when that Entrant had one and the person is not sanctioned (never when it was an Organizer entry someone had claimed). Re-entries by restoration are continuations, linked to the Entry they continue: exempt from Capacity and the Roster limit (the slot already exists), and a continuation chain counts as one use of its Grant. It needs no acceptance state and covers an identity-less Entry or a wrong claimer's cancel alike. Substitution and restoration are one re-point primitive: it updates the last publication's Participant→Entry record and notifies the Entrants; a reset moves no Participant (the Entry stays) but notifies the Entrants the same way; after the first publication, substitution and reset also notify the person replaced (only that they were replaced, if they are sanctioned), and the opponent when the label they see changes. A claim of an Entry whose tournament has been published (it has a last publication, even while being revised) passes the Event-lifecycle gate — even if the Event is cancelled or over — within the claim Grant's limits. By default a withdrawn Participant's unplayed matches are walkovers, derived rather than recorded: the format engine treats a match whose one side is withdrawn and has no result as the other side's walkover (ADR 0005 — progression is derived anyway), so a withdrawal before play makes nothing live and leaves unpublishing possible, and a substitution or restoration simply takes the derived walkover away. When a result is recorded that depends on a derived walkover, that walkover is recorded first, by the system, in the same transaction; from then on it is an ordinary result — substitution is refused and restoration keeps it — and correcting it follows the MVP's correction rules. A match whose both sides are withdrawn waits for the Organizer. The opponent of a derived walkover is told that their opponent withdrew and they advance. Results can still be recorded for a withdrawn Participant. Standalone tournaments have no Entries and so no withdrawals; their walkovers stay manual, as in the MVP.
- **Projection until pinned.** An unpinned draft's Roster and bracket are computed when read from the confirmed Entries, the format, the seeding order (random by a hash of the stored salt and each Entry's id, or confirmation order), and fixed seeds; changing these does not pin, removing an Entry just ends it, and reshuffling writes a new salt. The Roster pins into stored Participants on an explicit "pin" or at publication. The action carries every projection input the Organizer saw, refuses if anything but new arrivals changed, pins exactly the Entries shown, drops any that ended meanwhile (saying so), and leaves later arrivals pending. Registrations never write tournament documents, and a Track tournament has no Participant without an Entry.
- **Pending changes** of a pinned Roster are derived: confirmed Entries not on the Roster and withdrawn Participants; they apply in draft. Names are not pending changes: any change to an Entry's team name — a captain's, the Entrants' default names changing, or the Organizer's — writes its Participant's label in the same transaction, in every status, so a published bracket shows it at once; the Organizer's rename locks it, the rename limit stops churn, and the Organizer can correct any name at any time (owner decision, 2026-09-30, replacing approval of Entrants' renames). Applied additions take the next seeds within the Roster limit. In draft, the Organizer may take a Participant off a pinned Roster while keeping its Entry confirmed (it becomes a pending addition, an alternate), or swap a pinned and an unpinned Entry, keeping the seed; after a publication both are previewed operations, and the republish diff tells the person displaced. Organizer renames update both the Participant and its Entry. Every Entry id a client names — shown, fixed, substituted, or applied — must be an active confirmed Entry of that Track not already on the Roster; fixed seeds on ended Entries are dropped.
- **Publication** records the last publication (overwriting the previous one after diffing against it), closes the Track's public registration (writing the effective close, capped at the publication instant, into the Track's close; unpublishing does not reopen it), returns outstanding Offers to the Waitlist, and notifies exactly the Participants whose first match or Entry changed (the first publication diffs against nothing, and its preview lists withdrawn Participants whose names become visible). While unpublished after having been published, the Share Link by default shows only that the bracket is being updated and is temporarily not shown — to spectators, players, MCP, APIs, and unfurls alike, the Organizer alone seeing it; the Organizer may instead keep showing the last publication, with names from the current Participant rows (a removed one shows a neutral placeholder), under a "being updated" banner, and may switch between the two while in draft, each switch a two-phase operation (hiding takes away a view; showing re-exposes names). Unpublishing and hiding send no notice (the republish diff does), and notices already delivered stay. A live or completed tournament cannot be unpublished or hidden — players need it to play; a name problem there is fixed by renaming, which applies at once, or by removal. A never-published tournament is not found. Late arrivals come through invite links or the Organizer's entries as pending changes; when the tournament goes live, confirmed Entries not on the Roster are told they are not in the bracket, as is the Organizer.
- **Automatic publication** is off by default; enabling it (attaching with a publish time, setting or re-arming one) is two-phase, and refused on a cancelled Event and on a tournament that is published, live, or completed. It has three states — off, armed, failed. Its time is the Organizer's explicit time if they set one; otherwise it is derived, never stored — the earlier of the Track's close and its start — so it follows every later change to either, and closing registration by hand publishes at once. The time in force is one of the Track's due instants; when it comes, the Track's settle publishes, as follows. While armed or failed, its time counts as the Track's close.
  - **What it publishes.** Everything confirmed by its time, including changes the Organizer has not applied: an unpinned Roster pins the Entries confirmed at or before the time; on a pinned Roster, Entries confirmed at or before the time and not on it take, in confirmation order, the seeds of withdrawn Participants first and then the next seeds, within the Roster limit, and withdrawn Participants left over are taken off the Roster, the seeds below them closing up (fixed seeds stay where the Organizer put them). So nobody who withdrew before publication appears in the bracket, by name or as a walkover, and nobody confirmed before the close waits as a pending change nobody decided on. Arming says so in its preview, and pinning while armed warns that the pin does not stop it; an Organizer who wants exactly their pinned Roster disarms and publishes by hand. Entries confirmed after the time stay pending changes, and a withdrawal after publication follows the usual rules (a derived walkover, of which the Organizer is told).
  - **Failure.** If fewer than two Participants would be published (counted after the step above, withdrawn ones excluded), the Event is not published, it is suspended, or publication is refused for any other reason, it pins and publishes nothing, becomes failed — storing the time that was in force when it failed (never the commit), which is never due again and keeps counting as the close, so registration stays closed as Registrants were told — and tells the Organizer once, with the reason. Registrants are not told: their status reads "confirmed, bracket not yet published".
  - **Ways out**: disarm (the Track's own close applies again), re-arm with a new, future time (which writes the failed time into the Track's close as the earlier of the two, unless the Organizer also chooses, in the same preview, to reopen), or any publication (which turns it off). While failed, moving the Track's close later does not reopen; disarming does.
  - **Warnings**: arming while the Event is a draft; an explicit time after the Track's start, whether set so or left so by moving the start; and, as "publishing now", arming with a derived time already past and any change that brings the time in force to now — closing registration by hand or moving the start to now while the time is derived, or a reschedule setting an explicit time to the commit.
- Registrant status is derived against the last publication, never the draft.
- Detaching (deleting an attached tournament) is allowed while no result exists; its Entries remain, and a newly attached tournament starts unpublished. Attaching an existing standalone tournament is out of scope.

### Event lifecycle (ADR 0017)

Draft (Organizer only; no registration; no published tournaments) → published → cancelled (irreversible). An Event returns to draft only while nobody relies on it (no active Entry that has taken a seat — forming Entries do not count — and no withdrawn Participant in a bracket) and it has no published tournament. Cancelling closes registration, returns Offers to a frozen Waitlist, disarms automatic publication, and notifies Registrants that the Event is off while any tournaments may continue; the page and Entries stay, and tournaments keep their Share Links with a cancelled banner and may still record results, be unpublished and republished, and take Organizer entries, hand confirmations of waitlisted people, and substitutions; attaching a tournament, or publishing one for the first time, is refused once the Event is cancelled. A published Event that someone relies on is deleted only after cancelling, once it is over and seven days have passed since cancelling; deletion takes its tournaments and their results with it (its preview names any that are live, and result recording refuses under the tombstone), while notices already delivered survive. A Track someone relies on is deleted by a previewed operation that notifies its Registrants through the Event; one whose tournament has a result cannot be deleted. Deletions run in batches behind a tombstone set in their first transaction. An Organizer's account deletion cancels, keeps, or removes their Events as "Account sign-in and deletion" above sets out. After publication, time and place changes notify Registrants; a reschedule moves the Tracks' start times, registration instants, explicit publish times, and explicit Grant windows — only those still in the future at commit — by the same wall-clock difference in the Event's timezone (once an Event has started, its start is locked: the Organizer moves the end and individual Track starts, each Track's future instants — including the windows of Grants scoped to it — following its own start, Event-scope Grant windows being listed rather than shifted, and the end cannot move into the past while a tournament is live; an Event whose end has passed cannot be rescheduled later, so extending an Event never revives an ended Grant, and its preview says how many Grants have no end and so run until the new end (it lists — as for a moved close — the Grants whose end equals the old end, warning when their holders would be stranded)); its preview clamps or refuses any of them that would fall after the new end, and one moved earlier than the commit — the Event's end included — is set to the commit — a close so moved closes registration then, its returns following from the clock like any close, and an end so moved is final, which the preview says — and an explicit publish time is set to the commit like any other instant, so the tournament publishes then, which the preview says (a derived one follows the close and start it is derived from); for a failed automatic publication the preview offers, when the result is still in the future at commit, to re-arm it at its failed time shifted by the same difference, which the commit applies as a re-arm; a timezone change asks whether to keep the instants or the local times. Times display in the Event's timezone for in-person Events and in the viewer's for online ones; on a daylight-saving night, an ambiguous local time resolves to the earlier instant, with a warning.

**Impact rule.** Operations that take away something a person holds (an Entry, a Participant's slot, what they can see through a relation) or expose data are two-phase in the API: cancelling, deleting, rescheduling, or returning an Event to draft; deleting a Track or a tournament; first publication, republication with changed pairings, and unpublishing; enabling automatic publication; changing any Visibility or Track setting; widening a field's audience; removing an Entry or an Entrant, the captain-row reset, sanctioning a person (its preview lists outstanding claim Grants of Entries holding a typed-name row tied to that person and offers to revoke them), raising a Track's minimum or maximum, the Organizer's lineup change after the swap deadline, re-parenting or releasing a child Community, deleting a child, banning a Community, removing a player from a descendant's Squad, substituting, moving an Entry on the Waitlist, revoking a Grant together with the Entries still waiting through it, or — after a publication — taking a Participant off the Roster or swapping; regenerating a slug; handing an Event or tournament to another Community, and deleting a Community (Communities and roles, above). The preview is a mutation that stores the operation, target, arguments, Organizer, impact digest, and a ten-minute expiry with a random secret, returning the secret as a single-use token (and, for an operation not yet allowed, the earliest time it will be); the commit finds the row by secret, checks that the caller is the member who stored it and still holds the capability in the owning Community (a hand-over or a removed membership in between fails it), checks the expiry, recomputes, and deletes it. Expired rows are swept. Counts shown beside a preview come from a separate query capped at a bound ("500+") and stay outside the digest. The digest covers impact kinds and the per-person lists the Organizer decides on, not growing counts; notice recipients are taken at commit. The Organizer's "view as" preview (story 14) renders their own Event server-side through `canView` and the field audiences with a role — a visitor holding the bearer link, a confirmed Registrant of a chosen Track, or the holder of a chosen Grant — never a user id.

### Invite links — Access Grants (ADR 0018)

A Grant has an action (register, or claim a typed-name Entrant of an Entry; from ADR 0023 also join a Community, take over an Event, and record results on one tournament, and from ADR 0028 move a Community under another — the four whose secrets are stored hashed, since each confers an Organizer capability — and join a Squad, hashed like them although it confers no permission, since it stands in for a person's consent), a scope (a Track, the whole Event, or one Entry — the team's join link, ADR 0029; a Community, or one tournament, for the governance actions; one Squad for joining it), a use limit, its own window — instants, never a reference to another setting: a register Grant by default stores no end and runs from its creation until its Event is over, which already ends every register Grant, so moving the Event's end needs no rewrite; presets such as "until registration closes" or "until the public opening" copy the Track's stored instant at issuance (on a Track with no close, "until registration closes" is the default: no end) (moving that instant later lists the Grants that copied it, which do not move); explicit windows shift with reschedules and never pass the Event's end — revocation, and whether it reserves its seats (single-Track Grants with a use limit; the remaining uses never beyond free Capacity — Capacity minus confirmed Entries, outstanding Offers, and other Grants' unused reserved seats, whoever is waiting). It only ever narrows — revoking, shortening its window, or lowering its use limit — with the one exception of a code restored after its Event returns from private (below). Uses are derived: active Entries created through it plus those the Organizer removed, a continuation chain counting once while any member is active or removed; a self-cancellation frees its use. A Track-scope sanction ends the person's view through Grants scoped to that Track, and through Event-scope Grants as they apply to that Track; the rest of the Event is unaffected. A Track-scope sanction binds an identity; a fresh anonymous identity costs a robot check (ADR 0027), and a sanction that must follow the person is a Community-scope one — a ban — on an email account; the sanction preview also offers to revoke the register Grant the person came through. A claim Grant has no window and cannot be shortened, only revoked: it claims one typed-name Entrant of an Entry — "which one are you?" — and can be acted on while the chosen Entrant row is active and unclaimed, its Entry active, and a claim would pass the Event's lifecycle — published, not suspended, and neither cancelled nor over unless the Entry's tournament exists and has been published, that extension capped at seven days after the Event's end; after the Event's end it shows only that bracket; once claimed, the Entry grants what any Registrant's does. A register Grant whose end has passed, or whose Event is over, is ended for every mutation — and for the query path that grants view through it, which compares the end — or, for a register Grant with none, its Event's end — with the server's time (for a claim Grant: the Event's end — after which only the bracket is visible — and that end plus seven days, with the tournament's status) (a deliberate exception to reading time only in mutations: a client-supplied time could be spoofed; an open subscription keeps its last answer until re-evaluated) — and stays ended; a register Grant that does not reserve sees only public free seats, so a shared late link never jumps the Waitlist; revoking stores the revocation instant, and a register Grant's end is set to it too, so a revoked register Grant is simply one whose end has passed (a claim Grant, having no window, is revoked by the instant alone, which its view path checks); revoking, lowering the use limit, or a window that has ended releases its unused reserved seats and schedules settle. Revoking never silently ends Entries already made through the Grant: it lists its confirmed, offered, and waitlisted Entries. Revoking with its waiting Entries is a two-phase operation (its digest covers the Grant, not the list, since nobody can join through a revoked Grant): it revokes the Grant and marks it withdrawing, after which every Entry still waiting through it — waitlisted or holding an Offer — counts as removed for every gate and for `canView`, processed or not (an Offer ends with its removed Entry, as for any removal, and its seat is offered on), and settle writes those removals and their notices in bounded pages before it issues any Offer, the state change being its progress mark. The removal preview offers to revoke the Grant the Entry came through. Links are `/g#secret` (fragment, stripped from history after reading); regenerating a Grant's secret keeps the Grant — its window, uses, and reserved seats — and makes the old link and code dead at once (a Grant without a code gets none), so a leaked invitation is rotated without releasing a seat; typed codes are exchanged for the secret by a mutation rate-limited per (Event, user) with a global per-user cap, and entered only on pages the caller can already view, so a private Event's Grants are links only and no code is issued for one; making an Event private deletes the codes of its register Grants that have not ended (found by the Event, action, and end index; claim Grants have no codes, and an ended Grant's code is refused anyway), listed in the preview (their links keep working; once the Event is visible again, the Organizer may give an unended Grant whose code was deleted — marked so on the Grant — a new code, unique within its Event, without changing its link — the one widening a Grant allows, since it restores the way in the Organizer chose at issuance, and it is checked like issuance; a Grant issued without a code never gains one). cobracket never emails an address an Organizer typed in.

### Visibility (ADR 0019)

Event: unlisted (default) or private. Track: open, invite-only, or hidden. Attached tournaments follow their Track; standalone tournaments keep their field (unlisted or private, meaning Organizer only). `canView` and `canDiscover` as in ADR 0019: bearer links by slug need no identity; id-addressed routes need a relation (an Entrant row, an invitation included); Grants give view only while they can still be acted on; a withdrawn person sees their bracket only, and a Track-scope sanction ends that too; ended Entries grant nothing else. Field audiences: registrant names (everyone who can view — default; Registrants; organizers), exact address (confirmed people — default; everyone who can view), online link (confirmed people), waitlist names never. The registrant-name audience governs the view before and during the Event only: the playing lineup of a completed tournament is part of its published result, public with it (ADR 0029, Teams) — the bracket shows team names, the registrant list the active Entrants, and forming Entries' Entrants belong to the Registrants audience. The registration requirement is the three-step ladder of the Identity section (anonymous allowed ⊂ account required ⊂ Squad-linked teams only), applied to every Entrant. A Community page has a Visibility of its own — unlisted by default, private (members only), or public, with the directory — independent of the Events it owns (ADR 0028). Hidden-Track data never appears in shared lists, counts, or Discipline lists, and story 4's single-Track presentation is decided per viewer. Displayed counts come from a sharded counter per Track; no mutation reads them, except those that cap a Track (setting a Capacity, attaching a tournament) and build its seat document from their exact total. Regenerating the Event slug regenerates attached Share Links unless the Organizer keeps them.

### Activities and delivery (ADR 0014)

Every change a person must learn of is recorded — with the system as actor for automation and scheduled processing — but projection and pinning writes are not. List Activities (joined, cancelled) are pull-only and never reach a place. Person-addressed notices (waitlisted, Offer, Offer returned, Offer lapsed, confirmed — "confirmed, not in the bracket" after go-live —, withdrawn and claimed — also to the Organizer —, removed, substituted or restored, moved on the Waitlist, advanced by an opponent's withdrawal, not in the bracket, "did not get a place" for people still waiting when the tournament goes live, or at the Event's end for a Track whose tournament never went live or that has none, unless a cancellation notice already reached them (their Entries stay waitlisted either way), publication diffs, cancellation, deletion; for teams, "you can register", "no team formed", an invitation, a lineup change, "short-handed", and "below the minimum") are written into the recipients' in-app deliveries at commit, self-contained (names resolving by id while their subject exists), checked by membership only. A notice for an Entry reaches its captain and its account Entrants — a Squad-linked Entry's staff folded per Entry per day — paged by Entrant count; an Entrant's own changes reach the person and the captain (ADR 0029). A Community Follow (Communities and roles) delivers four kinds and no others — an Entry confirmed on a public Event, a public tournament (`canDiscover`) completed with the team's placement, a Squad member joined or left, a move in a public Ranking's standings — in-app always and by email where the follower turned it on for that Follow, `canView` re-checked at delivery; members are deduplicated against their implicit subscription (ADR 0028). Places take only Activities visible at Event level with an everyone-who-can-view audience. Announcements go to the page and, if connected, the Event's Discord webhook (Discord hosts only, mentions disabled; a private Event's webhook warns). Before sending registrant-only content, the Organizer sees how many Entries have no reachable person. The Organizer may edit or delete an Announcement, which is its own document referenced by its Activity (an edit changes its text, never its audience): the page and every in-app notice of it show its current text, marked edited, so a deletion takes it back everywhere cobracket controls (the notice then reads that the Organizer removed it); a delivery to a place not yet sent is rendered from the current content, or dropped if it was deleted, and one already sent — or already being sent when the deletion commits — cannot be recalled, which the deletion's confirmation says (deleting an Announcement is an Organizer confirmation in the UI, not a two-phase operation: it takes away content, not anything a person holds). Announcements are not person-addressed notices: their in-app copies are re-checked for access at read like any list Activity, and an Event's deletion takes its Announcements and their copies with it, as for every Activity of a deleted subject (ADR 0014); the Event's cancellation notice, sent earlier, is what Registrants keep. Delivery uses Workpool, Resend, and Rate Limiter; list Activities in inbox and feed re-check access at read (person-addressed notices by membership only), delivery at send; unread counts are capped. Email is part of this feature line (slice 9, after account sign-in in slice 1): person-addressed notices then reach a reachable person's in-app inbox and their verified email address, within their own delivery preferences, so an automatic confirmation or an Offer reaches someone who is not watching the page, and the Organizer's own notices (a withdrawal, a claim, a failed automatic publication) reach their email too. Push and Discord DM follow in the same slice; before it, and for anonymous people always, personal delivery is in-app only.

### Operations API

Every Organizer and Registrant capability is a Convex function in the operations API; identity resolves only through `convex/auth.ts` (ADR 0009). The settle cron and its per-Track settles, automatic publication, and deletion batches are internal functions — not capabilities, and not callable by clients — but whatever they change is recorded as Activities. For clients that cannot confirm with their user, the MCP server answers a two-phase commit with a link to the stored preview, its secret in the URL fragment as for Grants, for the human to confirm on the web: the page never mints an identity, needs the Organizer's own session (and says which browser that is), and shows the operation, its stored arguments, and the impact recomputed. The code layout is ADR 0020's: each subject is a top-level API module in `convex/` (`events.ts`, `tracks.ts`, `entries.ts`, `grants.ts`, `announcements.ts`, `settle.ts`, …; sign-in, the merge, and account deletion are `auth.ts`'s, the single auth seam of ADR 0003), internal functions included, and the write modules every path shares — the one that changes Entry states and the seat document first among them — live in `convex/model/`, so settle and the public operations call the same code.

### Performance and concurrency

- Unset Capacity on a Track with a tournament behaves as Capacity at the Roster limit, enforced but not shown as a Capacity. Raising Capacity after the close shows the Organizer how many are waiting, to confirm by hand.
- An Event holds at most 50 Tracks and 1,000 register Grants that have not ended — counted by two ranges of an index on Event, action, and end (no end, and end in the future), since revocation sets a register Grant's end — checked when one is issued, since nothing else adds to it (claim Grants and Entry-scope join links do not count: nothing Event-wide writes or lists claim Grants, and a join link — link-only, never given a code — is bounded by one unended per Entry, so Event-wide Grant operations that include join links are paged). A Track has at most 100 Entries in the offered state at a time, whatever their derived status (settle writes lapses and returns before issuing more); freed seats beyond that wait for the next settle. So every Event-wide operation — publishing, cancelling, suspending, lifting, rescheduling — fits in one transaction's write and scheduling limits (Convex: 16,000 documents written and 1,000 functions scheduled per mutation); raising either cap means batching those operations first.
- Exact Capacity serializes registrations on a capped Track: each one reads the Track's seat document — two numbers (and, once the effective close has passed, the seats free at it; see the settle function): the confirmed count and the unused reserved seats, the latter the sum of the contributions each unreleased reserving Grant stores (its remaining uses — a cache of the derived uses, kept only because a reserving Grant exists only on a capped Track, whose registrations already serialize on this document). The one module that changes Entry states updates the confirmed count and, for an Entry through a reserving Grant, that Grant's contribution and the sum together, as do Grant issuance and use-limit lowering; once settle releases a Grant (its end passed, or its Event cancelled or over), its contribution is zero and nothing changes it again. Everything else is read, bounded: the Track's offered Entries (at most the Offer cap) are classified by the clock and stored state — outstanding (a taken seat), lapsed, returned (waiting again), or removed, removal winning over lapse — and whether anyone waits is a returned Offer or the first waitlisted Entry by index (a withdrawing Grant's waitlisted Entries count until settle writes their removal, which only keeps public seats at zero); reserving Grants whose end has passed and that settle has not yet released are subtracted by their stored contribution, in one indexed query. An unlimited Track has no seat document, so its registrations never contend on one; it is built when the Track becomes capped (setting a Capacity, or attaching a tournament), from the sharded counter's exact total — a Grant can reserve only on a capped Track, so there are none yet. A Track never becomes unlimited while anyone waits or holds an Offer, or while any reserving Grant on it is unreleased: unsetting Capacity is refused then, and in that case detaching or deleting the tournament of a Track with unset Capacity writes the Roster limit as its Capacity, shown in the preview (otherwise the Track simply becomes unlimited again, and its seat document is deleted). So a registration reads a bounded set however large the Capacity, and concurrent registrations conflict on it and Convex retries them. This is inherent to "never more than N" and acceptable within the Roster limit; truly unlimited Tracks (no tournament, no Capacity) skip the count, and clients retry a registration that exhausts its retries. The spec does not claim burst-free registration.
- An anonymous identity holds at most 100 Entry and Entrant rows together — it owns nothing on the Organizer side (ADR 0024) — enforced where those rows are created from slice 1 (ADR 0027 lowered the provisional 1,000; past it, registering with an email lifts the cap), so merging it into an account is one transaction: those are the rows the merge re-points (plus the Player link on the Entrant rows; codes are derived and need no re-point), and a merge above the cap is refused with a message naming what to cancel first, so no merge is ever half done.
- The Entry row is the pivot of optimistic concurrency for everything on it (ADR 0029): registering, activating an Entrant, a swap, and a lineup change read and write the Entry (its `activePlayingCount` among them), so two acts on one team conflict there and Convex retries one; registration is idempotent, so a retry never takes a second seat. No operation scans a Track's Entrants unbounded: Entrants are read by Entry or by (Track, user), and the per-Event notice caps count Entrants, not Entries. The recruiting list is read by (Track, state) and capped for display; the cap is not a gate. Daily caps (invitations, affiliation requests) use the rate limiter. Nothing else is touched — rows an Event owns (Tracks, Grants, Announcements, Activities, schedule and seat documents, stored previews) reference the Event and read its Community through it; an unexpired preview of the merged identity is simply stale, since its commit checks the caller against the identity that fetched it; recorded actor ids and in-app delivery rows resolve through the alias row, so a person's inbox reads deliveries addressed to the account and its aliases.
- Registrations never write Event, Track, or tournament documents; the Event page shell and Share Link reads therefore stay cached across a burst, while counts and the registrant list re-run in their own queries. The Organizer's draft projection re-runs on each registration, bounded by the Roster limit.
- `canView` reads only documents registrations never write; identity-dependent parts are overlays; "your next match" is derived on the client.
- Impact previews use bounded reads and never read counts; batched deletions sit behind a tombstone; notice deliveries are rows written in batches. Materializing and publishing 128 Participants stays far inside one mutation's limits.
- Indexes: schedule documents by next due instant; Grants by secret, by Event and code (a code is exchanged only for a Grant of the Event whose page it is entered on), by scope and end, by Event, action, and end, and by Track, reserving, released, and end; Entries by Track and state, by Track, state, and Offer deadline, by Track, state, and waitlist position, by Track, state, and each outcome notice received, by Squad, and by Grant; Entrants by Entry and state, by Track, user, and state, by Track and state, and by Grant and state; sanctions by user and Community, by Track and user, and by email tag; Follows by user and by subject; squadMemberships by Squad and by user; Communities by parent; Participants by Entry; Activity subjects by subject and time; deliveries by recipient and time and by Activity (so a deletion's batches find an Announcement's copies); Events by slug; last publications by tournament.

### Changes to the MVP (docs/specs/mvp.md)

- Stories 4, 5, 6, 8, 10, and 26 narrow to draft: adding, pasting, and removing Participants, reordering seeds, regenerating the bracket, and changing the format require unpublishing first. Renaming a Participant widens to every status.
- Unpublishing (published → draft, before any result) moves from the deferred list into scope, and an unpublished Share Link shows by default only that the bracket is being updated (the Organizer may keep showing the last publication under a banner).
- Random seeding keeps a stored salt: regeneration reuses it, and "reshuffle" writes a new one.
- Tournament deletion is two-phase in the API and batched at large scale; Discipline suggestions list a curated set and the caller's own Disciplines only.
- Track tournaments gain confirmation-order seeding and fixed seeds; standalone tournaments keep random and manual; a standalone tournament's `private` Visibility (Organizer only) becomes real.
