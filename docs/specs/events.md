# Events: hosting, registration, and Track tournaments

Synthesized from the grilling session of 2026-09-27/28 with the owner, then hardened by review rounds. Vocabulary per [`CONTEXT.md`](../../CONTEXT.md); constrained by ADRs [0005](../adr/0005-results-are-the-source-of-truth.md), [0011](../adr/0011-physical-whole-tournament-deletion.md), and [0013](../adr/0013-one-identity-for-organizers-and-registrants.md)–[0019](../adr/0019-visibility-and-access.md). The product frame lives in [`docs/vision.md`](../vision.md); the standalone tournament is specified in [`mvp.md`](./mvp.md), and this spec changes it where noted.

**Status: draft.** Items marked _pending_ wait on questions not yet settled with the owner (listed at the end).

## Problem Statement

An Organizer running a community event today collects entrants by hand — a Discord thread, a form, a spreadsheet — and then types every name into a bracket tool. Capacity, waitlists, late dropouts, invitations, and "is this bracket final?" are all managed in chat. Registrants cannot see where they stand, spectators cannot find the bracket, and every change is a message someone misses. Existing event tools (Luma) handle registration but know nothing about brackets; bracket tools (start.gg) handle both but are heavy, dated, and account-first.

## Solution

An Organizer creates an Event, adds Tracks — one per competition or split — and publishes a page. People register from that page in seconds, anonymously if the Track allows it, and always see their own status. Capacity, a reachable-only Waitlist with time-limited Offers, invite links for invitations and early access, and registration windows run themselves. When a Track should become a competition, the Organizer attaches a tournament; confirmed Entries flow into its Roster until the Organizer pins it, and publishing fixes the bracket players prepare for. Every change a person must learn of is recorded as an Activity, which is how Registrants, co-organizers later, and integrations find out what happened. Everything an Organizer or Registrant can do stays in the one operations API, so MCP and a Discord bot can drive it too (ADR 0001, 0009).

## User Stories

### Organizer — the Event

1. As an Organizer, I want to create an Event as a draft with a name, description, start and end time, timezone, and an in-person place or online link, so that I can prepare it before anyone sees it.
2. As an Organizer, I want to give an in-person Event a public area and an exact address shown only to confirmed Registrants unless I choose otherwise, so that I do not publish my venue to everyone.
3. As an Organizer, I want to add Tracks to my Event — each with a name, an optional Discipline, an optional Capacity, an optional start time (for multi-day Events), a registration window, and whether anonymous registration is allowed — so that one Event can host several competitions or splits, some stricter than others.
4. As an Organizer, I want a single-Track Event not to show the Track concept, so that a simple meetup stays simple.
5. As an Organizer, I want to publish my Event, so that people with the link can see it and register.
6. As an Organizer, I want to choose whether my Event can be opened by anyone with the link or only by people I invite, so that I can run private or pre-release Events.
7. As an Organizer, I want to make a Track invite-only, or hide it from people without an invite, so that I can run invitationals and early access next to open Tracks.
8. As an Organizer, I want to require that a Track's Registrants be reachable, so that prestigious Tracks are not flooded by anonymous or duplicate entries.
9. As an Organizer, I want to edit an Event after publishing, with time and place changes announced to Registrants and the Tracks' windows and invite links moved along with a reschedule, so that nobody misses a change.
10. As an Organizer, I want to cancel an Event, with Registrants notified and the page kept up marked cancelled, so that people who registered anonymously still learn about it.
11. As an Organizer, I want to delete an Event nobody relies on, and a cancelled one once it is over and a week has passed, so that test runs and mistakes do not clutter my list.
12. As an Organizer, I want to delete a Track, with its Registrants told through the Event, unless its tournament already has results, so that a mistaken Track is removable.
13. As an Organizer, I want to see the impact of any operation that takes something away from people or exposes data before it happens, from the web or from chat, so that I never do it blindly.
14. As an Organizer, I want to preview my Event as a visitor, a Registrant, or an invite holder, so that I can check what each of them sees.
15. As an Organizer, I want to regenerate a leaked link, so that people who should not have it lose access.

### Organizer — Entries and the Waitlist

16. As an Organizer, I want to add Entries by name, one at a time or pasted as a list, so that people who signed up in Discord or walked in are on the list without registering themselves.
17. As an Organizer, I want to rename or remove any Entry, and optionally block the person from that Track, so that typos and no-shows are cheap to fix and troublemakers stay out.
18. As an Organizer, I want to confirm an Entry over Capacity, reorder the Waitlist, and confirm waitlisted people by hand with a notice to them, so that I stay in charge of who plays.
19. As an Organizer, I want freed places to go automatically to the next reachable waitlisted person while registration is open, so that seats fill themselves and nobody is confirmed without having agreed to it when they queued.
20. As an Organizer, I want to post Announcements to my Event and, if I connect a Discord webhook, have them appear in my server, so that everyone who should know does.
21. As an Organizer, I want to be told at once when someone in my bracket withdraws, so that I can substitute or plan a walkover.

### Organizer — invite links

22. As an Organizer, I want to create invite links and codes (codes only where the page itself is visible, so links only on a private Event) — single-use, multi-use, or unlimited — for a Track or the whole Event, each with its own time window, and — for a single-Track link with a use limit on a capped Track — the option to reserve its seats, so that invited players, early-access groups, and late arrivals get in without special cases.
23. As an Organizer, I want to send a claim link for an Entry I entered by name, so that the person can take it over, manage it, and be notified.
24. As an Organizer, I want to revoke any invite link, undo a wrong claim, and block or unblock someone, so that a leak, a mix-up, or a troll is fixable.

### Organizer — Track tournaments

25. As an Organizer, I want to attach a tournament to a Track at any time, following the Track's Discipline and Visibility, so that the Track becomes a competition when I decide.
26. As an Organizer, I want confirmed Entries to flow into the draft Roster by themselves until I pin it — by pressing "pin" or by publishing — so that registration never breaks a bracket I have settled and needs no work before I do.
27. As an Organizer, I want seeds assigned randomly (reshuffled freely) or by confirmation order (later, by Ranking), with any players I choose held at fixed seeds, so that I can seed the top players and still let everyone else flow in.
28. As an Organizer, I want to see the pending changes between the Track's confirmed Entries and a pinned Roster, and apply them all, one by one, or as a substitution into a withdrawn Participant's slot, so that I control every change after I have looked.
29. As an Organizer, I want to have the tournament published automatically at a time I set (by default at the registration close or the Track's start, whichever comes first), after seeing what that will publish, so that a hands-off weekly runs itself.
30. As an Organizer, I want publishing to close the Track's public registration and freeze the bracket, and unpublishing (before any result) to let me change the bracket again, so that players never see it change behind their backs.
31. As an Organizer, I want to see, before republishing, whose first match changes — and have exactly those players notified — so that a necessary change is communicated precisely.
32. As an Organizer, I want to substitute a walk-in for a withdrawn player who has not played yet, even during play, and to restore a player who withdrew by mistake with their results intact, so that a no-show or a misclick does not force a walkover.
33. As an Organizer, I want to detach a tournament from its Track while no result exists, so that a wrong start is recoverable.
34. As an Organizer of a standalone tournament, I want to make it private (visible to me only) or unlisted, so that a test bracket stays out of sight.

### Registrant

35. As a Registrant, I want to register from the Event page with only a display name, without signing up, when the Track allows it, so that joining takes seconds.
36. As a Registrant, I want to see my status at all times — confirmed (on a Track without a tournament), in the published bracket, confirmed and awaiting the Organizer's decision, confirmed before the bracket is published, not in the bracket, waitlisted with my position, or holding an Offer with its deadline — so that I never have to ask.
37. As a Registrant, I want to cancel my Entry, and to register again later (as a new Entry) if I change my mind, so that my place goes to someone else in the meantime.
38. As a reachable Registrant, I want to join the Waitlist of a full Track and be confirmed automatically when a place frees — or, if I choose, be asked first and given a deadline to answer — so that I get in fairly without watching the page.
39. As a Registrant, I want to register through an invite link or code, and to claim an Entry entered for me, so that invitations work for me.
40. As a Registrant, I want to see Announcements and changes relevant to me on the page and, if I am reachable, wherever I chose to receive them, so that I stay informed.
41. As a Registrant, I want to be told when I register where my display name will appear, so that I choose it knowingly.
42. As a Registrant in a Track tournament, I want to see my next match, so that I know when I play.

### Spectator

43. As a Spectator, I want to open an Event page or a Share Link without an account and see it update live — and keep seeing the last published bracket while the Organizer revises it — so that following along is effortless.

## Implementation Decisions

### Domain model

- **Event**: name, description, start and end (required, UTC), IANA timezone, mode (in person or online), area, exact address or online link, the audiences of the registrant list and the exact address, Visibility (unlisted or private; public reserved), default registration requirement, lifecycle state (draft, published, cancelled) with its publication and cancellation instants, whether a suspension is in force, a stop count (raised by every suspension and by cancellation), slug, a tombstone while a batched deletion runs (Tracks and tournaments carry one too), and an optional Discord webhook.
- **Track**: name, optional Discipline, optional Capacity, optional start time (defaults to the Event's start), optional registration window (opens, closes — publication pulls the close earlier), setting (open, invite-only, hidden), registration requirement (defaults to the Event's), and Offer hold time. Its scheduling state — the next due instant, indexed, and whether the Organizer has had each outcome summary — lives in a separate per-Track document (the Event has none: its instants are due instants of its Tracks, and Event-wide changes lower every Track's), and its displayed counts in a sharded counter, so registrations never write the Track.
- **Entry**: Track, optional holder, display name (and whether the Organizer's rename locked it), state (confirmed, waitlisted, offered with a deadline and the Event's stop count when offered; cancelled, removed, lapsed; any ended one that had a holder may carry a block), confirmation instant, waitlist position, optional Grant it was created through, the holder's automatic-acceptance choice, and which outcome notices it has received ("did not get a place", "not in the bracket"), each sent at most once. Entries are never deleted individually and never revived: each registration is a new Entry.
- **Access Grant** (action, scope, secret, optional code unique within its Event, whether its code was deleted when the Event went private, use limit, reserving flag and cached contribution, optional end, revocation instant, withdrawing mark); **Announcement** (its own document: text, audience, edited flag); **Activity** with one subject row per subject; per-recipient **delivery** rows; stored **previews** of two-phase operations (indexed by secret and by expiry).
- **Tournament** gains an optional Track link, a seeding order (random with a stored salt; confirmation order on Track tournaments; manual, as today, once the Roster is stored; later Ranking), fixed seeds, a pinned flag, an armed automatic-publication time, and its **last publication** in its own row (structure, seed order, and which Entry each Participant stood for, by id; overwritten on each publication). **Participant** gains an Entry link (required on Track tournaments); its holder is read through the Entry; its display name is its own label.
- Whether an Event is upcoming, ongoing, or over is derived from its times; a query that gates view on time compares with the server's time itself, and settle materializes the rest (lapses, returns, Grant releases, outcome notices) when their instant is processed (ADR 0019).

### Identity (ADR 0013, 0015)

Registrants use the same Convex Auth identity and `users` table as Organizers; roles are relations. Account sign-in with a verified channel (a confirmed email address to begin with) ships in this feature line, since the default below depends on it (owner decision, 2026-09-30). Registration requirement per Track (the Event's value by default): reachable only — the default — or anonymous allowed, which the Organizer turns on after the page sets out what it gains (a walk-in registers in seconds from a QR code, no email needed) and what it gives up (no notices outside the app, no Waitlist, the Entry tied to one browser, one person able to register several times, blocks easy to evade). Any state that waits on a later message — the Waitlist, later approval — requires reachability regardless. Organizer-facing data never carries user ids: people appear under a participant number scoped to the Organizer — the same across that Organizer's Events, different for every other Organizer — so an Organizer sees one person's Entries across their own Events and Tracks (with a per-person headcount per Event, and former names), and nobody correlates a person across Organizers except through their public Player page (Further Notes). Chat surfaces authenticate as a linked user through `convex/auth.ts`, with Organizer and Registrant scopes, and confirm two-phase operations with their human (MCP elicitation).

### Entries (ADR 0013, 0016)

An Entry has an optional holder: self-made Entries have one; Entries entered by name have none until claimed. A user holds at most one active Entry per Track; claiming while holding a self-made one offers to cancel it first; registering again after an Entry ended creates a new Entry, at the back. The Organizer may add, rename, and remove any Entry, including one for themselves as holder; Organizer entries skip the window, the Track setting, Capacity, reachability, others' blocks, and a live or completed tournament (a walk-in during play takes a withdrawn Participant's slot by substitution, or stays confirmed and not in the bracket), but are subject to the Event being cancelled (except on a Track whose tournament has been published and not deleted), suspended, or tombstoned, the Roster limit, and — for an Entry with the Organizer as holder — one active Entry per Track. Only the Organizer can undo a wrong claim — refused with the reason, like restoration, once the Event's lifecycle would no longer allow a claim: a two-phase reset that removes the Entry (optionally blocking the person), re-enters it by name in the same place — same confirmation instant, named with the name the Organizer last gave it, so nothing the wrong claimer set carries over (its Participant's label follows) — with a fresh claim link, and re-points its Participant. A claim tells the Organizer, and an Entry the Organizer entered stays exempt from the Track's reachability requirement after it is claimed. An Entry carries a display name only (trimmed, at most 120 characters, duplicates allowed), which by default follows its holder's account name — each user carries a display name, pre-filled from their first registration, so nobody types it per Track — unless the holder sets a name for that Track (a sponsor tag, say) or the Organizer renames it; a holderless Entry carries the name the Organizer entered. Contact data lives on the user as verified channels. Renaming the account asks whether the new name applies to future registrations only or to every Entry, past ones included; either way an Entry the holder named for its Track, or the Organizer renamed, keeps its name. An account rename is allowed once every seven days (plus one correction within an hour of a rename), and each rename records the previous name, which the Organizer sees in their participant list, so renaming never hides a person from an Organizer. Registration warns that an anonymous Entry is tied to this browser, and the Organizer sees likely duplicates.

Entries are never deleted individually. The holder cancels (asked to confirm first when the Entry is in a bracket that has been published); the Organizer removes; an Offer that is declined or expires lapses. The Organizer may block the person behind any ended Entry that had a holder — two-phase, since it ends their view, and removing their active Entry on the Track too if they hold one (a flag on the ended Entry, lifted only by unblocking; the block list shows the Entry's name and the Organizer-scoped participant number, never a user id; the Organizer may instead ban the person from all of their Events, present and future — the same two-phase operation with a wider scope, stored per Organizer and person, and never shown to anyone else); blocked people receive only notices about their own status on that Track. Ended Entries are visible to the Organizer only. If an ended Entry's Participant row exists — on a pinned Roster, or still recorded in the last publication — the Participant is withdrawn and the Organizer is told at once (judged on the state at the end of the transaction, so a re-point never raises a false alarm). An Organizer's rename made while a person holds the Entry locks the name for that person on that Track: the holder cannot rename it back, and a new Entry they make there inherits it. List Activities about ended Entries are shown to the Organizer only. Entries of a cancelled Event are kept.

### Capacity, Waitlist, Offers (ADR 0015)

Capacity is per Track; unset means unlimited. A confirmed Entry keeps its place until it ends; Capacity cannot be lowered below confirmed Entries plus outstanding Offers plus unused reserved seats. Public free seats are Capacity minus those three. On a Track with a tournament, no path — over-Capacity confirmation and Grant arrivals included — confirms beyond the Roster limit (128), and an Organizer's confirmation beyond Capacity counts outstanding Offers and unused reserved seats against it too, so it never takes a place someone already holds a claim to. Changing a Track's Offer hold time applies to Offers issued afterwards, and its registration requirement to registrations afterwards; existing Entries keep their state. A pasted list of names (story 16) is a batch of Organizer entries, at most 500 names per mutation (the client sends a longer list in chunks): on a Track with a tournament it enters names up to the Roster limit as counted for Organizer entries (outstanding Offers and unused reserved seats included) and refuses the rest, listed; two fixed seeds on one position are refused.

Only reachable users join the Waitlist; holderless Entries never wait. While the Track accepts registrations, a freed seat goes to the next waitlisted person: by default, and as the joining screen says, they are confirmed at once and told (a one-tap cancel follows the notice); a person who chose to be asked first receives an Offer instead, held for the Track's hold time (an Organizer setting per Track — 1, 6, 24, or 48 hours, 24 by default); An Offer can be taken — accepted with the holder's session, or at once if the person switches to automatic acceptance — while its deadline has not passed, it has not been returned, its Entry has not been removed (a withdrawing Grant's derived removals included), and its Track is accepting registrations now, the one predicate settle issues Offers under, checked with the server clock; the entry gates (the Track setting, the Grant the Entry came through, one active Entry) were passed on joining the Waitlist and are not asked again, and a block removes the Entry. Declining offers the seat onward at once and lets the person either leave or queue again at the back (a new Entry, subject to the registration gates then); expiry lapses the Entry and sends a one-tap invitation to queue again at the back. An Offer ends in one of two ways only: it lapses when its deadline passes while it could be taken, and otherwise it returns to the Waitlist with its place kept — whenever its Track stops accepting first, for any reason — and the holder is told; when both could apply, the return wins, so no timing turns a return into a lapse. Returns are derived from stored state, processed or not, and never depend on the operation that caused them: an Offer counts as returned when its deadline falls after an effective close that has passed, when its Track's tournament is live or completed (states that never revert), or when its Event's stop count has risen since it was offered — a count, not an instant, because settle reads the Event it issues under, so any suspension or cancellation that commits after an Offer's settle raises the count that Offer recorded, whatever the functions' clocks said. Settle then writes the Entry back to the Waitlist and sends the notice (for a cancellation, the cancellation notice covers it). Two single-Track operations write returns themselves, bounded by the Offer cap: the attach clamp, which returns only the Offers beyond it, and any operation that moves a passed effective close later — reopening, or disarming by hand or by deleting or detaching a tournament whose automatic publication is armed or failed — which first writes the returns that close implied, so an Offer once cut off never becomes outstanding again (a cancellation's own disarming needs none: its stop count already returns every Offer). An opening that has passed is never moved; closing is how registration stops. Whenever anyone waits, public free seats are zero — a freed seat reaches the public only through an empty Waitlist, and holders of Grants that do not reserve join the Waitlist too; after the close the Organizer confirms waitlisted people by hand, and they are told. When the tournament goes live, or the Event ends, the people still waiting are told they did not get a place and, at go-live, confirmed people left out of the bracket that they are not in it; their Entries stay as they are (the Organizer can still confirm a waiting one by hand). Any operation that creates or confirms an Entry after such a moment tells its person itself and records it. Settle first writes the pending returns, then pages the notices, recording on each Entry the notice it received, so none is repeated or skipped whatever the order and a tournament going live after the Event's end still tells the people left out of its bracket; when nothing remains to tell for a moment, it tells the Organizer once, recorded per moment on the Track's schedule document. An Offer past its deadline counts as lapsed for every gate, processed or not, unless it counts as returned. A single-Track Grant with a use limit, on a capped Track, may reserve its seats — a flag, not a count — so its holders never wait: its unused reserved seats are its remaining uses (never below zero), and none once it has ended for good (revoked, its window over, or its Event cancelled or over; a draft or suspended Event, or a window not yet open, keeps them counted). A self-cancellation frees a use and so the seat; a removal does not, and its seat goes to the Waitlist. Invitees beyond its use limit take a second link that does not reserve and queue like anyone else. So public free seats are Capacity minus confirmed Entries, outstanding Offers, and unused reserved seats, each seat counted once. Confirmation instants and waitlist positions are stored explicitly. Waitlist positions are sortable keys, suffixed with the Entry's id so no two tie, and a move reads the gap it lands in by index range, so it writes only the moved Entry and concurrent moves into one gap conflict. The Organizer may move one waiting Entry to another position — always two-phase, since any move changes someone's place (its digest covers the moved Entry and its new position, not the Entries it passes) — and only the moved person is told, everyone else seeing their current position in their status; an outstanding Offer is unaffected (the order decides only who is offered next, and a returned Offer rejoins at its Entry's current position). Automatic acceptance — the default — is performed by settle, which confirms such a person directly in the transaction that would otherwise issue their Offer; switching to it while holding an Offer accepts that Offer.

**Settle function.** One settle function per Track keeps the seat machinery converged, and it always runs as its own scheduled internal mutation, never inside another operation: scheduled by the cron over due instants, or immediately by a mutation that lowers a due instant, as follows. Every mutation that writes something settle reads, other than a registration consuming a free seat — a seat input (cancelling, removing, blocking, reordering the Waitlist, accepting or declining an Offer, Capacity, a Grant's issue, window, use limit, or revocation), an instant (a window, the Event's times), automatic publication (arming, re-arming, disarming), the tournament (attaching, detaching, deleting, publishing, unpublishing, going live), or the Event's lifecycle (publishing, returning to draft, cancelling, suspending, lifting) — lowers the stored next due instant of each Track it affects to now when it is later or absent (no due instant counts as later than any) (an Event-wide change: every Track of the Event, which the per-Event Track cap bounds), and only when that write changed it also schedules the settle immediately (`runAfter(0)`, which runs only if the mutation commits). The schedule document is therefore the only pending marker: a burst of changes schedules one settle, and a settle that fails is retried by the cron like any other due instant. A mutation decides only what it must itself — a registration's seat check — and every gate and the seat equation read the clock directly (the seat document plus its time corrections): an Offer is outstanding while its deadline is in the future and nothing has returned it (see the Offer rules above), and an Event is over once its end has passed. So nothing needs catching up before a decision, and no operation — cancel, remove, block, revoke, close, suspend — ever depends on settle succeeding. Under an Event's or a Track's deletion tombstone every mutation on it other than the deletion's own batches (and settle deleting its schedule document) is refused — internal ones, such as delivery writers, do nothing rather than throw, so the deletion's own batches write its deletion notices — and those batches never lower or create its schedule documents, so nothing is due there (a tournament's own tombstone, below, affects only the tournament). Settle issues Offers, lapses those whose deadline passed while they could be taken, sends the notices for returns read from the clock or stored state, records the resulting Activities ("not in the bracket" at go-live, "did not get a place" at go-live or the Event's end), performs an armed automatic publication when it is due, and stores the Track's next due instant (an Offer deadline, the effective opening and close, a Grant window's end, the Event's end, the armed publish time) — writing it only when it changes. The cron runs every few tens of seconds, reading only schedule documents that have a due instant (a range bounded below, since Convex orders a missing value before every number) and are due a few seconds before now — a due instant just lowered to now already has its own immediate settle, and reading up to now would make the cron conflict with every such write — and is specified by the properties it must keep, pinned by tests: every due instant of a healthy Track is processed within about one interval; one failing Track never delays another (each settle is its own scheduled mutation, and the cron never computes a next due instant itself); a failing settle is reported to the operator and retried with bounded exponential backoff that resets after a success or when the due instant changes; and per-tick work is bounded, continuing from a cursor; a settle with more work than one bounded page (Activities for a long Waitlist when the tournament goes live) writes a page and leaves its due instant at now. A Track that should not be processed simply has no due instant: settle stores none while its Event is suspended, writes nothing under a deletion tombstone but the deletion of its own schedule document (whose first transaction deletes the affected schedule documents and the cron's records for them), and never inserts a schedule document for a missing Track; lowering skips a Track under a deletion tombstone, and settle deletes the schedule document of a Track that is tombstoned or missing. Deleting a tournament alone tombstones only the tournament — its automatic publication off, its Track's settle scheduled, and the tournament excluded at once from every lookup (Participants by Entry, withdrawal alarms, Registrant status, the Roster limit, one tournament per Track, claim Grants' post-Event extension), so a new one may be attached meanwhile. While automatic publication is armed or failed, the effective close is the earlier of the Track's close and its time — derived, never written — so cron lag cannot let anyone in late and a failure keeps registration closed, as Registrants were told. Automatic publication pins only Entries confirmed at or before the armed instant (Grant and Organizer arrivals may come later); fixed seeds on later Entries are ignored, and those Entries become pending additions. Settle never throws on expected conditions (a deleted Track, a tournament that cannot publish); it records an Activity for the Organizer, except under a deletion tombstone. Suspending an Event writes the Event (suspension in force, stop count raised) and lowers its Tracks' due instants, and nothing else; lifting clears the flag; its outstanding Offers count as returned from then on, deliveries are held, and settle stores no due instant while it is suspended (automatic publication stays armed); `canView` shows a suspended Event to its Organizer only (its effect on a live tournament is part of the pending operator workflow). The operator can purge held deliveries before lifting; lifting first marks every armed publication whose time has come as failed, in the lift itself, then schedules the Tracks' settles and resumes deliveries — deliveries to places are re-rendered from current content (a deleted Announcement is not sent, and those for an Event already over are dropped, with a note to the Organizer), while in-app notices stay as written.

### Registration window and the decision function

Each Track stores optional opens and closes instants (UTC). Public registration is open when the effective opening ≤ now < the effective close: the opening is the later of the Track's opens and the Event's publication; the close is the Track's close (unset means the Event's end, so a plain Track keeps accepting at the door). Manual open and close write these instants; an opening that has passed is never moved. An automatic publication counts as the close while armed or failed; any publication, and re-arming from failed, writes that effective close into the Track's close, a publication also capping it at its own instant. Moving a close later is refused while the Track has a published tournament — reopening is exactly moving it later afterwards. Moving a close or an opening lists the Grants whose window ends at the old instant, warning when their holders would be stranded (invite-only or hidden Tracks, private Events); Grants never move with it. An ended Grant presented while the public window is open is ignored, and the person registers publicly. Clients display the state from the instants, the publication state, and a server-time offset; mutations decide with the server clock. When a Track's close is left at the Event's end but its tournament will publish automatically at the Track's start, the Organizer is warned that door arrivals will need invite links or the Organizer's own entries.

Whether a person may register or claim, and with what result (confirmed, waitlisted, refused with a reason), is decided by one pure function. `canView` comes first, so anyone who may not see the Track gets the same "not found" as for a missing one. For a person presenting a register Grant, the Grant's window replaces the Track's and the Grant passes its own Track's invite-only or hidden setting (an Event-scope Grant passes invite-only Tracks, never hidden ones); a full Track admits them only through a Grant that reserves its seats. Absolute gates: the Event is a draft, cancelled, over, being deleted, or suspended; the Track's tournament is live or completed; the Track's reachability requirement; the Waitlist's; a block or an Organizer ban on the person; one active Entry per user per Track; the Roster limit on a Track with a tournament. Claims take no seat: they are subject to the gates that concern the person (block, one active Entry, the Event's lifecycle, suspension) but not to windows, publication, or a live tournament; only active Entries can be claimed.

### Track tournaments (ADR 0016)

A tournament may be attached to a Track (at most one per Track) at any time; while attached, its Discipline and Visibility follow the Track, and the Track's Capacity is capped at the Roster limit (unset behaves as the limit, waitlisting beyond it). Attaching is previewed: it clamps Capacity to the limit, returning Offers and lowering the use limits of reserving Grants beyond it (both listed); if more Entries are confirmed than the limit, the Organizer pins at once the Entries they choose, up to the limit, and the rest stay confirmed as pending changes and are told they are not in the bracket when it goes live. Tracks that need a larger bracket (majors) wait for phases or pools, outside this feature line.

- **Structure changes only in draft**: Roster membership, seeding, format, and bracket generation. Labels — including Participants' display names — change in every status. Unpublishing returns a published tournament to draft, which is possible exactly while no result exists. This applies to standalone tournaments as well.
- **Substitution** re-points a withdrawn Participant with no recorded result to another confirmed Entry, taking the new Entry's name, in draft, published, or live, as a two-phase operation; it checks results in the same transaction. **Restoration** gives a withdrawn Participant, results and all, back to its person: the Organizer re-enters its Entry by name in place — the Participant's label, the ended Entry's confirmation instant and Grant link, exempt from reachability — and sends the person a fresh claim link — refused, with the reason in the preview, once the Event's lifecycle would no longer allow a claim — which also lands in the original holder's inbox when the ended Entry was self-made and they are not blocked (never when it was an Organizer entry someone had claimed). Re-entries by restoration and reset are continuations, linked to the Entry they continue: exempt from Capacity and the Roster limit (the slot already exists), and a continuation chain counts as one use of its Grant. It needs no acceptance state and covers a holderless Entry or a wrong claimer's cancel alike. Substitution, restoration, and a holder reset are one re-point primitive: it updates the last publication's Participant→Entry record and notifies the new holder; after the first publication, substitution and reset also notify the person replaced (only that they were replaced, if they are blocked), and the opponent when the label they see changes. A claim of an Entry whose tournament has been published (it has a last publication, even while being revised) passes the Event-lifecycle gate — even if the Event is cancelled or over — within the claim Grant's limits. By default a withdrawn Participant's unplayed matches are walkovers, derived rather than recorded: the format engine treats a match whose one side is withdrawn and has no result as the other side's walkover (ADR 0005 — progression is derived anyway), so a withdrawal before play makes nothing live and leaves unpublishing possible, and a substitution or restoration simply takes the derived walkover away. When a result is recorded that depends on a derived walkover, that walkover is recorded first, by the system, in the same transaction; from then on it is an ordinary result — substitution is refused and restoration keeps it — and correcting it follows the MVP's correction rules. A match whose both sides are withdrawn waits for the Organizer. The opponent of a derived walkover is told that their opponent withdrew and they advance. Results can still be recorded for a withdrawn Participant. Standalone tournaments have no Entries and so no withdrawals; their walkovers stay manual, as in the MVP.
- **Projection until pinned.** An unpinned draft's Roster and bracket are computed when read from the confirmed Entries, the format, the seeding order (random by a hash of the stored salt and each Entry's id, or confirmation order), and fixed seeds; changing these does not pin, removing an Entry just ends it, and reshuffling writes a new salt. The Roster pins into stored Participants on an explicit "pin" or at publication. The action carries every projection input the Organizer saw, refuses if anything but new arrivals changed, pins exactly the Entries shown, drops any that ended meanwhile (saying so), and leaves later arrivals pending. Registrations never write tournament documents, and a Track tournament has no Participant without an Entry.
- **Pending changes** of a pinned Roster are derived: confirmed Entries not on the Roster and withdrawn Participants; they apply in draft. Names are not pending changes: any change to an Entry's name — its holder's, an account rename reaching it, or the Organizer's — writes its Participant's label in the same transaction, in every status, so a published bracket shows it at once; the Organizer's rename locks it, the rename limit stops churn, and the Organizer can correct any name at any time (owner decision, 2026-09-30, replacing approval of holders' renames). Applied additions take the next seeds within the Roster limit. In draft, the Organizer may take a Participant off a pinned Roster while keeping its Entry confirmed (it becomes a pending addition, an alternate), or swap a pinned and an unpinned Entry, keeping the seed; after a publication both are previewed operations, and the republish diff tells the person displaced. Organizer renames update both the Participant and its Entry. Every Entry id a client names — shown, fixed, substituted, or applied — must be an active confirmed Entry of that Track not already on the Roster; fixed seeds on ended Entries are dropped.
- **Publication** records the last publication (overwriting the previous one after diffing against it), closes the Track's public registration (writing the effective close, capped at the publication instant, into the Track's close; unpublishing does not reopen it), returns outstanding Offers to the Waitlist, and notifies exactly the Participants whose first match or Entry changed (the first publication diffs against nothing, and its preview lists withdrawn Participants whose names become visible). While unpublished after having been published, the Share Link by default shows only that the bracket is being updated and is temporarily not shown — to spectators, players, MCP, APIs, and unfurls alike, the Organizer alone seeing it; the Organizer may instead keep showing the last publication, with names from the current Participant rows (a removed one shows a neutral placeholder), under a "being updated" banner, and may switch between the two while in draft, each switch a two-phase operation (hiding takes away a view; showing re-exposes names). Unpublishing and hiding send no notice (the republish diff does), and notices already delivered stay. A live or completed tournament cannot be unpublished or hidden — players need it to play; a name problem there is fixed by renaming, which applies at once, or by removal. A never-published tournament is not found. Late arrivals come through invite links or the Organizer's entries as pending changes; when the tournament goes live, confirmed Entries not on the Roster are told they are not in the bracket, as is the Organizer.
- **Automatic publication** is off by default; enabling it (attaching with a publish time, setting or re-arming one) is two-phase. It has three states — off, armed, failed. The armed time (default: the earlier of the close and the Track's start) is one of the Track's due instants; when it comes, the Track's settle pins and publishes. While armed or failed, its time counts as the Track's close. If fewer than two Participants remain, the Event is not published, or it is suspended, it pins and publishes nothing, becomes failed, and tells the Organizer once; a failed time is never due again. Pending additions do not stop it, nor does a withdrawn pinned Participant, whose slot shows a derived walkover and of which the Organizer is told. The ways out: disarm (the Track's own close applies again), re-arm with a new, future time (which writes the failed time into the Track's close as the earlier of the two, unless the Organizer also chooses, in the same preview, to reopen), or any publication (which turns it off). While failed, moving the Track's close later does not reopen; disarming does. Pinning while armed, arming while the Event is a draft, and moving a Track's start while its armed time is due ("publishing now") all warn.
- Registrant status is derived against the last publication, never the draft.
- Detaching (deleting an attached tournament) is allowed while no result exists; its Entries remain, and a newly attached tournament starts unpublished. Attaching an existing standalone tournament is out of scope.

### Event lifecycle (ADR 0017)

Draft (Organizer only; no registration; no published tournaments) → published → cancelled (irreversible). An Event returns to draft only while nobody relies on it (no active holder Entry, no withdrawn Participant in a bracket) and it has no published tournament. Cancelling closes registration, returns Offers to a frozen Waitlist, disarms automatic publication, and notifies Registrants that the Event is off while any tournaments may continue; the page and Entries stay, and tournaments keep their Share Links with a cancelled banner and may still record results, be unpublished and republished, and take Organizer entries, hand confirmations of waitlisted people, and substitutions; attaching a tournament, or publishing one for the first time, is refused once the Event is cancelled. A published Event that someone relies on is deleted only after cancelling, once it is over and seven days have passed since cancelling; deletion takes its tournaments and their results with it (its preview names any that are live, and result recording refuses under the tombstone), while notices already delivered survive. A Track someone relies on is deleted by a previewed operation that notifies its Registrants through the Event; one whose tournament has a result cannot be deleted. Deletions run in batches behind a tombstone set in their first transaction. After publication, time and place changes notify Registrants; a reschedule moves the Tracks' start times, registration instants, publish times, and explicit Grant windows — only those still in the future at commit — by the same wall-clock difference in the Event's timezone (once an Event has started, its start is locked: the Organizer moves the end and individual Track starts, each Track's future instants — including the windows of Grants scoped to it — following its own start, Event-scope Grant windows being listed rather than shifted, and the end cannot move into the past while a tournament is live; an Event whose end has passed cannot be rescheduled later, so extending an Event never revives an ended Grant, and its preview says how many Grants have no end and so run until the new end (it lists — as for a moved close — the Grants whose end equals the old end, warning when their holders would be stranded)); its preview clamps or refuses any of them that would fall after the new end, and one moved earlier than the commit — the Event's end included — is set to the commit — a close so moved closes registration then, its returns following from the clock like any close, and an end so moved is final, which the preview says — and an armed publish time moved into the past disarms; a timezone change asks whether to keep the instants or the local times. Times display in the Event's timezone for in-person Events and in the viewer's for online ones; on a daylight-saving night, an ambiguous local time resolves to the earlier instant, with a warning.

**Impact rule.** Operations that take away something a person holds (an Entry, a Participant's slot, what they can see through a relation) or expose data are two-phase in the API: cancelling, deleting, rescheduling, or returning an Event to draft; deleting a Track or a tournament; first publication, republication with changed pairings, and unpublishing; enabling automatic publication; changing any Visibility or Track setting; widening a field's audience; removing an Entry, resetting its holder, blocking a person (its preview lists outstanding claim Grants for Entries tied to that person and offers to revoke them), substituting, moving an Entry on the Waitlist, revoking a Grant together with the Entries still waiting through it, or — after a publication — taking a Participant off the Roster or swapping; regenerating a slug. The preview is a mutation that stores the operation, target, arguments, Organizer, impact digest, and a ten-minute expiry with a random secret, returning the secret as a single-use token (and, for an operation not yet allowed, the earliest time it will be); the commit finds the row by secret, checks that the caller is its Organizer and the expiry, recomputes, and deletes it. Expired rows are swept. Counts shown beside a preview come from a separate query capped at a bound ("500+") and stay outside the digest. The digest covers impact kinds and the per-person lists the Organizer decides on, not growing counts; notice recipients are taken at commit. The Organizer's "view as" preview (story 14) renders their own Event server-side through `canView` and the field audiences with a role — a visitor holding the bearer link, a confirmed Registrant of a chosen Track, or the holder of a chosen Grant — never a user id.

### Invite links — Access Grants (ADR 0018)

A Grant has an action (register, or claim one active Entry), a scope (a Track or the whole Event), a use limit, its own window — instants, never a reference to another setting: a register Grant by default stores no end and runs from its creation until its Event is over, which already ends every register Grant, so moving the Event's end needs no rewrite; presets such as "until registration closes" or "until the public opening" copy the Track's stored instant at issuance (on a Track with no close, "until registration closes" is the default: no end) (moving that instant later lists the Grants that copied it, which do not move); explicit windows shift with reschedules and never pass the Event's end — revocation, and whether it reserves its seats (single-Track Grants with a use limit; the remaining uses never beyond free Capacity — Capacity minus confirmed Entries, outstanding Offers, and other Grants' unused reserved seats, whoever is waiting). It only ever narrows — revoking, shortening its window, or lowering its use limit — with the one exception of a code restored after its Event returns from private (below). Uses are derived: active Entries created through it plus those the Organizer removed, a continuation chain counting once while any member is active or removed; a self-cancellation frees its use. A block ends the person's view through Grants scoped to that Track, and through Event-scope Grants as they apply to that Track; the rest of the Event is unaffected. Blocks bind an identity, so a fresh anonymous session can evade them until anti-spam measures exist; the block preview also offers to revoke the register Grant the person came through. A claim Grant has no window and cannot be shortened, only revoked: it can be acted on while its Entry is active and unclaimed and a claim would pass the Event's lifecycle — published, not suspended, and neither cancelled nor over unless the Entry's tournament exists and has been published, that extension capped at seven days after the Event's end; after the Event's end it shows only that bracket; once claimed, the Entry grants what any Registrant's does. A register Grant whose end has passed, or whose Event is over, is ended for every mutation — and for the query path that grants view through it, which compares the end — or, for a register Grant with none, its Event's end — with the server's time (for a claim Grant: the Event's end — after which only the bracket is visible — and that end plus seven days, with the tournament's status) (a deliberate exception to reading time only in mutations: a client-supplied time could be spoofed; an open subscription keeps its last answer until re-evaluated) — and stays ended; a register Grant that does not reserve sees only public free seats, so a shared late link never jumps the Waitlist; revoking stores the revocation instant, and a register Grant's end is set to it too, so a revoked register Grant is simply one whose end has passed (a claim Grant, having no window, is revoked by the instant alone, which its view path checks); revoking, lowering the use limit, or a window that has ended releases its unused reserved seats and schedules settle. Revoking never silently ends Entries already made through the Grant: it lists its confirmed, offered, and waitlisted Entries. Revoking with its waiting Entries is a two-phase operation (its digest covers the Grant, not the list, since nobody can join through a revoked Grant): it revokes the Grant and marks it withdrawing, after which every Entry still waiting through it — waitlisted or holding an Offer — counts as removed for every gate and for `canView`, processed or not (an Offer ends with its removed Entry, as for any removal, and its seat is offered on), and settle writes those removals and their notices in bounded pages before it issues any Offer, the state change being its progress mark. The removal preview offers to revoke the Grant the Entry came through. Links are `/g#secret` (fragment, stripped from history after reading); regenerating a Grant's secret keeps the Grant — its window, uses, and reserved seats — and makes the old link and code dead at once (a Grant without a code gets none), so a leaked invitation is rotated without releasing a seat; typed codes are exchanged for the secret by a mutation rate-limited per (Event, user) with a global per-user cap, and entered only on pages the caller can already view, so a private Event's Grants are links only and no code is issued for one; making an Event private deletes the codes of its register Grants that have not ended (found by the Event, action, and end index; claim Grants have no codes, and an ended Grant's code is refused anyway), listed in the preview (their links keep working; once the Event is visible again, the Organizer may give an unended Grant whose code was deleted — marked so on the Grant — a new code, unique within its Event, without changing its link — the one widening a Grant allows, since it restores the way in the Organizer chose at issuance, and it is checked like issuance; a Grant issued without a code never gains one). cobracket never emails an address an Organizer typed in.

### Visibility (ADR 0019)

Event: unlisted (default) or private. Track: open, invite-only, or hidden. Attached tournaments follow their Track; standalone tournaments keep their field (unlisted or private, meaning Organizer only). `canView` and `canDiscover` as in ADR 0019: bearer links by slug need no identity; id-addressed routes need a relation; Grants give view only while they can still be acted on; a withdrawn person sees their bracket only, and a block ends that too; ended Entries grant nothing else. Field audiences: registrant names (everyone who can view — default; Registrants; organizers), exact address (confirmed people — default; everyone who can view), online link (confirmed people), waitlist names never. Hidden-Track data never appears in shared lists, counts, or Discipline lists, and story 4's single-Track presentation is decided per viewer. Displayed counts come from a sharded counter per Track; no mutation reads them, except those that cap a Track (setting a Capacity, attaching a tournament) and build its seat document from their exact total. Regenerating the Event slug regenerates attached Share Links unless the Organizer keeps them.

### Activities and delivery (ADR 0014)

Every change a person must learn of is recorded — with the system as actor for automation and scheduled processing — but projection and pinning writes are not. List Activities (joined, cancelled) are pull-only and never reach a place. Person-addressed notices (waitlisted, Offer, Offer returned, Offer lapsed, confirmed — "confirmed, not in the bracket" after go-live —, withdrawn and claimed — also to the Organizer —, removed, substituted or restored, moved on the Waitlist, advanced by an opponent's withdrawal, not in the bracket, "did not get a place" for people still waiting when the tournament goes live, or at the Event's end for a Track whose tournament never went live or that has none, unless a cancellation notice already reached them (their Entries stay waitlisted either way), publication diffs, cancellation, deletion) are written into the recipients' in-app deliveries at commit, self-contained (names resolving by id while their subject exists), checked by membership only. Places take only Activities visible at Event level with an everyone-who-can-view audience. Announcements go to the page and, if connected, the Event's Discord webhook (Discord hosts only, mentions disabled; a private Event's webhook warns). Before sending registrant-only content, the Organizer sees how many Entries have no reachable person. The Organizer may edit or delete an Announcement, which is its own document referenced by its Activity (an edit changes its text, never its audience): the page and every in-app notice of it show its current text, marked edited, so a deletion takes it back everywhere cobracket controls (the notice then reads that the Organizer removed it); a delivery to a place not yet sent is rendered from the current content, or dropped if it was deleted, and one already sent — or already being sent when the deletion commits — cannot be recalled, which the deletion's confirmation says (deleting an Announcement is an Organizer confirmation in the UI, not a two-phase operation: it takes away content, not anything a person holds). Announcements are not person-addressed notices: their in-app copies are re-checked for access at read like any list Activity, and an Event's deletion takes its Announcements and their copies with it, as for every Activity of a deleted subject (ADR 0014); the Event's cancellation notice, sent earlier, is what Registrants keep. Delivery uses Workpool, Resend, and Rate Limiter; list Activities in inbox and feed re-check access at read (person-addressed notices by membership only), delivery at send; unread counts are capped. Email, push, and Discord DM wait for account sign-in (_pending_); until then personal delivery is in-app only.

### Operations API

Every Organizer and Registrant capability is a Convex function in the operations API; identity resolves only through `convex/auth.ts` (ADR 0009). The settle cron and its per-Track settles, automatic publication, and deletion batches are internal functions — not capabilities, and not callable by clients — but whatever they change is recorded as Activities. For clients that cannot confirm with their user, the MCP server answers a two-phase commit with a link to the stored preview, its secret in the URL fragment as for Grants, for the human to confirm on the web: the page never mints an identity, needs the Organizer's own session (and says which browser that is), and shows the operation, its stored arguments, and the impact recomputed. The code layout is ADR 0020's: each subject is a top-level API module in `convex/` (`events.ts`, `tracks.ts`, `entries.ts`, `grants.ts`, `announcements.ts`, `settle.ts`, …), internal functions included, and the write modules every path shares — the one that changes Entry states and the seat document first among them — live in `convex/model/`, so settle and the public operations call the same code.

### Performance and concurrency

- Unset Capacity on a Track with a tournament behaves as Capacity at the Roster limit, enforced but not shown as a Capacity. Raising Capacity after the close shows the Organizer how many are waiting, to confirm by hand.
- An Event holds at most 50 Tracks and 1,000 register Grants that have not ended — counted by two ranges of an index on Event, action, and end (no end, and end in the future), since revocation sets a register Grant's end — checked when one is issued, since nothing else adds to it (claim Grants do not count: nothing Event-wide writes or lists them). A Track has at most 100 Entries in the offered state at a time, whatever their derived status (settle writes lapses and returns before issuing more); freed seats beyond that wait for the next settle. So every Event-wide operation — publishing, cancelling, suspending, lifting, rescheduling — fits in one transaction's write and scheduling limits (Convex: 16,000 documents written and 1,000 functions scheduled per mutation); raising either cap means batching those operations first.
- Exact Capacity serializes registrations on a capped Track: each one reads the Track's seat document — two numbers: the confirmed count and the unused reserved seats, the latter the sum of the contributions each unreleased reserving Grant stores (its remaining uses — a cache of the derived uses, kept only because a reserving Grant exists only on a capped Track, whose registrations already serialize on this document). The one module that changes Entry states updates the confirmed count and, for an Entry through a reserving Grant, that Grant's contribution and the sum together, as do Grant issuance and use-limit lowering; once settle releases a Grant (its end passed, or its Event cancelled or over), its contribution is zero and nothing changes it again. Everything else is read, bounded: the Track's offered Entries (at most the Offer cap) are classified by the clock and stored state — outstanding (a taken seat), lapsed, returned (waiting again), or removed, removal winning over lapse — and whether anyone waits is a returned Offer or the first waitlisted Entry by index (a withdrawing Grant's waitlisted Entries count until settle writes their removal, which only keeps public seats at zero); reserving Grants whose end has passed and that settle has not yet released are subtracted by their stored contribution, in one indexed query. An unlimited Track has no seat document, so its registrations never contend on one; it is built when the Track becomes capped (setting a Capacity, or attaching a tournament), from the sharded counter's exact total — a Grant can reserve only on a capped Track, so there are none yet. A Track never becomes unlimited while anyone waits or holds an Offer, or while any reserving Grant on it is unreleased: unsetting Capacity is refused then, and in that case detaching or deleting the tournament of a Track with unset Capacity writes the Roster limit as its Capacity, shown in the preview (otherwise the Track simply becomes unlimited again, and its seat document is deleted). So a registration reads a bounded set however large the Capacity, and concurrent registrations conflict on it and Convex retries them. This is inherent to "never more than N" and acceptable within the Roster limit; truly unlimited Tracks (no tournament, no Capacity) skip the count, and clients retry a registration that exhausts its retries. The spec does not claim burst-free registration.
- Registrations never write Event, Track, or tournament documents; the Event page shell and Share Link reads therefore stay cached across a burst, while counts and the registrant list re-run in their own queries. The Organizer's draft projection re-runs on each registration, bounded by the Roster limit.
- `canView` reads only documents registrations never write; identity-dependent parts are overlays; "your next match" is derived on the client.
- Impact previews use bounded reads and never read counts; batched deletions sit behind a tombstone; notice deliveries are rows written in batches. Materializing and publishing 128 Participants stays far inside one mutation's limits.
- Indexes: schedule documents by next due instant; Grants by secret, by Event and code (a code is exchanged only for a Grant of the Event whose page it is entered on), by scope and end, by Event, action, and end, and by Track, reserving, released, and end; Entries by Track, holder, and state, by Track, state, and Offer deadline, by Track, state, and waitlist position, by Track, state, and each outcome notice received, and by Grant; Participants by Entry; Activity subjects by subject and time; deliveries by recipient and time and by Activity (so a deletion's batches find an Announcement's copies); Events by slug; last publications by tournament.

### Changes to the MVP (docs/specs/mvp.md)

- Stories 4, 5, 6, 8, 10, and 26 narrow to draft: adding, pasting, and removing Participants, reordering seeds, regenerating the bracket, and changing the format require unpublishing first. Renaming a Participant widens to every status.
- Unpublishing (published → draft, before any result) moves from the deferred list into scope, and an unpublished Share Link shows the last publication with a banner.
- Random seeding keeps a stored salt: regeneration reuses it, and "reshuffle" writes a new one.
- Tournament deletion is two-phase in the API and batched at large scale; Discipline suggestions list a curated set and the caller's own Disciplines only.
- Track tournaments gain confirmation-order seeding and fixed seeds; standalone tournaments keep random and manual; a standalone tournament's `private` Visibility (Organizer only) becomes real.

## Testing Decisions

- **Seam 1 — pure functions**: the registration and claim decision function and its "accepting now" predicate (every gate, with and without Grants, reachability, windows, time), `canView`/`canDiscover` over the Visibility chain and every viewer kind including withdrawn and blocked people, audience resolution, the draft projection (Entries + order + salt + fixed seeds → Roster and bracket, stable under insertion, with fixed seeds), pending-change derivation, and the impact-operation classifier (every operation is checked against the rule). Table-driven; they carry the bulk of the tests.
- **Seam 2 — the operations API via `convex-test`**: registration lifecycles (confirm, waitlist, Offer accept/decline/expire/auto-accept and return by every cause (a reopen racing an unprocessed close included), a failed settle retried by the cron, cancel and re-register, withdrawal, removal with and without block, claim and holder reset), settle invariants after every seat-input write, the settle cron processing instants late or on deleted subjects, pinning with a stale view (refused, or dropping ended Entries), publication and unpublication with diffs and the last-publication record, substitution racing a result, automatic publication becoming failed when it cannot publish (and at the lift of a suspension), re-points (substitution, restoration, reset) updating the last publication, Event cancel and delete with surviving notices, two-phase tokens refusing another target or stale impact, Grant windows across a reschedule, and not-found uniformity for non-viewers.
- A property test drives random sequences of Entry operations, Capacity changes, and elapsed instants against the settle invariants.
- Pages follow the existing page-test and browser-gate conventions; the Event page shell and Share Link must keep their queries identity-free and Entry-free, asserted directly.

## Out of Scope

Approval-based registration; check-in (QR and express mode), including combined at-the-door registration and check-in; re-hosting by cloning (the vision's settled direction; its details — and whether templates help — are to be discussed with the owner); inviting past Registrants and binding invite links to a person; explicit Follows (of Events, Tracks, Players); multiple tournaments per Track, phases, and pools; attaching an existing standalone tournament to a Track; Track exclusion rules; Event-wide Capacity; organizer-defined registration questions; teams (the "confirmed people" audience is defined over people on an Entry so teams can extend it); Communities, co-organizers, and member-only audiences; public listing, search indexing, and vanity URLs; a seeding-reveal stage before the bracket; Discord-role gating; match-participant and checked-in audiences (room codes); automated walkover cascades; email, push, and Discord DM delivery until account sign-in exists (_pending_); paid Events.
