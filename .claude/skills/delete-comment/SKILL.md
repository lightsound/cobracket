# Delete Comment

Prose comments rot: they repeat the code until they drift, then they lie.
This repo keeps its facts in code, ADRs (`docs/adr/`) and docs, and enforces
the result with `bun run lint:comments` — a ratchet that bans new prose
comments and only ever lets the recorded set shrink. This skill is the
repeatable audit that produced that state (first run: 2026-11-21).

## Corpus

Audit every comment in tracked source:

- `src/`, `convex/` (hand-written), `spacetimedb/` (hand-written),
  `scripts/`, `e2e/`, tests wherever they live, config files
  (`.fallowrc.jsonc`, `.importlintrc.jsonc`, `vite.config.ts`,
  `vitest.config.ts`, `cloudflare.config.ts`), root files,
  `.github/workflows/*.yml`, `src/theme.css`, `.env.example`,
  `.claude/hooks/*.sh`.

Exclude, and say so in the report: generated trees (`convex/_generated/**`,
`spacetimedb/bindings/**`), vendored and kit-managed skill files
(`.claude/skills/**`, `.agents/skills/**`, `.cursor/**`), `.deepsec/**`,
tool-managed files (`.claude/hooks/fallow-gate.sh` — generated by fallow),
`node_modules`, lockfiles, and all `.md` documents (documents are not
comments).

## Machine directives are not prose — never delete them

Directives are instructions to tools; deleting one breaks a gate. They are
counted separately and left intact:

- import-lint tags (`/** @public */`, `@package`, `@private`) — the repo's
  public faces depend on them
- suppression directives **with their reasons**: `import-lint-disable`,
  `fallow-ignore` / `fallow-ignore-file` / `fallow-ignore-next-line`,
  `oxlint-disable` / `eslint-disable`, `@ts-expect-error` / `@ts-ignore` /
  `@ts-nocheck`, `@vite-ignore`, `prettier-ignore` / `oxfmt-ignore`,
  `v8 ignore` / `istanbul ignore`
- `/// <reference ... />`, shebangs, `@generated` / DO NOT EDIT headers,
  SPDX / license lines, `shellcheck` / `yamllint` directives. (Kit sync
  markers live in the Markdown guidance files; documents are outside the
  corpus.)

If a directive is attached to prose, keep the directive and judge only the
prose. If prose must shrink around a `/** @public */` JSDoc, the block
becomes exactly `/** @public */`.

## The four categories

Judge every prose comment — a block, not a line — as exactly one of:

- **Tautology** — repeats what the code already shows. Example from the
  first run: the shadcn lint test's expectation annotations
  (`"5 shadcn(no-unknown-classes)", // string`), and section labels in
  `src/theme.css` (`/* Chrome */`, `/* Brand ("venom" lime) */`).
- **Stale** — states a fact that is no longer true. Examples:
  `convex/schema.ts` said the auth module "lands in a separate task"
  (`convex/auth.ts` exists and implements it); `spacetimedb/src/schema.ts`
  called the share slug "a crypto-random token" (it is ADR 0032's
  HMAC derivation); `deploy.yml` said production is "deliberately not
  live" (live for design review since 2026-09-27). Verify staleness
  against the code and the ADRs, never from the comment's own wording.
- **Excuse** — excuses or justifies a hacky implementation ("temporary",
  "for now we just…", "good enough") where the code diverges from the
  design. The first run found **zero**: every candidate was sanctioned
  design on inspection (the newest-100 cap in `convex/tournaments.ts` is
  the spec's Deferred section verbatim; the SpacetimeDB adapter's
  write-result synthesis is ADR 0031's design). Check the spec and ADRs
  before calling a comment an excuse.
- **Decision Record** — documents an important, non-obvious decision:
  a contract, an invariant, a measured reason, a rejected alternative.
  Example: the `createBackendQuery` contract that lived in
  `src/lib/backend.ts`'s JSDoc, now an amendment to ADR 0004.

Long comments are the weakest class: a long "tautology" is often a
decision record in disguise (a contract, a false-pass hazard, a seeding
constraint). Sample and re-judge them before deleting.

## Actions

- **Tautology** → delete.
- **Stale** → delete. If the stale text also lives in a user-facing
  string (the `deploy.yml` notice repeated its comment's false premise),
  fix the string too and flag the non-comment edit in the PR body.
- **Excuse** → delete the comment **and** file a GitHub issue
  (`gh issue create`, English) naming the hack, its location, and what
  the proper fix would be. Do **not** fix the hack in the audit PR.
- **Decision Record** → move it into an ADR under `docs/adr/`, following
  the repo's format (title, prose, `## Considered Options`,
  `## Consequences`; amendments are prepended as
  `Amended on <date> (...): ...` paragraphs after the title). Extend the
  ADR that already covers the decision; create the next number only when
  none does. Facts about the diagnostics gates go to
  `docs/diagnostics-gates.md` instead — it is their designated home.
  At the code site, delete the comment, or leave a **one-line pointer**
  where a signpost is genuinely needed
  (`// Draws (the drawsAllowed threading): docs/adr/0002-....md.`).
  List every pointer left in the report. Config files are the standing
  exception: rule rationale stays inside `.fallowrc.jsonc` and
  `.importlintrc.jsonc`, where the config's own convention puts it.

After moving anything, grep for prose that referenced the removed
comments ("see the header of…", "the comments at…") and keep every
reference truthful.

## The ratchet

`scripts/lint-comments.ts` (wired as `lint:comments` in `verify`) scans
the corpus above, classifies each comment block as directive or prose,
and compares the prose set against `scripts/lint-comments.baseline.json`
(file + normalised-text hash, multiplicities preserved):

- a prose comment that is not in the baseline **fails**;
- a baseline entry whose comment no longer exists **fails** — the
  baseline may only shrink, and it stays honest;
- `--update` regenerates the baseline from the current tree.

Update procedure: make the intentional change (delete the comment, or
move it into an ADR and leave a pointer), run
`bun scripts/lint-comments.ts --update`, and **review the baseline diff
in the PR like code** — an `--update` that adds entries is a new comment
sneaking in, not a removal being recorded.

## Verification

Deletions must be comment-only. Prove it per file type before the PR:
for TS-family files, tokenise the before and after versions with the
TypeScript scanner (skipping trivia) and compare the token streams —
equal streams mean no code changed; for hash/CSS files, compare with
comment lines stripped. Then:

1. `bun run verify` — the full gate, which now includes `lint:comments`.
2. `bun x vp check` clean on every new or edited `.md` (oxfmt formats
   Markdown; the ADR and doc edits included).
3. The standing PR rule: an independent agent re-checks categorisation
   samples (the long-tautology class first), verifies no directive or
   load-bearing comment was deleted, re-runs the comment-only proof and
   the gates — fix and repeat until it reports no new findings, and only
   then create the PR.

Report: corpus and exclusions; counts (total, directive vs prose, per
category); issues filed (number + title, or "none — zero excuse
comments" with the rejected candidates); ADRs created or extended and
every pointer left; baseline size; comment-only lines deleted; and the
estimate of lines the codebase would shed if **all** prose comments were
deleted (comment-only lines only — an inline comment sheds no line).
