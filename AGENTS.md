## Architecture Notes

- Module boundaries: browser code stays in `src/`; backend code stays in `spacetimedb/` (ADR 0031): a top-level file of `spacetimedb/src/` is an API module and the only place a reducer or view is registered (the operations API is their public reducers and views: every Organizer capability plus the Share Link read, ADR 0001; `auth.ts` is auth, ADR 0031; `schema.ts` the schema), and a subdirectory is a library that registers nothing: `spacetimedb/src/lib/` for what API modules share (import it as `./lib`; ImportLint keeps it out of `src/`), with the format engine (`spacetimedb/format/`) and the lifecycle table (`spacetimedb/lifecycle/`) as sibling packages. Nothing on this platform enforces the registration rule mechanically (ADR 0031 states this honestly): the guard discipline is convention, carried by the module harness's guard tests and the connection-level suite — every reducer resolves identity first through the binding module (`spacetimedb/src/lib/binding.ts`)
- Lifecycle state changes go only through the shared transition table in `spacetimedb/lifecycle/` (ADR 0033): module guards and status writes consult it, and the client derives offered actions from it; allowed-status lists and next-status rules are never restated elsewhere. Adding a lifecycle state or event means updating the table and its exhaustive transition tests in the same change
- The browser client is the SpacetimeDB SDK's `DbConnection` (from the generated bindings in `spacetimedb/bindings/`), not React. Solid 2 subscribes to it through the data seam (`src/lib/backend.ts`, whose implementation is `src/lib/spacetimedb.ts`)
- Two things keep page boundaries from waiting on round trips they do not need, both measured in Chromium against a local deployment with 100ms of one-way latency (the measurements are in `docs/diagnostics-gates.md`): the Organizer identity is one app-wide subscription (`src/organizer.tsx`, read with `useOrganizer()`; a per-page `createOrganizer()` cost every page a "Checking your session…" round trip, and the Home list a second one behind it, an `[ASYNC_WATERFALL]`), and each route's data starts on link intent (`preload` in `src/router.ts` → `prefetchBackendQuery`, the seam's prefetch — an early subscription the page then finds warm; it runs ahead of the click only because the router is created with `preloadLinks: intentPreload()`, since link preloading is opt-in from router 2.0.0-next.38). What remains is honest: the management page's data after *creating* a tournament (nothing to hover), and the Discipline suggestions (an invisible `<datalist>` fallback, keyed to the view's discipline)
- Generated or vendored code: `spacetimedb/bindings/` (from `bun run spacetime:codegen`). Do not edit by hand
- Sensitive areas: `vite.config.ts` must keep `host: '0.0.0.0'` for Cursor's preview. Keep `solid({ start: { devtools: false } })` unless `@solidjs/start-devtools` is installed
- Verifying reactive code: with `bun dev` running, the dev server serves `POST /__solid/diagnostics` (`@solidjs/diagnostics` + the plugin's `diagnostics: true`). Open the page, then `curl -X POST localhost:3000/__solid/diagnostics -d '{"method":"begin"}'`, perform one interaction, and read `{"method":"costs"}` / `{"method":"end"}` — the artifact carries rule diagnostics plus per-re-run causality, self-time, waste and holds. Prefer this over reading the code or instrumenting it by hand. Loops and budgets: `node_modules/@solidjs/diagnostics/skills/agent-loops/SKILL.md`. One page under test at a time (first responder wins), and pass `{ name }` to memos/effects you intend to interrogate — anonymous `computed` rows are unactionable.
- Reactivity diagnostics: `src/dev-diagnostics.ts` turns on Solid's attribution engine, called from `App` next to `initAuth()`. That is the opt-in tier that reports `[SILENT_HOLD]`, `[UNSTABLE_LIST_IDENTITY]`, `[IMMUTABLE_UPDATE_IN_STORE]`, `[ASYNC_WATERFALL]` and friends — the runtime evidence for Solid 2 hard rules that `solid2-kit check` can only see as tokens. Watch the browser console during `bun dev`; every code maps to a repair in `node_modules/solid-js/skills/reactivity-diagnostics/SKILL.md`. Stripped from production (`isDev`, plus an inert no-op build of `solid-js/attribution`), so it costs nothing there, and it stands down under vitest and in the browser gate's `--mode e2e`, where a harness owns the engine — an app-side hold opens a fresh window over the engine's tables and hides what the gate recorded, and holds combine per key, so a threshold a gate turns off would stay armed beside the app's hold (`src/dev-diagnostics.test.tsx` measures both sides); in `--mode e2e` it installs only the scope-width recorder (`src/scope-widths.ts`). Both gate environments disable solid-refresh, whose wrapper memo is a reactive source per component row and would pollute the gates' raw scope-width counts, so the gates measure the shipped graph. The same codes are enforced, not merely watched, by the test gate below. The `solid-2` skill documents the engine from kit v0.11.1 on
- The diagnostics test gate: `src/test-setup.ts`, wired as `setupFiles` for the `src` project, runs every test body inside a `@solidjs/diagnostics` capture with attribution on and fails the test on what it finds (the judgement itself is `assertGate` in `src/diagnostics-verdict.ts`, shared with the browser gate below). Three questions, because no one of them is enough. One `expectNoDiagnostics` covers every code the gate can see — 65 of the engine's 67, `[HOT_SCOPE_TIME]` and `[FALLBACK_FLASH]` being off for reasons below. `expectNoSilentHolds` covers what that leaves: the engine emits a hold's code only past `holds.infoMs` (100ms), so a shorter unacknowledged hold is real, recorded, and coded nowhere. The third: no scope may track 30 sources or more (`WIDE_SCOPE_SOURCES` in `src/diagnostics-verdict.ts`, counted by `src/scope-widths.ts` from the engine's `create` and `rerun` records); the widest scope in the shipped app tracks 9. The `src` project runs on happy-dom because the `node` condition resolves Solid's *server* build, where writes are inert (`[SERVER_WRITE]`), effects never run and the tables stay empty — a green reactive test proving nothing. Two engine thresholds are changed and the rest are defaults: `hotTime` and `fallbackFlashes` are both **off** in this environment, because each measures the harness rather than the app — wall-clock taken while five vitest projects transform and run concurrently against an emulated DOM, and a fallback's showing timed against fixture latency that no fixture possesses. So every assertion the gate makes is count-based or structural, and time budgets are measured where they mean something: the dev-server artifact loop above, against a real browser. The other duration-gated codes stay on — an unacknowledged hold and a sequential-flight waterfall are shapes the app either has or does not, and neither a slow runner nor an instant fixture invents one. `src/diagnostics-gate.test.tsx` proves both halves (the engine finds a real mistake here; an undeclared finding fails the test) by re-running itself in a child vitest with the declarations withheld. The measurements behind every choice in this bullet are in `docs/diagnostics-gates.md`.
- The real-browser diagnostics gate: `e2e/share-link.test.ts` (vitest project `e2e`, `bun run test:e2e`) drives Chromium through `playwright-core` against the dev server in `--mode e2e` and a local SpacetimeDB standalone with the real module published — nothing faked — and captures the whole Organizer path (create a 16-player double elimination, add the roster, generate, publish, open the Share Link) through `@solidjs/diagnostics`' `captureBrowserArtifact`, the in-page bridge the Vite plugin already injects for the curl loop above. The artifact is judged by `assertGate` in `src/diagnostics-verdict.ts`, the same verdict the happy-dom gate applies, so the two cannot drift; engine thresholds stay at their defaults here, because a real browser is where the wall-clock ones mean something — all but `fallbackFlashes`, since what `[FALLBACK_FLASH]` measures is the backend's latency, and the gate's backend answers over loopback. It exists because the happy-dom gate cannot see everything. Two numbers decide its shape. The scope-width check fails at 30 sources, and the scenario size is a contract: the per-row defect it exists to catch costs the list's insert effect one source per row, so the 8-player double elimination (15 matches) cannot falsify it and the 16-player one (31 matches) can — do not shrink the scenario without re-proving the gate (the manual procedure is in `docs/diagnostics-gates.md`). solid-refresh is off in that mode, and so is the Vite plugin's `performanceTracks` injection (on by default under `vite dev`): each pollutes the scopes the gate times. `e2e/global-setup.ts` boots what it needs: with `E2E_BASE_URL` set it starts nothing; with `.env.local` naming a *local* standalone (`VITE_SPACETIMEDB_HOST` / `VITE_SPACETIMEDB_DB`) that already answers, it publishes the current module there and starts only the dev server; otherwise it starts a standalone too, on the gate's own port, and publishes the module to a database that exists only for the gate. The target is asserted local before the app starts — the publish host is built from a loopback literal and the gate's own port, asserted free before the server starts, and the publish names its server explicitly — so the gate cannot publish to Maincloud or write tournaments to a cloud deployment; children die with the run — the whole process group, waited on until every member is gone. The boot mechanics and the measurements are in `docs/diagnostics-gates.md`.
- Changing the gates: before editing `src/test-setup.ts`, `src/diagnostics-verdict.ts`, `src/diagnostics-gate.test.tsx`, `src/dev-diagnostics.ts`, `src/scope-widths.ts`, `e2e/global-setup.ts`, `e2e/share-link.test.ts`, `vite.config.ts` or `vitest.config.ts`, read `docs/diagnostics-gates.md` (which holds the browser gate's boot mechanics) and the header of the file you are changing. When the browser scenario or a threshold changes, re-prove the browser gate with the manual defect injection described there.
- Testing a page: `src/test-fakes.ts` replaces the app's data seam so a whole page runs under the gate without a backend deployment. It is cheap because of ADR 0004 — a page reaches the backend through `src/lib/backend.ts` (`getBackendUrl`, `createBackendQuery`, `runMutation`, `prefetchBackendQuery`, driven by the descriptors in `src/lib/operations.ts`) and `src/lib/auth`, and nothing else — so those two plus the two router hooks are mocked and the rest of the page runs for real. `publishQuery` is typed against the operation descriptors, whose Args/Result are the contract types declared in `src/lib/operations.ts`, so a fixture is typed against the declared contract. The adapter is written against the same declarations, but the type checker does not hold the two sides together — their parity with the real module is carried by the live adapter test (`src/lib/spacetimedb.live.test.tsx`); the connection suite separately proves the module's wire behaviour through the generated bindings. The fake's first read is a **promise**, on purpose: `<Loading>` boundaries then engage as they do in production and a held write forms, which is what gives the gate something to judge — a page tested against synchronous data proves much less. `src/pages/*.test.tsx` are the worked examples; prefer extending them to writing a narrower component test

## Commands

- Install: `bun install`
- Dev: `spacetime start --listen-addr 127.0.0.1:3100` for a local server (port 3100, not the CLI's default 3000 — that is the dev server's port), `bun run spacetime:publish:local` once to publish the module (it also seeds the module secret from the gitignored `.spacetime-secret`, ADR 0032), and `bun dev` with `VITE_SPACETIMEDB_HOST` and `VITE_SPACETIMEDB_DB=cobracket` in `.env.local` (two long-running processes: the standalone and the dev server). Production serves the same backend on Maincloud (see `## Production deployment`)
- Build: `bun run build`
- Deploy (production, see `## Production deployment`): `bun run deploy` = `deploy:backend` (`spacetime publish` of the module to Maincloud, then a build with the Maincloud host and database baked in; needs an authenticated `spacetime` CLI — CI installs the pinned CLI and logs in with `SPACETIMEDB_TOKEN`) then `deploy:web` (`cf deploy dist/client`, needs `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`). `deploy:web` does not build: it uploads the `dist/client` that `deploy:backend`'s build just produced, so run `bun run build` first when using it on its own. Normally CI runs this (it installs the pinned CLI itself); a local run is the fallback
- Hosting locally: `bun run serve:hosting` (`vp preview`, serves the built `dist/client` on port 4173; the `cf dev` serving it replaces used 8787). The way to exercise the SPA catch-all — an unmatched path returns `index.html` with 200 — before deploying; `bun dev` does not. It is a static preview, not workerd, so it proves the catch-all's outcome, not Cloudflare's asset pipeline; the pipeline itself is exercised by `deploy:web` (add `--dry-run` to `cf deploy dist/client` to rehearse the upload without applying it)
- Gates: `bun run verify` runs every check below in one command — toolchain, typecheck, tests, format/lint, import boundaries, fallow as CI runs it, Solid patterns, theme, comments, build. Run this before committing rather than the individual scripts; it is the same list CI runs (`ci.yml` on every pull request, `deploy.yml` before it touches production), so there is nothing to remember and nothing to skip. The individual scripts stay for when you want one of them while iterating. The one gate outside it is the browser gate (`bun run test:e2e`, below): run it when a change touches a page, a list, or the data seam
- Typecheck: `bun run typecheck` (the three TS projects: root `src/`, `scripts/`, `spacetimedb/`)
- Test: `bun run test` (Vitest is the single test runner — ADR 0006; do not use `bun test`). Eight projects in `vitest.config.ts`, split by environment; `bun run test` runs six of them and leaves `e2e` and `connection` to their own scripts (`bun run test:e2e`, `bun run test:connection`), and the `ssr` one takes `src/**/*.ssr.test.tsx` and exists because `src/Document.tsx` can only be rendered by the server build (Solid refuses to client-create `<html>`/`<head>`/`<body>`). **Every test under `src/` fails if it produced a Solid diagnostic or left a hold unacknowledged** — see `## Architecture Notes` for how, and `src/test-setup.ts` for the contract. Three things it asks of a test: a test whose *subject* is a finding declares it with `expectDiagnostics(code)`, `expectSilentHold()` or `expectWideScope()`, each of which **requires** it to appear (never use any of them to quiet a finding about real code); the capture opens in `beforeEach` and closes in `afterEach`, so a file's module scope is not gated (keep fixtures and one-off setup there, never a render) and neither is work a test schedules without settling — an un-awaited `setTimeout` or promise lands on whichever test is open next, or on nothing; settle it with `await resolve(...)` / `flush()`; and tests under `src/` must stay sequential, since the channels are process-global (the gate detects a `test.concurrent` overlap and fails, rather than blaming the wrong test). A fourth thing it cannot ask for, so read it as a rule: **some checks are scale-dependent, and a small fixture cannot reach them**. The scope-width check fails at 30 sources on one scope, `[HUGE_FAN_OUT]`/`[HUGE_FAN_IN]` and the `[HOT_SCOPE_*]` family at their own counts — so a list rendered with three rows in every test proves nothing about the per-row cost; give any list-shaped subject a fixture above the threshold (`src/bracket/BracketView.test.tsx` carries a 31-match fixture for that reason).
- Browser gate: `bun run test:e2e` (the `e2e` vitest project — see `## Architecture Notes`). Fetches the browser it needs: when the headless Chromium the pinned `playwright-core` wants is not where it looks, the global setup installs the headless shell — into playwright's own per-platform default store when `PLAYWRIGHT_BROWSERS_PATH` is unset, and into `~/.cache/ms-playwright` with the test workers pointed there when the variable names a store that lacks the build — so a hosted agent image whose `PLAYWRIGHT_BROWSERS_PATH` holds a different build needs no setup step and is never written to (the preinstalled build is not a substitute: a different Chromium build's timings trip the gate's wall-clock codes where the pinned shell passes — the measurement is in `docs/diagnostics-gates.md`). `playwright-core` is pinned exactly, so the browser build follows the lockfile; `bun x playwright-core install chromium` ahead of time, as CI does, is only a way to skip that first download. Starts its own SpacetimeDB standalone and dev server unless a local one is up, or `E2E_BASE_URL` points at a page served in `--mode e2e`. Not part of `bun run verify` — it needs a browser, a backend binary and two servers, a minute or two `verify` should not carry on every run — so CI runs it as its own job (`ci.yml` `e2e`, with both downloads cached), independent of `verify`; `deploy.yml` runs it too, as its `e2e-gate` job, and the deploy waits on it.
- Format + lint: `bun x vp check` (`--fix` to apply). [Vite+](https://viteplus.dev) owns the dev/build/test/fmt/lint toolchain: the `dev`/`build`/`serve`/`test` scripts delegate to `vp`, `vite` is aliased to `@voidzero-dev/vite-plus-core` via `overrides`, and test files import from `vite-plus/test`. oxfmt/oxlint config (including the ignore list for generated/vendored/tool-managed files) lives in the `fmt`/`lint` blocks of `vite.config.ts`; `vp check` also runs tsrs type checks, which complement but do not replace `tsc --noEmit`. Warnings fail the check (`lint.options.denyWarnings` in `vite.config.ts`): Oxlint's built-in rules sit at `warn`, so without it a warning would pass — a clean run means zero warnings and zero errors
- Solid pattern guard: `bun run lint:solid` (runs `solid2-kit check` — blocks React / Solid 1.x patterns in `src/` — plus `solid2-kit doctor` for project wiring drift)
- Toolchain guard: `bun run check:bun` — Bun enforces neither `packageManager` nor `engines.bun` (it installs under any version, silently), so this is the substitute: it fails when the running Bun is outside `engines.bun`, or when `packageManager` contradicts that range, and warns when you are in range but off the pin. Run it first if anything about an install or a lockfile looks wrong. CI derives the version from `packageManager` (setup-bun's `bun-version-file`), so it is declared once; `bun run check:bun -- --strict` then runs before `bun install` and fails on an inexact match, which is what catches the action resolving something else — its reader falls back to `engines.bun` and then to `latest` without failing
- Tailwind vocabulary: `@shadcn/lint`, run by `bun x vp check` (`lint.jsPlugins` in `vite.config.ts`, ADR 0012). Fails on any class `src/theme.css` does not define — raw palette colors, arbitrary values, typos that would silently generate no CSS — on `style` properties other than custom properties, and on a caller restyling one of the repo's own components (`no-restyle`: every relatively imported component is guarded; callers may pass `layout` classes only); each message names the repair. It is not officially Solid-aware, so `scripts/shadcn-lint.test.ts` pins the class forms it must keep reading
- Theme guard: `bun run lint:theme` (the bans that are valid Tailwind and so invisible to the above: `dark:` variants, since every token is theme-complete via `light-dark()` — ADR 0007; and the `style` attribute outside `src/bracket` — ADR 0012)
- Import boundaries: `bun run lint:imports` ([ImportLint](https://github.com/uhyo/import-lint): each directory is a package; exports are package-private unless tagged `/** @public */`. Model and fixing guide: `.cursor/skills/import-lint/SKILL.md`, or `bun x import-lint explain <rule>`)
- Comment guard: `bun run lint:comments` — prose comments are banned outside the checked-in baseline (`scripts/lint-comments.baseline.json`), which may only shrink: a new prose comment fails, and so does a baseline entry whose comment no longer exists. Machine directives are not prose and stay exempt (import-lint tags, fallow/oxlint suppressions with their reasons, shebangs, `/// <reference>` tags). A fact worth keeping belongs in an ADR or a doc, not a comment; the audit process and the ratchet update procedure are the `/delete-comment` skill (`.claude/skills/delete-comment/SKILL.md`)
- Update Solid agent guidance: `bunx solid2-kit sync` (rules, skills, and the managed AGENTS.md/CLAUDE.md blocks are owned by [solid2-agent-kit](https://github.com/lightsound/solid2-agent-kit); do not edit them by hand)
- Fallow: `bun run fallow` (full), `bun run fallow:audit` (changed files), `bun run fallow:ci` (what the CI `fallow` job checks, and part of `verify`). The CI job never installs dependencies, and fallow answers differently when `node_modules` exists: measured on the ADR 0020 split, a local run reported none of five findings CI failed on (four private-type-leaks, one unused devDependency) and a copy without `node_modules` reported all five. `fallow:ci` runs on such a copy of the working tree, so trust it, not a plain local run, to predict CI. `fallow` is pinned exactly in `package.json` because the CI action installs whatever version that field names
- Fallow agent surfaces: `.cursor/mcp.json` / `.mcp.json` (`fallow-mcp` entry only), skills under `.agents/skills/fallow` and `.claude/skills/fallow`. Re-run with `bunx fallow agent install` (byte-stable). Do not run `fallow similar-code setup` unless a human asks.

## Production deployment

Two production surfaces (ADR 0010): the **SpacetimeDB module on Maincloud** (database `cobracket`) for `spacetimedb/`, and a **Cloudflare Worker serving static assets** (`cloudflare.config.ts` is the whole Worker configuration; `cf deploy dist/client` uploads the prebuilt assets, with no delegated build) for the client build. Continuous deployment is `.github/workflows/deploy.yml`: a push to `main` runs the gates, then `bun run deploy`. Everything below is also runnable by hand as a fallback.

**Backend cutover (migration slices M5–M6, 2026-11-21)**: production ran on Convex until M5 and starts empty on SpacetimeDB — no Convex data was migrated (the disposition the owner confirmed at M5). M6 removed the Convex backend from the tree, so the old deployment is no longer a rollback path: rollback is the previous SpacetimeDB module and bundle. The Convex production deployment itself was not deleted; its teardown is the owner's aftercare.

**Status: live for design review** (owner's decision; first deploy 2026-09-27; `docs/vision.md` "Project posture"). The URL is for the owner's own review until they decide to share it; do not advertise it or treat production data as durable yet.

- URLs: web `https://cobracket.cobracket.workers.dev` (Worker `cobracket` on the account's `cobracket` workers.dev subdomain), SpacetimeDB `https://maincloud.spacetimedb.com` (database `cobracket`).
- Secrets are **repository** secrets (Settings > Secrets and variables > Actions > Repository secrets — not an Environment, which `deploy.yml` does not declare). Agents do not need them: CI deploys. Never put any of them in `.env.local` — that file is local development only
  - `SPACETIMEDB_TOKEN`: the owner's SpacetimeDB login token — on the owner's machine, `spacetime login show --token` prints it (the `--token` flag matters: without it the command prints only the Identity, which is not a credential). The token's identity owns the production database, so CI publishes as the owner (the deploy job runs `spacetime login --token` with it first — the 2.15 CLI takes its token from its own config file, not from an environment variable). Token issuance stays with the owner; if it leaks, revoke it from the same login session and replace the secret
  - `CONVEX_DEPLOY_KEY` (removal note — not one of the three secrets the preflight checks): read by nothing since M6 removed the Convex backend; it is removed from the repository secrets as the post-merge step of M6, once the post-merge deploy is verified
  - `CLOUDFLARE_API_TOKEN`: an **account** API token (Cloudflare dashboard > Manage Account > Account API Tokens > Create Token; needs Super Administrator), not a user token — it belongs to the account, so CI keeps deploying whatever happens to one person's membership. Permission: the Workers **Editor** role scoped to the `cobracket` Worker only (the legacy "Workers Scripts" permissions are superseded by these roles); no zone permissions, since the Worker only serves `workers.dev`. Editor can deploy an existing Worker but not create one — creating needs product-level Admin — so create the `cobracket` Worker once in the dashboard (Workers & Pages > Create > Hello World, named `cobracket`) before issuing the token; the first deploy replaces its script. No IP filter (GitHub-hosted runners have no fixed addresses). The workflow sets `CLOUDFLARE_ACCOUNT_ID` so `cf deploy` needs no account-discovery call — the `/memberships` lookup account tokens cannot answer
  - `CLOUDFLARE_ACCOUNT_ID`: the Account ID shown on the Cloudflare dashboard's Workers & Pages overview. The account must have a `workers.dev` subdomain (created the first time Workers & Pages is opened)
- Until all three secrets exist, the workflow's `preflight` job skips `deploy` (grey, with a notice annotation naming the missing secrets) instead of failing the run, so a red `main` always means a failed gate or a failed deploy — never "secrets not set yet". Nothing needs re-enabling: the next push (or a manual run of the Deploy workflow) after the secrets are added deploys
- There is no auth-key seeding step any more: SpacetimeDB mints identities natively (ADR 0031), so there are no signing keys to provision. The module secret (ADR 0032) was seeded once, out-of-band, immediately after the first production publish, while the database was still fresh; the deploy never generates or rotates it, and a second seed is refused by the module itself
- Deploy order inside `bun run deploy` is deliberate: `deploy:backend` publishes the module first and only then builds the client with the Maincloud host and database baked in, so the bundle that points at the new backend is built once the module it talks to is live; `deploy:web` uploads `dist/client` afterwards. If the upload fails after the publish, production keeps serving the previous bundle against the new module — so re-run the workflow, do not hand-patch
- `bun run deploy:backend` bakes `VITE_SPACETIMEDB_HOST` and `VITE_SPACETIMEDB_DB` into the build (package.json). The values are public identifiers, not secrets. It writes no files, so it never disturbs `.env.local`
- Never point local development at production: local dev stays on the local standalone (127.0.0.1:3100). The production database shares the local one's name (`cobracket`) but lives on `--server maincloud` — before any command that can touch production, know which server and deployment it targets and name them in your report. Until the owner shares the URL, production changes need no consent (`## Agent Rules`, the first rule); this repo's rule overrides the skill's consent step
- Tournament creation is anonymous and unthrottled in the current code: the account requirement (ADR 0024) lands with slice 1 of `docs/specs/events.md`, and the per-account creation and publish limits (ADR 0027) with slice 3. The operational cap is a **spending limit and usage alert on Maincloud** for the production database (console.spacetimedb.com; ADR 0027 adds a usage alert in Resend beside it); set it before sharing the URL widely

## Fallow

- Every rule is `error` except `policy-violation`, which is `off` because no `rulePacks` are authored. Do not demote a rule to warn; turn it off only if the finding cannot be true for this repo, and say why in `.fallowrc.jsonc`.
- fallow sees dead code in `spacetimedb/` normally — no plugin makes its files entry points or credits their exports — so an unused export in the module is reported like anywhere else (ADR 0031).
- `coverage-gaps` gates `fallow health --coverage-gaps` and nothing else: the default run and `fallow audit` do not consult it, so it can exit 1 without turning CI red. Read its **listing**, not its percentage — it is a static test-dependency graph, which cuts both ways: `src/router.ts` lazy-importing every page made it count `src/pages/Tournament.tsx` as covered the moment any page had a test while nothing exercised a line of it, and now it counts `scripts/lint-theme.ts` as untested although `scripts/lint-theme.test.ts` drives it through six cases — as a subprocess, which is the only way to exercise a Bun script with its own `Glob` and cwd, and a subprocess is not an import edge. That file is the whole remaining listing (97.9%), so this rule's floor is 1 and a green run is not available; the same applies to any future script tested this way.
- Type-aware analysis is on (`typeAware.enabled`, `require: best-effort`). Prefer `--type-aware --symbol-impact` / `fallow inspect --file <path>` before deleting a symbol.
- Use `fallow audit --format json --quiet` before committing AI-generated changes.
- Use `fallow dead-code --format json --quiet`, `fallow dupes --format json --quiet`, and `fallow health --format json --quiet` for targeted checks.
- Use `fallow list --entry-points --format json --quiet` and `fallow list --boundaries --format json --quiet` to inspect project shape.
- Solid 2 start mode has no `src/main.tsx`. Keep `src/App.tsx` and `src/Document.tsx` in `.fallowrc.jsonc` `entry` or they look unused.
- `fallow doctor` checks project readiness (config, workspaces, type-aware companion, caches) without analysing or mutating anything. Run it first when a fallow command behaves oddly, before re-running the analysis.
- Two tools guard imports, on different axes, and neither replaces the other. ImportLint works at **export** granularity (every directory is a package; exports are package-private unless tagged `/** @public */`) — that is what holds a risky dependency behind a narrow module (ADR 0004) and what blocks `src/` from reaching the backend module's internals. fallow `boundaries` works at **zone** granularity (which directories may import which), which ImportLint cannot express once an export is `@public` and therefore visible app-wide. The one zone rule configured is exactly that gap: `src/bracket` (the pure layout layer, ADR 0007) may import no other zone, so it cannot acquire a backend client through the seam's (`src/lib/backend`) `@public` exports. Verified both ways — that import passes ImportLint and fails fallow. Do not restate ImportLint's model as zones.
- When a rule is `error` with nothing configured, fallow says so under `audit`'s `workspace_diagnostics` and the zero count means nothing ran — check there before reading a green audit as enforcement. That is why `policy-violation` is off rather than left `error` with no rule packs, and why `boundary-violation` only stayed `error` once zones existed.

## Agent Rules

- Until the owner shares the URL, cobracket has no users (`docs/vision.md` "Project posture"), so **backward compatibility is not a constraint anywhere**: rename or move reducers and views, change URLs, drop or reshape tables, fields, and indexes, and clear stored data — local or production — whenever that is the simpler design. Write no migrations, compatibility shims, deprecated aliases, or fallbacks for old data, and do not weigh "existing data" or "old clients" in a decision. This covers production too: neither a deploy nor a command run directly against production (clearing a table, setting an env var) needs the owner's consent first — name the deployment you acted on in your report. The owner lifts this rule when they decide to share the URL
- Do not edit `spacetimedb/bindings/` (generated; regenerate with `bun run spacetime:codegen`)
- Never style with `dark:` variants or raw/arbitrary color values. Use the semantic tokens from `src/theme.css` (`bg-surface`, `text-ink`, `text-accent`, Match-state `live`/`win`/`loss`, ...); they resolve both themes via `light-dark()`. `bun run lint:theme` and `bun x vp check` enforce this
- Write conditional classes as an object inside an array (`class={["base", { "text-win": won() }]}`), never a bare object `class={{ ... }}`: `@shadcn/lint` does not read the bare form, so a typo there passes every gate (ADR 0012)
- A component owns its look: callers pass layout classes only (margin, width, placement), never color, padding, border or type (`no-restyle`, ADR 0012). A caller that needs a different look is a variant prop on the component, not a `class`
- Never use `style` outside `src/bracket`; style with classes. Inside the Bracket, `style` only sets custom properties for runtime geometry and classes consume them (`style={{ "--card-x": ... }}` + `translate-x-(--card-x)`) (ADR 0012)
- Do not change `host: '0.0.0.0'` or re-enable Solid devtools without installing its optional peer
- Package manager is Bun 1.4 (`bun.lock`). Do not add npm or pnpm lockfiles
- Project decisions override generic skill advice: auth is the module's native Identity binding behind the isolated `src/lib/auth` module (ADR 0031) — anonymous identities in the current code, and from slice 1 of `docs/specs/events.md` an email one-time code, required on the whole Organizer side (ADR 0021, 0024); billing, custom domains, and similar capabilities are out of MVP scope (`docs/specs/mvp.md`)

## Solid 2.0 (not React, not Solid 1.x)

- All TSX in this project is Solid 2.0. Components run **once**; reactivity flows through signals/stores to JSX. - Before writing TSX, read the `solid-2` skill (`.cursor/skills/solid-2/SKILL.md` for Cursor, `.claude/skills/solid-2/SKILL.md` for Claude Code): patterns, decision tables, official doc URLs. Hard rules auto-attach from `.cursor/rules/solid-2.mdc` in Cursor and live in a managed block in `CLAUDE.md` for Claude Code.

Use the project's `lint:solid` script if one exists; otherwise `npx solid2-agent-kit check` (with the kit as a devDependency) or `npx github:lightsound/solid2-agent-kit check`. An edit-time hook may also run this gate automatically after each file edit — treat its findings as errors to fix immediately, not warnings. Do not install `eslint-plugin-solid` (built for Solid 1.x; misreads Solid 2 idioms).
- After editing `package.json`, `tsconfig*.json`, or root config files (Vite, ESLint), run `solid2-kit doctor` — it fails on React/Solid 1.x wiring: `react`/`vite-plugin-solid`/`eslint-plugin-solid`/SolidStart dependencies, 1.x `solid-js` ranges, and `jsx`/`jsxImportSource` values other than `preserve`/`@solidjs/web`.

- Solid 2.0 shipped recently and breaks with 1.x — never trust pre-2.0 Solid docs, tutorials, or training knowledge. Verify APIs against https://docs.solidjs.com/llms.txt (the canonical docs serve plain markdown). If the project has `@solidjs/router`, server functions, or `@solidjs/meta`, use those official pages (see the skill's official-docs index) — not React Router, Next.js, SolidStart 1.x, or Solid Router 0.x/1.x JSX `<Route>`/`<A>`. Core `action` from `solid-js` is a generator transaction; router `formAction`/`query` from `@solidjs/router` are POST forms and a read cache (router `action` is a deprecated alias of `formAction`, and `useAction` is deprecated: call the server function directly — a mounted router applies its revalidation and redirect on any call <!-- upstream:router-action-deprecated -->). React `useDeferredValue` is `createDeferred(fn)`: an async memo that lags but never leads <!-- upstream:create-deferred-export -->. Core `refresh(source)`, router `revalidate(key)`, and server-function `return reload(...)` are three different APIs. Pass the accessor to `isPending(user)`, not `isPending(user())`. Pass async values as values (`user={user()}`) — JSX props are lazy; types stay `User`, not `Promise<User>`. `<Loading>` wraps the read, not the memo. Nested fetches run in parallel (components do not suspend). `isPending` is a per-expression question (`isPending(() => props.story)` / `isPending(selectedId)`), not a global spinner; `latest(selectedId)` is opt-in so highlight and content stay consistent by default. `<Errored>` heals when the source succeeds. Pass a function to `render`/`hydrate`: `render(() => <App />, root)`. Component teardown is `onSettled`, not `onCleanup` — return the cleanup; `onCleanup`, memo/effect creation, and `flush()` throw inside the `onSettled` callback in dev. Creating a memo/effect/root inside an effect's `apply` callback throws in dev too (`[PRIMITIVE_IN_EFFECT_CALLBACK]`) — create it in the body or compute phase. <!-- upstream:primitive-in-effect-callback --> Effect `apply` functions use block bodies (`(t) => { document.title = t; }`): any return value other than a cleanup function halts reactivity. Stores are written only through the setter's draft — writes to the store itself are ignored (dev warns `[STORE_WRITE_OUTSIDE_SETTER]` <!-- upstream:store-write-outside-setter -->), and `Map`/`Set`/`Date` inside a store are not tracked. Shared state, app-wide included, is created in a provider at the root of `App` (`createContext<T>()` + `useX()`), never a module-level signal/store (one instance serves every SSR request). Errors thrown out of an `action` never reach `<Errored>` — catch them in the action or `.catch` the call. One router instance; in-app navigation is `useNavigate` / `<a href>`, not `window.location`. Types: `solid-js` exports no `JSX` namespace — markup types are `JSX.Element` from `@solidjs/web` or `Element` from `solid-js` (alias it `SolidElement` next to DOM code) <!-- upstream:jsx-namespace-absent -->. Reset-a-signal-on-change is a writable derivation (`createSignal(() => { source(); return initial; })`), never an effect calling the setter. Client mode mounts with `render()` into an empty body — no hydration mismatch exists, so never defer initial values to post-mount React-style (that can overwrite persisted state). Client → server is additive (same setters + `action` + server functions): do not rewrite App with loading/error branches, disable optimistic rows until ack, invent tRPC, or refetch in `hydrate`/`onSettled`. The graph continues across the wire (`live()` owns the client connection; `<Reveal>` not a delayed stream). A server bundle uses `handleRequest` / Fetchable `fetch`; client-only start is static `dist/client`. One browser-only value takes `ssrSource: "client"` on the memo/signal/derived store, not a `clientOnly` component split. Router link state is `aria-current`/`data-active` + CSS (`data-pending` is opt-in via `createRouter({ links: pendingLinks })`; `useLinkState`/`useIsRouting` in JSX) <!-- upstream:pending-links-opt-in -->; link preloading is opt-in too (`preloadLinks: intentPreload()` for hover/focus/touch; none by default; opt one link out with the string `preload="false"`) <!-- upstream:preload-links-opt-in -->; search params via `useSearchParams`; router forms validate on the server (`throw respond({issues},{400})`) with inline errors from `useSubmissions`. Confirmations on another channel — fire-and-forget sends, and mutations whose result is read through `live()` — wait with `yield until(predicate, {timeout})`, not `refresh()`. Declare live reads `live(fn)` — it implies `GET` (`live(GET(fn))` is the same) <!-- upstream:live-implies-get -->. Debounce at the handler; inputs feeding a request bind `latest(query)`. Dev diagnostics are errors: `[STRICT_READ_UNTRACKED]` means a read outside a tracking scope, `[ASYNC_STORE_SETTER]` means a store setter callback awaited (the draft is a synchronous transaction — await first, then write) <!-- upstream:async-store-setter-throws -->, a held write needs `isPending`/`latest`/optimistic/`affects` feedback or dev + attribution reports `[SILENT_HOLD]` (a write that must not join another update's hold goes in `onFlush(...)` <!-- upstream:on-flush -->), and `[UNCOMMITTED_INPUT_OVERWRITTEN]` means a `value`/`checked` binding re-wrote the bound value over text the user typed but never committed (`value={props.name} onChange={commit}` with no draft signal) — bind a draft signal written from `onInput`, or `defaultValue` <!-- upstream:uncommitted-input-overwritten -->. Error monitoring is `configureClientErrors` / `configureServerErrors` (or per root `render(fn, root, undefined, { onError })` — options are the 4th argument), not a side effect inside `<Errored fallback>`; the server hook must return a reference or nothing, never the error itself. `<Dynamic>` is deprecated — use `dynamic()`. <!-- upstream:dynamic-deprecated --> Observability is on by default in development: whenever a change touches stores, lists, async, actions, or effects, keep the dev console free of `[CODE]` findings and run an attribution session (`/__solid/diagnostics` `begin` → interact → `whyDidRun` / `costs` → `end` with `@solidjs/diagnostics` installed, otherwise `isDev`-guarded `attribution.enable({ log: false })` + `why()` / `costs()`) before finishing. `vite dev` is always the dev build; `solid({ observe: true })` is a production opt-in.

# Personal working style

How this repository's owner works with agents. Portable: nothing here depends on one machine or repository. Where a project-specific section of the file that carries this text says otherwise, the project-specific section takes precedence.

## Chat and reporting

- The chat between the agent and the user is Japanese.
- No interim progress reports. Report once, when the work is done, with the results.
- Prose is concise and plain, but items the rules require (the decisions table, PR URLs, test counts, and other structured facts) are never omitted or aggregated for brevity.

## Decisions

- When implementation needs a judgment call, do not ask the user. Propose a solution, then run rounds of searching for a strictly better alternative or a silver bullet; stop the search when a round produces no new option.
- Then extract the principle that generates the constraint and check whether the problem can be dissolved structurally. Only after that pick the best option.
- The final report lists every judgment call in a table with three columns: decision, chosen option, and the round in which no new option appeared. Never summarize or aggregate this table; when relaying another agent's report, keep it intact.

## Delivery

- When the work is done, open the PR as ready for review, not as a draft, and address review-bot findings.
- Do not create or update `README.md` unless the user explicitly asks.
